# 한국어 ASR 벤치마크 설계

이 문서는 공통 벤치마크의 측정 계약입니다. [공통 파일 평가](evaluation.md)의 manifest·CER·batch RTF·추론 CPU/RSS·재채점은 구현했고, paced/live 지연·정렬·드롭·백로그는 아직 미구현입니다. 실제 RP5에서 공식 샘플 1개 및 [KSS 개발용 50개](../results/summaries/zipformer-kss-dev50-20261028.md)의 batch 평가·결과 회수·재채점을 확인했습니다. 기존 단일 샘플 로그는 [실험 기록](../experiments/m1_zipformer/README.md)의 제한된 필드만 제공합니다.

보존 프로브를 사용하는 [반복 도구](rp5_repeat_benchmark.md)는 별도로 구현했습니다. 원본 지연 계측점은 유지하며 자원은 모델 로딩을 포함한 전체 프로세스 범위로 수집하므로, 아래 공통 실행기의 steady-state 및 반환 시점 기준 지표와 구분합니다. [사용자가 제공한 RP5 반복 요약](../results/summaries/zipformer-repeat-20261028-reported.md)은 수신했으며 원시 자료 검증은 아직 남아 있습니다.

## 시간 기준과 모드

경과 시간은 동일 프로세스의 단조 시계(`time.perf_counter_ns`)를 사용합니다. 실행 날짜는 별도 UTC 타임스탬프로 기록합니다. 장비 간 wall clock 차이로 지연을 계산하지 않습니다.

| 기호 | 기준 이벤트 |
| --- | --- |
| `t0` | 첫 오디오 샘플 캡처 시작 또는 paced replay의 가상 캡처 시작 |
| `t_audio_end` | 마지막 실제 오디오 샘플 시각; replay에서는 `t0 + duration` |
| `t_ref_end` | 정답으로 라벨링한 발화/문자/구간의 음향적 끝 시각 |
| `t_capture_end(i)` | 청크 i의 마지막 샘플을 캡처 완료한 시각 |
| `t_enqueue(i)`, `t_dequeue(i)` | 처리 큐 입력 및 인출 시각 |
| `t_decode_start/end(i)` | 청크 디코딩 처리 시작 및 종료 시각 |
| `t_partial` | 최초 비어 있지 않은 부분 가설을 호출자에게 반환한 시각 |
| `t_final` | 최종 가설을 호출자에게 반환한 시각 |

자막 UI에 전달·렌더링하는 시스템에서는 별도로 `t_display`를 기록해 엔진 반환과 화면 표시를 구분합니다. 오디오 전처리, resampling, I/O, 모델 로딩, 워밍업을 포함한 범위를 결과에 명시합니다.

`batch`는 준비된 전체 PCM을 최대 속도로 처리합니다. `paced_stream`은 청크 끝의 오디오 시각까지 대기한 뒤 입력합니다. `live`는 향후 마이크에서 실제 캡처하며 두 모드와 구분합니다. 각 모드의 실험을 섞어 집계하지 않습니다. 모델 로딩 시간과 cold start는 별도 항목으로 측정하고, steady-state 값에서 제외합니다.

## 정확도·속도·지연 정의

| 지표 | 정의·단위·해석 |
| --- | --- |
| CER | 정답 문자 수 `N`에 대해 `(S + D + I) / N`. Unicode NFC → 공백 문자 제거 → Unicode 범주 P(문장부호) 제거 후 코드포인트 단위 Levenshtein 거리. 숫자·영문 대소문자는 유지. 정규화 정책과 버전을 고정하고 원문을 보관. Corpus CER은 전체 편집 수 합 / 전체 정답 문자 수 합이며 샘플 CER 평균과 구분 |
| 빈 정답 | `N=0`인 샘플의 CER은 미정의(`null`). 별도로 빈 정답 샘플 수 및 비어 있지 않은 가설 수를 보고. Corpus CER의 분모·분자에서는 해당 샘플 모두 제외. 전체 N=0이면 corpus CER도 `null` |
| 파일 일괄 처리 RTF | `batch`에서 준비된 float PCM으로 새 인식 상태를 만드는 시점부터 최종 결과 반환까지의 wall time / 실제 오디오 길이. 파일 읽기·변환·모델 로딩·워밍업·채점·쓰기 제외; 특징 추출·디코딩·flush 포함. Corpus RTF는 성공 파일의 시간 합 / 오디오 길이 합. 1 미만은 이 범위에서 오디오 길이보다 짧게 처리했다는 뜻 |
| 스트리밍 처리 RTF | 강제 입력 대기를 제외한 처리 구간의 wall time 합 / 실제 오디오 길이. 입력·디코딩·결과 조회·최종 flush를 포함하고 처리 구간 중복 합산 금지. 전체 replay 경과 시간 / 길이와 구분; CPU 사용 시간 / 길이도 별도 지표 |
| 오디오 시작 기준 첫 부분 자막 시점 | `t_partial - t0`(초). 발화 시작 전 무음, 모델 lookahead, 청크 수집·큐·추론을 포함. 비어 있지 않은 부분 가설이 없으면 `null`과 사유. 화면 기준이면 `t_display - t0`를 별도 이름으로 기록 |
| 실제 인식 지연 | 라벨링한 문자/구간의 음향적 끝 `t_ref_end`부터 그 내용을 포함한 가설 반환까지(초). 정답-가설 대응 및 최초 등장/이후 수정 없이 확정되는 stable 기준을 명시. alignment 없이 첫 부분 시점에서 임의의 청크 길이를 빼서 계산하지 않음. 미계측은 `null` |
| 청크 처리 지연 | `t_decode_end(i) - t_decode_start(i)`(ms). 큐 대기를 제외. 최신 입력 청크 끝부터 결과 반환까지의 지연도 별도 기록 가능하나 음향적 정답 기준 인식 지연과 동일하지 않음 |
| 최종 확정 지연 (입력 끝 기준) | `t_final - t_audio_end`(초). 최종 flush 포함. 파일 끝과 실제 발화 끝이 다를 수 있음. 서비스에서 `t_final - t_ref_end`를 발화 끝 기준 지표로 별도 기록하여 endpoint 대기를 포함 |
| p50/p95 지연 | 위 지연 종류별로 관측 집단·모드·스레드를 분리하여 계산. 청크 지연은 유효 청크별, 최초 부분/최종 지연은 발화 실행별. nearest-rank: 정렬 후 `ceil(p*n)`번째 값(p=0.50/0.95, 1부터 시작). n·결측·실패 수를 함께 보고. 단일 측정에서 분위수를 성능 통계로 제시하지 않음 |

현재 프로브의 첫 시간은 디코딩 직후 `get_result`/`print` 전 기록한 근사값입니다. 공통 실행기에서는 위 표의 결과 반환 시점으로 계측점을 통일합니다. 기존 로그를 새 지표로 소급 변환하지 않습니다.

## 자원·안정성 정의

| 지표 | 정의와 수집 범위 |
| --- | --- |
| CPU | RP5의 추론 프로세스 및 명시한 자식 프로세스의 `(user + system CPU 시간 증가) / 관측 wall time * 100`(%). 코어 하나 최대 100%, 4코어 최대 약 400%인 기준. 전체 장비 CPU와 분리. 원시 시간 차분으로 전체 구간 평균을 계산하고 고정 100ms 간격 표본의 p95·최대도 기록 |
| RSS | 프로세스별 resident memory bytes를 MiB로 변환(`bytes / 2^20`). steady-state 평균·관측 최대, 로딩 포함 최대를 분리. Linux `/proc` 또는 수집 라이브러리·버전을 명시. 여러 프로세스 RSS 합은 공유 페이지를 중복 계산할 수 있음. 측정 간격 사이 피크 누락 가능 |
| 드롭 | 캡처부터 디코더까지 수락하지 못한 청크 수와 실제 손실 오디오 초. 단계별 드롭 위치·정책, 중복 없이 계산한 분모(입력 청크 수/총 오디오 길이)와 비율을 기록. 장치 underrun/overrun도 별도 횟수로 기록. 미계측을 0으로 쓰지 않음 |
| 백로그 | 큐에서 대기 중이며 아직 인출되지 않은 실제 샘플 수 / sample rate(초), 큐 깊이(청크), 최고령 청크의 대기 시간(ms). 처리 중인 청크는 제외한다고 고정. 100ms 표본의 p50/p95·최대와 시작/종료 잔량, 시간에 따른 증가 추세를 기록 |
| 입력 마감 초과 | 청크의 기대 입력 완료 시각과 실제 처리 종료 시각의 차이의 양수 부분(ms). 처리 중 청크·스케줄 지연이 섞인 보조 지표. 큐 백로그나 드롭 수의 대체값이 아님 |

수집기 자체 비용, 프로세스 범위 및 표본 간격을 결과에 남깁니다. 입력 큐 용량·가득 찼을 때 버림/차단 정책을 고정합니다. 백프레셔로 입력을 느리게 하는 것과 실제 손실을 구분합니다. 현재 WAV replay 프로브는 마이크·별도 큐가 없으므로 드롭·백로그를 검증하지 못합니다.

## 비교 절차

1. 동일한 정답 manifest, 데이터 split, 음량·resampling 정책, 청크 크기, endpoint/flush 설정을 고정합니다. 짧은/긴 발화, 앞뒤 무음, 숫자·외래어, 잡음 조건을 포함하고 데이터 수·총 길이를 기록합니다. 데이터 유출을 피하도록 튜닝용과 최종 평가용을 분리합니다.
2. RP5의 OS·커널·aarch64·Python·런타임 버전, 모델 및 오디오 SHA-256, 정밀도/양자화, 전원·냉각·CPU governor·클럭·온도·throttling, 백그라운드 부하, Git 커밋과 설정을 기록합니다.
3. 모델 로딩/cold start를 별도 측정합니다. 워밍업 3회 후 각 조건을 최소 30회 반복하는 것을 시작안으로 삼고 실제 횟수를 기록합니다. 1/2/4스레드 순서를 교차 또는 무작위화해 열·순서 영향을 줄입니다. 반복해도 원본 오디오가 하나면 데이터 다양성은 증가하지 않습니다.
4. batch RTF와 paced/live 지연을 독립 실행에서 측정합니다. 각 실행의 가설과 이벤트 시간을 보관하고, 원시 자료에서 정의에 맞춰 집계합니다. 실패·OOM·타임아웃을 삭제하지 않으며 성공률·결측 이유를 함께 보고합니다.
5. 여러 샘플·반복 실행의 CER, RTF, 지연 분포, CPU/RSS, 드롭/백로그를 함께 비교합니다. p95 꼬리와 장시간 백로그 증가·온도 변화를 확인한 후 스레드·청크·양자화를 선택합니다.

30회는 시작안이며 통계적 충분성을 보장하지 않습니다. 단일 WAV 1회 값만으로 최적 스레드 수, 실시간 서비스 안정성, 정확도, p50/p95를 결론 내리지 않습니다.

## 결과 보관

원시 실행 자료는 `benchmarks/runs/<run-id>/` 또는 `results/<run-id>/`에 둡니다(Git 제외). 환경 JSON, pip freeze, 설정, manifest/자산 체크섬, 가설, 이벤트 타임라인, 자원 표본, 실패 상태를 보관합니다. 측정하지 않은 필드는 `null` 및 이유를 씁니다. 숫자 0은 측정된 0일 때만 사용합니다.

작은 익명 요약은 `results/summaries/<run-id>.json`/`.csv`/`.md`로 검토 후 버전 관리할 수 있습니다. 원시 타임라인·전사·개인정보·대용량 배열을 요약에 넣지 않습니다. 기존 실험의 요약은 출처 보존을 위해 해당 `experiments/` 안에 유지합니다.

초기 원시 로그 3개는 `archive-initial-zipformer-20261028` 태그에 이력·체크섬과 함께 보관하고 현재 main에서는 추적하지 않습니다. 현재 브랜치에서는 예외 없이 원시 결과를 Git 제외 경로에 두며, 작은 요약만 검토해 버전 관리합니다.
