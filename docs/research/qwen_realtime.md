# Qwen 단독 1배속 연속 입력 검사

2026-11-10. 최근 고정100개 결과는 **파일 전체 batch 평가**입니다. 이전 Zipformer+Qwen 보정의 1배속·장시간 기록과 구분합니다. 이제 Qwen 단독의 실제 자막 지연을 우선 측정합니다.

## 첫 구현과 고정 조건

- 기존 `dataset.prepare_track`으로 해시가 있는 WAV를 연결하고, 각 원음 뒤에 1초 무음을 추가합니다. 원본은 변경하지 않습니다. 파일 경계로 VAD·모델을 초기화하거나 전사를 강제 확정하지 않습니다.
- 기존 `streaming.run_paced`의 독립 프로세스가 100ms 청크를 1배속으로 공개합니다. 입력 큐는10개이며 처리 지연 때문에 입력 시계를 늦추지 않습니다. 손실 프레임을 이어 붙이지 않고 오류로 남깁니다.
- 기존 `SegmentPipeline`과 `BoundedProbabilityVad(K2SileroProbability)`를 재사용합니다. 같은 검증 Silero 파일·16kHz·identity PCM·문맥0·최대5초 구간입니다. Python ORT 확률 경로는 이전 native VAD와 완전히 동일하다고 주장하지 않습니다.
- Qwen GGUF Q8_0·2T·기존 런타임/greedy/context512/출력128토큰을 유지합니다. 모델1회 로딩, 첫 추론1회·추가 워밍업3회 후 입력 시계를 시작합니다.
- 활성 음성이2초 쌓이면 첫 부분 전사를 요청하고 이후1초마다 도착한 접두 PCM만 다시 전사합니다. 긴 발화는5초에서 구간 확정하고 다음 구간을 받습니다. 부분 결과는 수정될 수 있습니다.
- 전사 작업자는 하나이며 최종 구간 FIFO는4개, 대기 부분 전사는 최신1개입니다. 최종 구간을 우선 처리합니다. 교체된 부분 요청도 기록하며 입력 드롭과 구분합니다. 최종 큐가 차면 오류로 기록합니다.

이 방식은 **음성 수신과 추론이 동시에 진행되는 부분 자막 파이프라인**입니다. 각 추론은 현재까지 받은 짧은 PCM의 batch 호출이며 KV를 초기화합니다. Qwen encoder의 증분 실행·청크 간 KV 재사용·생성 토큰 즉시 배포를 구현한 것은 아닙니다. 현재 어댑터·가중치를 유지하고 중복 재전사의 비용과 실제 지연부터 확인합니다.

## 측정값

| 값 | 기준 |
| --- | --- |
| 첫 자막 / 첫 부분 자막 | 연속 입력 시작→비어 있지 않은 결과 stdout 발행. 확정·부분 종류를 구분 |
| 구간 확정 지연 | 소유 음성 구간 끝의 입력 예정 시각→최종 전사 발행. VAD 종료 대기·큐·추론 포함 |
| 전체 종료 지연 | 마지막 입력 프레임 예정 시각→모든 최종 전사 반환 |
| 처리 대기 | 요청 제출→실제 추론 시작. 입력 큐 backlog와 ASR 작업 큐를 별도 기록 |
| 정확도 | 최종 구간 원문을 순서대로 연결하고 전체 원문 정답에 `ko_cer_v1` 적용. 부분 가설은 정답에 더하지 않음 |
| 실패·자원 | 입력 드롭·교체된 부분 요청·큐 초과·ASR 실패·빈 출력, CPU/RSS·온도·실제 클럭·제한 플래그 |

원시 `jobs.jsonl`은 요청·교체·시작·성공/실패·원문·payload 해시·도착 프레임·시각을 보존합니다. 최종 실패를 빼고 점수를 좋아 보이게 만들지 않습니다. 외부 `thermal-run`은 기존 사용자가 허용한 온도 대기 없는 운영 조건을 사용하며 온도를 기록합니다.

`worker.json`의 `first_caption_from_track_start_s`와 `first_partial_from_track_start_s`가 태그를 구분한 주 지표입니다. 공통 입력기의 `telemetry.first_partial_from_audio_start_s`는 청크 수신 시 관측한 누적 문자열이며 확정 문자열도 포함할 수 있어 별도 주 지표로 쓰지 않습니다. 단어 음향 정답 시각과 engine TTFT는 미계측(null)입니다. VAD 경계는 고정된 음소 끝이 아니므로 다른 분할 정책끼리 구간 지연만으로 우열을 정하지 않습니다.

## 첫 RP5 파일럿

고정100개를 `(길이, ID)`로 정렬해 최단·중앙(0기반50번째)·최장3개를 중복 없이 선택합니다. 결과를 보기 전에 manifest·SHA·순서를 고정하며 길이순으로 연결합니다. 첫 실행 ID는 `realtime-20261110-01`, 원시는 `results/optimization/opt3/<실행ID>/`입니다. 이는 구현·지연 확인용 소규모 파일럿이며100개 정확도 평가나 자연 대화·장시간 안정성 검증이 아닙니다.

[첫 실측 결과](../../results/summaries/optimization/realtime-pilot-20261110.md): 입력·추론 동시 진행은 확인했으나 지연과 추가 삭제 오류·EOF 무음 오인식으로 후보 채택은 보류합니다. 양자화 비교 전에 같은 입력의 부분 요청 off 대조와 VAD 경계를 분리 점검합니다.

Host에서는 가짜 VAD/ASR와 실제 입력 프로세스로 동시 수신·인과성·유한 큐·실패 보존을 확인합니다. main 반영 후 RP5에서 기존 모델·실제 VAD·실제 추론으로 검사합니다. WAV 전체를 미리 메모리에 준비하지만 작업자에는 도착한 프레임 범위만 전달합니다. 전체 WAV·평가 이벤트는 검사 길이에 비례해 메모리를 사용하므로 상시 서비스의 메모리 상한을 주장하지 않습니다.

## 이후 비교

### 2026-11-10 후속 대조 — 결과 확인 전 고정

`realtime-controls-20261110-01`에서 첫 파일럿과 같은 manifest·38.7835625초 입력·Q8·2T·VAD·5초·워밍업·온도 운영 정책을 사용합니다. 순서는 새 부분 on → `--no-partials` off 대조이며 완전 무음도 그대로 처리합니다. 두 실행의 최종 PCM 해시·경계·전사와 지연을 비교합니다. 다음에 `--silence-policy skip-zero`만 바꾼 부분 on 실행으로 EOF 무음 오인식을 확인합니다. 완전0 PCM 생략은 `skipped_silence`로 남기며 입력 손실이나 성공한 ASR 호출로 세지 않습니다. 기존 기본값은 `preserve`입니다.

별도 VAD 진단은 같은100ms PCM에서 기존 native VAD와 현재 bounded VAD의 구간/PCM 해시를 대조하고512프레임별 확률·신호 크기를 보존합니다. ASR 성능 실행과 겹치지 않게 수행합니다. 앞부분 손실의 원인을 확인한 뒤 필요한 VAD 변경만 별도 실행으로 비교합니다. 원음·정답·이전 결과는 유지합니다.

진단에서 두 VAD의 경계·PCM은 같았고 최장 원음 앞6초의 peak는 약0.012였습니다. 후속 `q8-on-zero-gain12`는 `--vad-gain-db 12`만 추가해 비교합니다. 증폭·클리핑은 VAD 입력에만 적용하며 ASR로 전달하는 PCM은 identity 원음입니다. 기존 기본값0dB는 보존합니다. 같은 소규모 목록의 오류가 늘지 않을 때 양자화 파일럿의 공통 경로로 사용하며 전체100개 정확도 채택을 뜻하지 않습니다.

12dB 후보는 실제 오류52→67개로 악화돼 채택하지 않았습니다. 다음 `q8-on-zero-threshold03`은 증폭0dB·부분 on·완전0 생략을 유지하고 `--vad-threshold 0.3`만 바꿉니다. 기본0.5는 보존합니다. 같은3개에 추가 실패 없이 오류가 줄 때 양자화 공통 조건으로 사용하고, 악화되면 기존0.5로 비교합니다.

`realtime-quant-20261110-01`은 같은3개·2T·부분 on·완전0 PCM 생략에서 Q8→Q6_K→Q5_K_M→Q4_K_M 순으로 실행합니다. 같은 VAD 조건·최종 구간 PCM 해시를 확인하고 결과·실패·첫 자막·파일 시각 앵커·확정 지연·CPU/RSS/열을 비교합니다. file type/tensor 혼합 dtype·모델 SHA는 자산 명세에 고정합니다. 새 BF16 원본 SHA는 `12b2894d9a7c98cd8f26670f5a47ab738f42bcc98df21e109be493870c71ba50`이며 각각 독립 변환합니다. 추가 오류·실패·빈 출력이 있는 후보는 채택하지 않습니다.3개는 선별 파일럿이며100개·독립 데이터·장시간 검증은 최종 선정 전 별도 단계입니다.

연속 입력 경로를 확인한 뒤 같은100개 순서·분할·업데이트 간격·2T에서 **텍스트 모델 Q8_0→Q6_K→Q5_K_M→Q4_K_M**을 비교합니다. 오디오 mmproj는 우선 같은 Q8_0 파일을 유지합니다. 낮은 비트가 RP5에서 더 빠르거나 한국어 정확도를 유지하는지는 실측으로 판단합니다. 스레드·빌드·KV 설정은 동시에 바꾸지 않습니다.

고정한 ggml-org 배포 revision에는 text/mmproj의 Q8_0·BF16 파일이 있습니다. 낮은 비트는 같은 BF16 원본에서 각각 독립 생성하고 변환 도구·명령·tensor dtype·SHA를 기록합니다. Q8을Q6으로, 그 결과를 다시Q4로 누적 재양자화하지 않습니다. [llama.cpp 양자화 문서](https://github.com/ggml-org/llama.cpp/blob/7d7f0287530bc8981690f361d8c1627dbae1c99a/tools/quantize/README.md), [고정 자산·런타임](opt2_gguf.md).

기존 `qwen/gguf.py`를 `asset_manifest`로 확장해 낮은 비트에도 같은 평가·연속 실행기를 사용합니다. Q8 기본 설정·배포 해시는 유지하고, 새 자산 명세는 BF16 출처·text SHA·오디오 Q8 SHA·도구 커밋을 검사합니다. `native/gguf/quantize.py`는 별도 변환 환경·빌드에서 각 모델과 명세를 생성합니다.
