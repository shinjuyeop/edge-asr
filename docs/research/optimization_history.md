# ASR 최적화 과정

Qwen3-ASR-0.6B를 Raspberry Pi 5의 ARM64 CPU에서 실행하며 발견한 문제와 개발 방향의 변화를 정리합니다. 2026-11-09부터 11-12까지의 실험 보고서와 구현을 바탕으로 작성했습니다. 각 단계의 수치는 해당 대조 실험 안에서 비교하며, 서로 다른 단계의 지연을 이어 붙여 누적 개선율로 계산하지 않습니다.

이 문서는 중요한 판단이 바뀐 흐름을 설명합니다. 현재 설정과 다음 작업은 [현재 상태](../status.md), 실행 방법은 [실행 안내](../guides/qwen3_optimization.md), 개별 조건·원시 기록은 각 단계에 연결한 보고서를 기준으로 합니다.

## 1. 평가 기준을 연속 입력으로 확장 — 11월 9~10일

초기에는 준비된 WAV 전체를 처리하는 batch 평가로 모델의 정확도와 추론 비용을 확인했습니다. 고정 100개는 Zeroth 60개·FLEURS 40개, 원음 합계 약 14분 51초의 낭독 자료로 정했습니다. 이 자료는 이후 개발·회귀 평가에 반복 사용하며 독립 holdout과 구분했습니다.

입력이 진행되는 동안 언제 자막을 반환하는지 확인하기 위해 WAV를 100ms 단위로 1배속 공급하는 연속 평가를 추가했습니다. 독립 입력과 단일 추론 작업자·유한 큐를 사용하고 파일 경계에서 상태를 초기화하지 않았습니다. 고유 3개 파일럿에서 입력과 추론의 병행·드롭 0을 확인했지만 첫 부분 자막은 5.297초 뒤에 나왔고 연결 CER도 기존 batch 가설보다 나빴습니다.

첫 100개 연속 평가도 호출 실패·입력 드롭 0으로 완료했지만 연결 CER는 14.06%로, 동일 순서의 기존 batch 가설 7.64%보다 높았습니다. 이때는 각 파일에 1초씩 추가 무음을 넣어 총 공급 시간이 약 16분 31초였습니다. 이후 주 비교는 추가 무음 0초로 맞추고, batch RTF와 별도로 첫 자막 발행·최종 반환·입력 드롭·정확도를 판단하는 방향으로 정했습니다. 입력 완료와 인식 품질을 각각 검증해야 한다는 출발점입니다.

근거: [고정 100개 준비](../../results/summaries/optimization/fixed100-preparation-20261109.md), [batch 기준선](../../results/summaries/optimization/fixed100-baseline-20261109.md), [첫 연속 파일럿](../../results/summaries/optimization/realtime-pilot-20261110.md), [첫 100개 연속 평가](../../results/summaries/optimization/realtime100-q8-20261110.md).

## 2. 정확도·완료율·메모리를 함께 보고 GGUF를 주 후보로 유지 — 11월 10일

추가 무음 0초의 같은 100개와 최종 214구간 PCM으로 ONNX INT8과 GGUF Q8을 비교했습니다. GGUF는 연결 CER 13.23%(ONNX 15.98%)·호출 실패 0회(1회)·관측 최대 RSS 1830.53MiB(2096.09MiB)로 유리했습니다. 반면 첫 자막 중앙값은 5.43→6.16초로 늘었고 p95는 12.25→10.92초로 줄었습니다.

이 결과를 근거로 후속 최적화의 주 후보는 GGUF Q8로 유지했습니다. 지연의 모든 지표가 좋아진 선택은 아니었고, 양자화·프런트엔드도 다른 배포 구성 비교였습니다. 양쪽에 남은 같은 VAD 미방출 사례와 batch 대비 추가 오류를 다음 조사 대상으로 삼았습니다.

근거: [ONNX/GGUF 연속 입력 비교](../../results/summaries/optimization/realtime100-backends-20261110.md).

## 3. VAD 누락을 보정하고 구간 길이의 정확도·지연 절충을 확인 — 11월 10일

GGUF에서도 자막이 없는 원음이 남아 있었습니다. 저장 VAD 확률과 전달 구간을 조사하니 낮은 신호에서 시작 지속 조건을 통과하지 못한 사례가 확인됐습니다. 임계값 조정만으로 해소되지 않아 기존 RMS 보정을 VAD 입력에 적용하고 ASR에는 원음을 그대로 전달했습니다.

같은 100개에서 VAD 보정·5초 구성은 미출력 원음 1→0개, 연결 CER 13.23→11.12%로 개선됐습니다. VAD 판정 전환 30초·ASR 상한 8초의 복합 구성은 CER 8.26%로 더 정확했지만, 공통 99개 첫 자막 p95가 기존 10.92초에서15.09초로 늘었습니다. 이 전체 대조는 여러 조건이 달라 8초 구간 하나의 효과로 해석하지 않았습니다.

후속 개발에는 지연을 고려해 VAD 보정·5초를 선택하고 8초 복합 구성은 정확도 참고로 보존했습니다. 보정 5초에서도 첫 자막 중앙값은 늘었고 batch 대비 오류 134개가 남았습니다. 다음 과제는 이 정확도를 유지하며 부분 재전사와 큐 대기를 줄이는 것이었습니다.

근거: [VAD 보정·구간 길이 대조](../../results/summaries/optimization/realtime-accuracy-20261110.md).

## 4. 부분 갱신 빈도를 낮춰 중복 추론과 큐 대기를 줄임 — 11월 11일

부분 자막은 입력 도중의 접두 PCM을 반복 전사해 만듭니다. 같은 음성을 다시 처리하는 비용과 최종 요청의 대기를 확인하기 위해 첫 부분 요청 1초는 유지하고 이후 갱신 간격 2초·4초를 비교했습니다.

같은 100개에서 갱신 4초는 최종 210구간 PCM·전사·연결 CER 11.12%를 유지했습니다. 첫 자막 p95는 9.34→5.49초, 최종 호출 큐 대기 p95는 5.96→3.92초로 줄었습니다. 실제 부분 호출은 132→113회였고 긴 접두 음성의 재전사가 줄었습니다.

따라서 첫 요청은 일찍 보내고 이후 갱신 빈도를 낮추는 구성을 선택했습니다. 부분 결과 사이의 갱신 간격은 길어지는 절충이 있었습니다. 이 결과는 호출 스케줄과 입력 길이에 따른 운영 관측이며 모델의 개별 연산이 빨라졌다는 판정은 아닙니다.

근거: [부분 갱신2초/4초 대조](../../results/summaries/optimization/realtime-schedule-20261111.md).

## 5. 생성 중 표시를 추가하고 접두부 재표시를 보류 — 11월 11일

완성 문자열의 반환까지 기다리는 표시를 앞당기기 위해 C++ bridge에서 생성 토큰을 Python으로 전달했습니다. 완결된 UTF-8 접두부부터 임시 가설로 발행하고 종료 result를 확정 결과로 사용했습니다. 같은 100개 끔/켬 대조에서 최종 전사·CER 11.12%를 유지하며 첫 표시 p95가 5.49→5.19초로 줄었습니다. 전체 추론 합계는 2.2% 늘고 최종 반환도 조금 늦어져, 표시 이득과 연산 비용을 함께 기록했습니다.

토큰 표시 후에는 이미 보인 부분 문장이 최종 호출의 첫 글자로 덮여 짧아지는 문제가 있었습니다. 같은 구간의 다른 호출이 기존 문장의 접두부를 다시 생성하는 동안에는 기존 문자열을 유지하고, 확장·실제 내용 변경·종료 result는 전달하도록 했습니다. 같은 로그에 적용한 분석에서 접두부 재표시 철회 99→0회였고 후속 RP5 100개에서도 0회를 확인했습니다. 실제 내용 변경에 따른 철회는 남았습니다.

이 단계에서 생성 중 표시와 접두부 재표시 보류를 개발 동작에 포함했습니다. 첫 표시는 텍스트 이벤트 발행 시각으로 측정했고 실제 GUI 시각과 구분했습니다. 부분 가설의 정답 정확도는 남은 검증이며 다음에는 음성 처리·prefill·decode의 연산 비용을 살폈습니다.

근거: [생성 중 토큰 전달](../../results/summaries/optimization/realtime-token-20261111.md), [표시 안정성](../../results/summaries/optimization/realtime-stability-20261111.md).

## 6. 단계별 스레드 특성을 확인하고 생성 2T·음성/prefill 3T 선택 — 11월 11~12일

처음에는 음성 처리·prefill·토큰 생성에 같은 스레드 수를 적용했습니다. 2T/3T/4T 선별 후 같은 100개 새 2T→3T 대조에서 최종 전사·CER를 유지하며 전체 추론 합계 8.3% 감소를 관측해 모두 3T를 선택했습니다. 다만 음성/prefill은 줄고 decode는 늘어, 연산 단계마다 적합한 스레드 수가 다를 수 있음을 확인했습니다.

이에 생성과 음성/prefill의 스레드 설정을 분리했습니다. 첫 6개 반복에서 생성 2T/음성 3T의 최종 처리 개선은 3.88%·2.82%로 반복 3% 선별 조건에 미달해 그 실행은 100개 없이 종료했습니다. 이후 별도 사전 조건의 새 100개 3/3→2/3 대조에서는 최종 210구간 PCM·전사·토큰 ID와 CER 11.12%가 같고, 최종 추론 합계가 514.45→495.50초로 3.68% 줄었습니다. 이 추가 근거로 2/3을 후속 개발 기준으로 선택했고 이전 선별 판정은 보존했습니다.

11월 12일에는 생성 2T를 고정하고 음성/prefill 3T·4T를 같은 6개 2/3→2/4→2/3으로 비교했습니다. 앞 control 대비 후보의 음성/prefill 합계는 4.65% 줄었지만 전체 추론 합계가 0.17% 늘어 사전 조건 하나를 통과하지 못했습니다. 100개로 확대하지 않고 2/3을 유지했습니다. 같은 2/3의 앞뒤 최종 합계도 4.44% 달랐으므로 4T의 효과가 없거나 통계적으로 악화됐다고 판정하지 않았습니다.

스레드 선택은 소표본 선별과 100개 검증의 범위를 구분하고, 열 제한·실행 순서에 따른 변동을 포함한 개발 판단으로 남겼습니다. 다음에는 스레드를 더 늘리기보다 남은 연산과 반복 입력의 비용을 분해했습니다.

근거: [모두2T/3T/4T 대조](../../results/summaries/optimization/realtime-threads-20261111.md), [분리6개 반복](../../results/summaries/optimization/realtime-split-20261111.md), [분리100개 추가 대조](../../results/summaries/optimization/realtime-split100-20261111.md), [음성/prefill 3T·4T 선별](../../results/summaries/optimization/realtime-prefill-20261112.md).

## 7. 남은 비용을 분해하고 캐시 재사용 범위를 한정 — 11월 12일

당시 2/3의 보존한 100개·329호출을 재집계했습니다. 전체 추론 합계 634.318초에서 음성 처리+prefill은 54.76%, 토큰 decode는 43.90%, KV 초기화는 0.37%였습니다. 초기화 자체보다 큰 연산 구간을 살펴볼 근거이며, 입력 경과 시간이나 자막 지연의 비율과는 다릅니다.

반복 처리된 PCM 좌표는 음성 길이로 122.264초였지만 같은 전체 PCM의 중복 호출은 0개였습니다. 이 음성 길이를 절감할 수 있는 연산 시간으로 환산하지 않았습니다. 고정 소스 검토에서는 음성이 늘 때 전처리 특징과 encoder embedding이 달라질 수 있어, PCM 접두부 일치만으로 기존 음성 KV를 재사용하는 방식은 보류했습니다.

작은 후보로 음성 앞의 동일 text prefix KV만 유지하는 방식을 선택했습니다. 분석 시점에는 미구현이었고, 이후 소스 커밋 `e9656cc`에서 선택 기능 `cache_text_prefix`와 단계별 계측을 추가했습니다. 음성·뒤 text·이전 생성 토큰은 다시 계산하고, 불일치·제거 실패·호출 실패 때는 전체 초기화로 복귀하도록 했습니다. 구현 직후 공유 개발 설정은 캐시를 켜지 않은 2/3을 유지했습니다.

이때 다음 작업은 같은 6개 연속 입력에서 캐시 끔/켬의 PCM·최종 전사·토큰 ID·완료율과 첫 표시·최종 반환·메모리를 비교하고, 실제 prefix 토큰 수와 처리 비용을 분리 계측하는 것이었습니다. 후속 실측과 개발 설정 변경은 아래 8절에 기록합니다.

근거: [반복 처리·KV 분석](../../results/summaries/optimization/realtime-cache-audit-20261112.md), [캐시 구현 구조](../reference/architecture.md), [선택 실험 실행 안내](../guides/qwen3_optimization.md#고정-text-prefix-kv-선택-실험), [사전 검증 조건](qwen_realtime.md#고정-text-prefix-kv-대조--2026-11-12-사전-조건).

## 8. 고정 9토큰 KV를 검증하고 개발 구성에 반영 — 11월 12일

RP5 실제 모델에서 콜드·웜 호출의 전사·토큰 ID가 같고, 의도적 callback 실패 뒤 캐시 초기화와 정상 복구가 이루어짐을 확인했습니다. 재사용 가능한 음성 앞 prefix는 9토큰이었습니다. 같은 6개 끔→켬→끔 비교가 선별 조건을 통과해, 같은 새 빌드로 새 끔→켬 비교를 100개 전체에 실행했습니다.

최종 210구간의 PCM·전사·토큰 ID·CER 11.12% 동일·실패/드롭/미출력 0을 유지하며 사전 21조건을 통과했습니다. 전체 추론 합계는 623.416→566.280초로 9.16% 줄었고, 첫 표시 p95는 4.410→4.128초·파일 끝 반환 p95는 3.378→2.819초였습니다. 워밍업 후의 335호출은 모두 9토큰을 재사용했습니다.

고정 prefix 평가 25.967→0초와 KV 처리 2.361→0.008초를 확인했지만 다른 단계 비용과 시작 온도·열 상태도 달라 전체 개선을 prefix 생략만의 효과로 해석하지 않았습니다. 부분 호출 119→125회·문자 철회 171→182자 증가도 함께 기록했습니다. 공유 개발 설정은 검증한 2/3·`cache_text_prefix=true`로 갱신했고 기존 빌드·끔 설정은 보존했습니다. 이는 개발 구성 채택이며 자연 대화·마이크·최종 장시간 운영 검증은 남아 있습니다.

근거: [고정 text prefix KV 100개 검증](../../results/summaries/optimization/realtime-prefix-cache-20261112.md), [현재 개발 설정](../../configs/gguf_realtime.toml).

## 9. 첫 후속 요청을 앞당겼지만 큐 부담 증가로 보류 — 11월 12일

청취 도구와 기존100개 로그에서,4자 표시가 늦은10개 모두 첫 부분 결과가1~3자였고5초 최종 호출까지 충분한 내용이 나오지 않는 것을 확인했습니다. 각 구간의 첫 요청 뒤2초 후 한 번 더 요청하는 선택 옵션을 만들고, 기존 고유6개에서 기존→후보→기존을 대조했습니다.

최종 PCM·전사·토큰 ID·CER은 같았지만 후보의 부분 추론은22.19초로 기존10.02~10.78초보다 늘었습니다.4자 표시 p95는5.37초로 양쪽 기존5.23/5.30초보다 늦고 최종 큐 대기도 늘어, 이번 후보는100개 없이 종료했습니다. 현재 첫1초/이후4초를 유지하고 다음에는 호출을 늘리기보다 첫 요청에 공급하는 음성 길이를 검토하기로 했습니다.6개 운영 관측으로 자연 대화나 순수 설정 인과 효과를 주장하지 않습니다.

## 10. 가변 요청으로 갱신을 늘렸지만 긴 대기는 남음 — 11월 12일

고정 간격 대신 작업자 유휴·새 음성량·직전 비용을 사용하는 선택 모드를 구현했습니다. 같은6개에서 최대 갱신 공백 p50은4.33~4.57초에서2.72초로 줄어 더 자주 내용이 늘어나는 신호가 있었습니다. 그러나 p95는7.63초로 늘고 전체 추론도52.87초로 증가해 고정4초를 유지했습니다. 최종 전사·CER·완료율은 같았고100개는 실행하지 않았습니다.

## 14. Q4 prefill 병목을 커널까지 확인 — 11월 13일

기존 엔진을 바꾸지 않는 선택 함수 추적으로 실제 ARM Q4_K/Q6_K 커널과 Q8 대비 동일 연산량을 확인했습니다. 현재 열 제한 없는 추가 진단에서도 긴 prefill은 Q8 약412ms·Q4 약546ms였고, 입력 변환과 GEMM 모두 CPU 비용이 컸습니다. 변환은3.5~3.7배였지만 추적된 추가 CPU의 대부분은 행렬곱이어서 변환만의 최적화로 충분하다고 가정하지 않습니다. 다음은3T 커널 내부 검토이며 최적화 채택·새 CER 결과와 구분합니다.
