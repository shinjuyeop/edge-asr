# Qwen3-ASR 기반 ARM64 Edge 추론 최적화

**Low-Latency Korean ASR on Raspberry Pi 5**

목표는 Qwen3-ASR-0.6B의 한국어 정확도와 처리 완료율을 유지하면서 RP5 CPU에서 실제 음성 인식 지연을 줄이는 것입니다. 추론 시간, 메모리, 발열, 장시간 안정성을 함께 판단합니다. 기존 모델 비교 결과는 출발 자료이며 새 최적화 기준선은 OPT-0에서 고정합니다.

## 단계와 완료 조건

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| OPT-0 기준선·오류 | 기존 ONNX 단독 경로, 56ms 잔여 구간 실패 재현, 반복 기준선 | 데이터/모델/런타임/설정 해시, 실패 원시, 로딩·첫 추론·steady-state 분리, 반복 수·열 조건·정확도 판정 기준 고정 |
| OPT-1 병목 | 전처리, Audio Encoder, LLM Prefill, Token Decode 계측 | 가능한 구간별 측정·계측 오버헤드 확인; 분리 불가능한 구간은 합산과 한계를 명시 |
| OPT-2 엔진·양자화 | 기존 sherpa-onnx INT8과 별도 llama.cpp GGUF Q8_0 비교, 이후 Q4/스레드/affinity/cache 검토 | 같은 입력·출력 정책에서 정확도·실패·속도·메모리·열 보고, 효과 있는 구성만 유지 |
| OPT-3 연속 음성 | Qwen 단독 VAD·청크·중간 결과·종료 판단·큐 처리 | 말하는 중 첫/부분 결과, 고정 음향 기준 지연, 수정/확정·손실·백로그 검증 |
| OPT-4 실보드 최종 | 새 한국어 holdout·장시간 연속 입력 | 정확도·실패·드롭·지연·RSS 추세·열 제한을 포함한 최종 구성 판정 |

처음부터 추상 엔진 계층이나 복잡한 서비스 구조를 만들지 않습니다. 현재 첫 추론·워밍업·회전 반복·고정 PCM 재현은 `qwen/benchmark.py`로 통합합니다. [첫 OPT-0 결과](../../results/summaries/optimization/opt0-pilot-20261109.md)를 확보했고 [OPT-1 호출 경계 실측](../../results/summaries/optimization/opt1-profile-20261109.md)으로 Python·ORT Run 범위를 분리했습니다. [OPT-2 프로토콜](opt2_gguf.md)에 GGUF 경로·고정 자산·비교 판정 기준을 정했습니다. 실제 사용자 TTFT·operator별·단독 KV 비용은 후속 계측입니다.

## OPT-0에서 고정할 계약

- KSS 개발 50개는 튜닝·회귀용입니다. 이미 검토한 FLEURS 30개도 오류 분석용으로 분류하고 최종 독립 평가에는 새 holdout을 정합니다.
- 공통 `ko_cer_v1`, corpus CER, 발화별 변화, 성공/실패·정답 문자 커버리지를 함께 보고합니다. 실패를 제외한 CER만으로 개선을 선언하지 않습니다. 허용 CER 변화와 실패 기준은 실험 결과를 보기 전에 수치로 확정합니다.
- 56ms 오류는 입력 길이만의 문제로 단정하지 않습니다. 원 발화, 구간 PCM, 이전 문맥, 토큰 예산, native 경고를 보존하며 하나씩 바꿔 재현합니다.
- 모델 로딩, 첫 추론, 별도 워밍업 후 반복 추론을 구분합니다. 반복 수·실행 순서·시작 온도·냉각·CPU 설정·런타임과 모든 자산 해시를 기록합니다.
- 초기 주 비교는 Qwen 단독입니다. 이전 Zip 동시 실행의 CPU/RSS/반환 지연을 단독 성능으로 옮기지 않습니다. 원본 비양자화 모델은 필요할 때 정확도 참조로 별도 실행하며 기존 INT8을 원본 가중치라고 부르지 않습니다.

## 평가 규모와 실행 주기 — 2026-11-09 합의

실행 시간을 고려해 **개발 검사와 후보 비교 모두 우선 고유 발화 100개의 고정 목록**으로 진행합니다. 약1,000개 확장과 KsponSpeech 전체 평가는 선택 후속 작업으로 두며 현재의 필수 준비·실행 범위에 포함하지 않습니다. [고정100개 준비](fixed100.md)를 완료했으며 Zeroth60·FLEURS40, 총891.1448125초입니다. Host 준비·RP5 전송 검증과 ASR 실측은 구분하고 기존 KSS50 결과는 그대로 보존합니다.

| 구분 | 준비 목표 | 실행 시점 |
| --- | --- | --- |
| 기본 검사·후보 비교 | 100개, 총 음성 길이 10~15분을 목표로 길이·화자·발화 조건을 고려해 선정 | 개발 중에는 변경한 구성부터 검사, 후보 비교에는 같은100개 전체 사용 |
| 선택 확대 | FLEURS 한국어 test382 + Zeroth test457 + KsponSpeech 자유발화200~300개를 합친 약1,000개 구성은 후속 검토안으로 보존 | 조건 커버리지·오류율 차이의 불확실성을 보고 필요할 때 범위를 다시 고정 |
| 선택 대규모 검사 | KsponSpeech eval-clean/other 전체6,000개 | 필요할 때 검토. 현재 최적화 진행의 필수 조건은 아님 |

목록은 모델 출력을 보기 전에 선정 규칙·seed·리비전·입력/정답 해시와 함께 고정합니다. 같은 음원을 반복해100개로 세지 않습니다. 접근 가능한 자료에서 여러 화자·짧은/중간/긴 발화·낭독/자유발화를 고려하고 확보하지 못한 조건이나 화자/세션 정보는 미확인으로 표시합니다. 이후 새 독립 평가를 추가할 때는 기본100개와의 문장·음원 중복 및 화자/세션 분리 가능 여부를 확인합니다. 이미 사용한 FLEURS test100개와 validation30개는 개발/회귀·오류 분석 자료이며 외부 배포처의 test 표기만으로 새 holdout이나 Qwen 사전학습과의 독립성을 주장하지 않습니다.

기본100개는 반복 최적화의 작은 회귀 평가입니다. CER·실패·발화별 개선/악화와 입력 조건을 함께 보고하고, 이 목록의 결과를 한국어 전반의 정확도나 최종 독립 평가 성능으로 일반화하지 않습니다.

발화 수와 총 음성 길이를 함께 관리합니다. 100개를 충족하려고 긴 음성을 잘라 버리거나 결과를 본 뒤 쉬운 발화로 바꾸지 않습니다. 개발 목록에도 긴 입력을 포함하고, 10~15분 길이 목표와 조건 커버리지를 동시에 맞추기 어려우면 목록 고정 전에 이유를 기록하고 목표를 조정합니다. 기존 KSS6/50개·56ms 진단과 원시 결과는 보존합니다.

개발 중에는 변경한 구성으로 정확도·실패를 먼저 검사합니다. 정식 속도 비교에서는 비교 구성 모두를 같은 장비·프로토콜로 다시 측정하고 과거 RTF를 새 실행의 실측값으로 옮기지 않습니다. 전체 소요 시간은 새 목록의 실제 음성 길이와 별도 파일럿 실측으로 산정합니다. 준비 전의 일정 산술 예시는 성능 측정값으로 기록하지 않습니다.

데이터 원본의 접근·이용 조건, 전사 변환 정책과 `ko_cer_v1` 적용, 실패 보존, 데이터셋별·길이별 집계를 확정한 뒤 새 목록을 준비합니다. 마이크가 없는 동안에는 공개 파일의 연속 입력·실시간 지연 검증을 별도로 진행합니다.

현재 고정100개는 낭독 자료이며 자유발화·잡음·4.2초 미만·30초 이상 입력은 포함하지 않았습니다. Zeroth의 식별 가능한 화자는10명이고 FLEURS 화자 수는 미확인입니다. 기존 KSS 짧은 입력과56ms 진단은 별도로 보존합니다. 새100개의 첫 ASR 결과는 [기준선 보고서](../../results/summaries/optimization/fixed100-baseline-20261109.md)에 분리했습니다. ONNX는99/100 성공으로 전체100개 정확도 기준선이 미완료이고 GGUF의 새 전체 실행을 이후 자체2T 비교 기준으로 사용합니다. TTFT는 여전히 null입니다.

## 지연과 정확도 해석

Batch RTF는 준비된 전체 음성의 처리 비용입니다. 실시간 발화 중 자막 지연을 대신하지 않습니다. 새 부분 출력 경로에서는 요청 수락→첫 출력 토큰(엔진 TTFT), 첫 오디오→첫 비어 있지 않은 자막, 고정된 정답 음향 끝→최초/안정된 전사, 발화 끝→최종 반환을 따로 기록합니다. 텍스트 결과를 한꺼번에 주는 현재 API에서는 TTFT를 추정하지 않고 미계측으로 둡니다.

기존 보정 반환 지연은 VAD 소유 구간 끝 기준입니다. 구간 길이나 종료 판단을 바꾸면 기준점도 움직이므로 비교 가능한 고정 오디오 앵커가 필요합니다. 구현이 발화 종료 후 완성 결과만 반환하는 동안에는 발화 중 부분 자막이 구현됐다고 표시하지 않습니다.

현재 한 번의 디코딩 안에서 사용하는 KV cache와 청크 사이 encoder/prefill 재사용은 다른 변경입니다. 먼저 기존 동작과 병목을 확인합니다. ONNX INT8과 GGUF Q8_0은 양자화 방식도 다르므로 첫 비교는 엔진+모델 자산 구성 비교이며 순수 엔진 효과로 단정하지 않습니다.

## 잠정 목표

| 지표 | 1차 목표 | 도전 목표 |
| --- | --- | --- |
| Batch RTF | ≤0.5 | ≤0.3 |
| 구간 종료→완성 반환 p95 | ≤2초 | ≤1초 |
| 한국어 정확도 | 사전 고정한 CER·실패 허용 기준 통과 | 새 독립 평가에서 검증 |
| 연속 운영 | 입력/처리 드롭 0, 백로그 추세 확인 | 열 제한 없이 안정적 |
| 메모리 | RSS·프로세스별 증가 원인 분리 | 필요한 범위에서 감소·증가 억제 |

수치는 달성 보장이 아니며 OPT-0/1 근거로 조정할 수 있습니다. 목표를 바꾸면 이유와 시점을 기록합니다. 최소 30분 통과만으로 상시 운영 안정성을 주장하지 않습니다.

## 보존과 경로

설정은 `configs/onnx.toml`·`configs/gguf.toml`, Qwen 실행은 `src/edge_asr/qwen/`, C++/빌드는 `native/`, 연구 메모는 `docs/research/`에 둡니다. 새 결과는 `results/optimization/<단계>/<실행ID>/`, 검토 요약은 `results/summaries/optimization/`입니다. 모델은 `models/qwen3-opt/<자산ID>/`, 외부 엔진 소스·빌드는 `runtimes/qwen3-opt/<엔진ID>/`, 새 Python 환경은 `.venv-qwen3-opt-<실행ID>`를 사용할 수 있습니다. 기존 자산은 경로 그대로 읽어 재사용해도 됩니다.
