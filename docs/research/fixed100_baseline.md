# 고정100개 ONNX 출발 기준선·GGUF 비교

2026-11-09, 실제100개 ASR 결과를 보기 전에 고정합니다. 실행 ID는 `fixed100-baseline-20261109-01`입니다. [고정100개 준비](fixed100.md)와 이전 KSS50·OPT-0/1/2 결과를 보존합니다.

## 기준선의 의미와 구성

**출발 기준은 기존 sherpa-onnx INT8 ONNX 2스레드입니다.** 원본 FP16 모델을 뜻하지 않으며 frontend FP32·encoder INT8·decoder UINT8 혼합 배포본과 기존 디코딩 정책을 그대로 사용합니다. 이번에 추론 알고리즘·가중치·스레드 최적화를 적용하지 않습니다.

GGUF Q8_0 2스레드도 같은100개로 측정합니다. 이후 GGUF의 최적화 효과는 **이번 GGUF 2T 값**과 비교하고 ONNX는 출발 참조로 유지합니다. 엔진·가중치 양자화·프런트엔드가 함께 다른 구성 비교이며 순수 엔진 효과로 단정하지 않습니다.

| 항목 | 고정 조건 |
| --- | --- |
| 장비/범위 | RP5 ARM64 CPU, Qwen 단독 batch. Zip·VAD·Refine·화면 출력 없음 |
| ONNX | `configs/optimization/fixed100_onnx_2t.toml`, 기존 별도 ONNX 환경·모델·출력 정책 |
| GGUF | `configs/optimization/fixed100_gguf_q8_2t.toml`, 기존 llama.cpp/libmtmd·text/mmproj Q8_0·별도 C ABI |
| 공통 | 한국어·2T·context512·출력 최대128, 16kHz mono PCM16 → 공통 float PCM |
| GGUF 기본값 | prefill2T, batch/ubatch512, KV K/V f16, flash attention auto, KleidiAI OFF |
| 상태 | 모델은 프로세스당1회 로드, 각 파일은 새 인식/KV 상태. 청크 간 재사용 없음 |
| 호출 | 같은 첫 파일의 첫 추론1회 → 추가 워밍업3회 → 고정100개 각1회 |
| 측정 도구 | 공통 `tools benchmark-qwen3 --repetitions 1` 실행기, 새 출력 경로 |

두 새 설정은 기존2T 설정과 model/audio/워밍업/정규화 값이 같습니다. 출력 경로만 새 OPT 실험으로 구분합니다. 런타임·모델·config·소스·입력 해시를 기록하고 기존 Python 환경이나 하드웨어 설정을 변경하지 않습니다.

## 계측과 판정

- 로딩·첫 추론·워밍업·scored100개를 분리합니다. 자산 해시를 미리 읽으므로 cold-storage 로딩 실험이 아닙니다. RTF는 준비한 PCM에서 어댑터 최종 전사 반환까지이며 WAV I/O·변환·모델 로딩·워밍업·결과 기록은 제외합니다.
- 공통 `ko_cer_v1`의 corpus CER, 자료별·길이별 오류, 발화별 개선/동률/악화, 성공/실패/중단/미실행, 정답 문자 커버리지, 빈 정규화 출력·native 경고를 함께 보고합니다. 원문·토큰·실패 경고·경과 시간은 원시에 남깁니다.
- **성공100/100·문자 커버리지100%·빈 정규화 출력0개**를 정확도 완료 조건으로 둡니다. 현재 공통 CER/RTF는 성공 파일만 집계하므로 실패가 있으면 전체100개의 주 성능값으로 채택하지 않습니다. 실패/중단/미실행을 빈 가설로 처리한 보조 CER는 전체정답3,848자를 분모로 별도 표기하며 미실행이 있으면 완료 평가로 해석하지 않습니다.
- 모든100개가 시도되어 성공/실패 호출의 elapsed가 유한하게 기록된 경우에만 실패 비용을 포함한 전체 시도 RTF도 별도 계산합니다. 중단·미실행·반환하지 않은 호출의 시간을0이나 추정값으로 채우지 않습니다. 같은 성공 부분집합 비교는 ID와 분모를 따로 밝힙니다.
- 이후 최적화의 우선 채택 조건은 같은 엔진의 이번2T 기준선 대비 **추가 편집 오류0개·실패0개·빈 출력0개를 유지하면서 RTF 감소**입니다. RSS·열/클럭과 발화별 악화도 함께 검토합니다. 첫 단회 비교로 작은 속도 차이의 통계적 우월성을 주장하지 않고 유망하거나 불확실한 변경만 추가 반복합니다.
- 처리시간/RTF의 p50·p95는 길이가 다른 파일100개의 분포입니다. 발화 끝→자막 지연이나 사용자 TTFT가 아닙니다. GGUF 내부 첫 토큰 선택 시각도 외부 callback·자막 TTFT와 구분합니다. 실제 부분 자막·백로그·드롭·장시간 안정성은 이번 batch에서 null입니다.
- PID CPU·100ms RSS, 온도·fan·sysfs 클럭·실제 ARM 클럭·현재 제한과 과거 이력을 기록합니다. 표본 사이 피크나 고정 클럭은 보증하지 않고 결측은 null입니다.

## 온도·외부 제한과 실행 순서

먼저 `controlled-onnx-01 → controlled-gguf-01` 순서로 시도합니다. `warn75-stop80`, 시작53°C 이하·현재 제한없음3회, admission 대기최대300초, 75°C 경고·80°C/현재 제한/새 제한 이력/필수 센서 결측 중단을 사용합니다. 권장 목표는 추론 중75°C 이하입니다. 새 실행기에서 이 정책의 명시적1800초 상한과 실제 ARM 클럭 기록을 지원하며 기존 legacy 기본600초·75°C 정책은 유지합니다.

두 구성이 온도 조건을 만족하며100개를 완료하고, 실제 클럭 기록이 충분하고 시작 온도 차이가2°C 이내일 때만 온도 조건을 맞춘 구성 간 속도 비교로 분류합니다. 75°C 경고 여부·최고 온도는 별도로 표시합니다. 조건을 만족해도 엔진+양자화+프런트엔드 구성 비교이며 열평형/순수 엔진 인과 실험은 아닙니다.

현재 냉각으로 admission/열·감속 조건을 지키지 못하면 해당 시도와 중단/미실행을 그대로 보존하고 통제 비교 캠페인을 종료합니다. 앞서 사용자가 온도와 무관한 진행을 허용했고 이번 검토에서도 통제/운영 측정을 구분하기로 했으므로, **별도 `operational-onnx-01 → operational-gguf-01`**에서 `operational --skip-temperature-admission`으로100개 완주를 시도합니다. 이는 시작 온도·감속을 관찰하는 운영 기준선이며 통제된 속도 기준으로 채택하지 않습니다. 온도 조건만으로 실패한 원 실행을 성공으로 바꾸거나 결과를 섞지 않습니다.

두 모드 모두 작업별 외부1800초·주소 공간4GiB·core dump0과 기본 펌웨어 보호를 적용합니다. 저전압·필수 센서 결측·비온도 오류는 온도 fallback 사유로 삼지 않습니다. 모델 자체 실패만으로 같은100개를 다른 모드에서 재실행하지 않고 실제 실패를 보고합니다. 각 작업은 순차·독립 프로세스이며 SSH 단절에도 기록이 남도록 별도 driver에서 실행합니다. 초기 모델 실패와 열 중단을 구분합니다. 정책 변경은 새로운 실행 ID와 사전 문서 개정으로만 적용합니다.

Host 개발·모의 검사 → main commit/push → RP5 pull·입력 해시 대조 → 실제 추론 순서로 진행합니다. Host에서 모델 추론을 하지 않습니다. Host 회수 후 모든 새 원시 해시·공통 재채점/분석을 RP5와 대조하고 기존 자산 보존을 확인한 뒤 한국어 보고서에 초기값을 기록합니다.

## 재부팅 뒤 인프라 중단 재시도 — 2026-11-09

첫 운영 GGUF 실행 중 SSH·ping/LAN 주소 응답이 끊겼고 사용자가 재부팅했습니다. 부팅 ID가 바뀌었으며 최초 driver/worker의 완료 영수증은 없습니다. 마지막 유효 로컬 thermal 기록은17:51:34 KST로, 연결 장애 동안에도 내부 기록이 계속됐습니다. 이전 부팅의 영구 journal/pstore가 없어 네트워크/OS/전원 원인은 미확정입니다. 열 제한 관측을 연결 장애 원인으로 단정하지 않습니다.

원래 실행 ID와 모든 원시 바이트(마지막 NUL/미완성 줄 포함), 오래된 `running` 상태를 그대로 보존하고 별도 reconciliation 영수증에서 인프라 중단을 표시합니다. 미완성 마지막 JSONL 줄은 위치·바이트 수·해시를 기록한 뒤 분석에서 제외하며 원본을 수선하지 않습니다. 이미 원자적으로 저장된 predictions의 성공/중단/미실행을 그대로 집계하되 완료100개 기준으로 채택하지 않습니다. measurements와 predictions의 지속화된 호출 수가 다르면 그 차이도 기록합니다. fan의 `4294967295` 같은 비현실적인 카운터는 RPM 최대값으로 채택하지 않고 원시 값·유효성 문제를 별도로 보고합니다.

새 실행 ID `fixed100-baseline-recovery-20261109-01`에서 **GGUF만100개 전체를 처음부터1회** 재시도합니다. 첫 실행의 일부 결과를 이어 붙이지 않습니다. ONNX 완료 시도는 반복하지 않습니다. 동일 입력·순서·첫 추론/워밍업 파일·모델·어댑터·2T/context512/출력128·운영 정책·1800초/4GiB 조건을 유지합니다. 이번 문서 수정의 commit 전후 추론 코드·설정이 같은지 확인합니다. 새 부팅의 시작 온도·제한 이력을 별도 기록하므로 냉각 상태를 맞춘 속도 비교로 해석하지 않습니다.

OS 설정을 변경하지 않고 현재 커널 로그를 SSH로 Host에도 저장합니다. SSH 단절 시 이 수집도 끊길 수 있고 panic/네트워크 원인 포착을 보장하지 않습니다. 새 실행까지 인프라 중단으로 완료되지 않으면 반복을 자동 확대하지 않고 미완료와 원시를 보고합니다. 완료 시 첫 ONNX와 재시도 GGUF를 각각의 실행 ID·부팅 조건과 함께 보고하고, 공통 재채점·해시·모의 테스트·자산 보존을 다시 대조합니다.
