# M3-0: 음량·냉각·VAD/구간 사전 검증

**상태: 부분 완료.** 공통 음량 개발 평가와 단독 1T 냉각 검사는 수행했다. 추가 Zipformer 2T 부하는 사전 75°C 허용 조건을 넘어서 중단했고, VAD 실제 검출·endpoint·Hybrid 동시 실행은 아직 검증하지 않았다. 기존 설정을 실서비스 설정으로 변경하지 않았다.

원시 실행 ID: `results/preflight/m3-0-20261029-01`. 기계 판독용 [요약 JSON](m3-0-preflight-20261029.json), [실행·선택 정책과 M3-1 설계](../../docs/m3_preflight.md)를 함께 참고한다. 기준 main은 `d7bb3bd`; 초기 부하 코드는 `e63881a`, 음량/전처리 계측은 `6da200d`, 추가 부하/VAD 도구는 `a1feed1`이다. 기존 어댑터·평가기·scorer·정규화·설정 9개 파일은 기준 커밋과 바이트 일치를 확인했다.

## 1. M2-3 원시 기록 재분석

FLEURS 100개 저장 가설을 다시 채점했고 WAV 해시를 확인했다. 과거 측정값이나 입력을 수정하지 않았다. 아래 RMS/길이별 집계는 **사후 탐색 통계**이며 새로운 독립 평가가 아니다.

| M2-3 FLEURS 구간 | 발화 수 | Zipformer CER | SenseVoice CER |
| --- | ---: | ---: | ---: |
| RMS < -45 dBFS | 48 | 98.09% | 8.89% |
| RMS ≥ -45 dBFS | 52 | 22.80% | 8.41% |
| 길이 ≤ 8초 | 8 | 19.53% | 8.59% |
| 8초 < 길이 ≤ 15초 | 76 | 53.46% | 7.75% |
| 길이 > 15초 | 16 | 79.24% | 11.36% |

Zipformer의 전체 2,543개 문자 오류 중 삭제가 2,306개였다. 저음량 48개 중 45개는 빈 전사이며 이 구간 삭제는 1,997개다. 8~15초 길이 안에서도 저음량 CER 98.79%, 그 외 20.50%다. 다만 긴 자료에 저음량 자료가 많고 화자·문장·숫자·도메인도 달라 **길이 또는 음량 하나로 FLEURS 오류 전체를 설명할 수 없다**. 음량에 대한 특징 추출/학습 분포 민감성, 낭독 도메인·고유명사 차이 등이 원인 후보다. M3 KSS 개입 실험은 음량 영향을 지지하지만 FLEURS 개선을 직접 검증한 결과는 아니다.

M2 KSS 스레드 비교의 Zipformer CPU는 1T 약 100%, 2T 약 325%, 4T 약 397%였다. 2T에서 CPU를 사용한 TID가 4개 관측됐으므로 `num_threads`가 프로세스 전체 스레드 상한은 아니다. 세션별 스레드 풀·spinning은 후보이며 정확한 원인은 미확정이다. M2 4T 부하 중 최고 85°C 이상과 새 제한 이력이 있었지만, 당시 제한 비트는 주로 실행 경계에서 읽었으므로 개별 추론의 제한 발생 시점을 소급 확정할 수 없다.

SenseVoice는 M2 순수 무음 6개 중 0.5/1/3/10초 4개에서 비어 있지 않은 전사를 냈다. 이를 일반 오탐률로 해석하지 않는다. 합성 장문 32.07/60.61/120.59초에서 처리 시간은 2.519/7.277/22.280초, 관측 RSS는 약 626/767/1,214 MiB였다. 긴 입력에서 비용이 증가했으며, 해당 4T batch 수치를 실제 Refine 확정 지연으로 사용하지 않는다. 과거 오출력은 보존했고 금칙어 필터를 추가하지 않았다.

## 2. 공통 음량 정책 실측

KSS 원본 50개 × 원음/24dB 감쇠/24dB 감쇠+Gaussian 잡음(-55dBFS) × 정책 3개를 별도 PCM16 WAV 450개로 만들었다. 모든 후보의 참조 전사·프레임 길이는 동일하다. 두 모델 각각 1T, 워밍업 3회, `ko_cer_v1`, SenseVoice 한국어·ITN 꺼짐이다. 6회 독립 프로세스에서 **900/900 평가 성공, 워밍업 18회 성공**, Host 재채점 6개 모두 일치했다. 독립 원본 발화는 50개이며 단일 여성 화자의 개발 자료다. 아래 값은 조건별 50개를 각 1회 실행한 집계다.

| 입력 조건 | 정책 | Zipformer CER | batch RTF | SenseVoice CER | batch RTF |
| --- | --- | ---: | ---: | ---: | ---: |
| 원음 | 그대로 | 11.64% | 0.1358 | 5.16% | 0.0980 |
| 원음 | 고정 +12dB | 14.68% | 0.1362 | 6.08% | 0.0985 |
| 원음 | RMS 후보 | 12.17% | 0.1363 | 5.56% | 0.0986 |
| -24dB | 그대로 | 77.12% | 0.1351 | 4.37% | 0.0978 |
| -24dB | 고정 +12dB | 13.10% | 0.1361 | 4.10% | 0.0983 |
| -24dB | RMS 후보 | 15.08% | 0.1363 | 4.23% | 0.0985 |
| -24dB + 잡음 | 그대로 | 81.48% | 0.1351 | 8.33% | 0.0978 |
| -24dB + 잡음 | 고정 +12dB | 35.85% | 0.1360 | 7.80% | 0.0983 |
| -24dB + 잡음 | RMS 후보 | 33.20% | 0.1362 | 7.67% | 0.0985 |

추론 구간 평균 CPU는 두 모델 모두 약 100.1%였다. Zipformer 관측 RSS는 정책 순서대로 254.3/251.7/254.6 MiB, SenseVoice는 554.9/557.6/556.4 MiB였다. 로딩 RSS와 추론 RSS는 원시 manifest에서 별도 보존한다. 입력 전처리 비용은 위 RTF에 포함되지 않으며, 과거 2T/4T 값과 속도 향상률로 비교하지 않는다.

**사전 고정 규칙의 공통 개발 후보는 `rms26`이다.** 새 clipping 0, 각 모델 원음 CER 악화 1%p 이하를 만족하는 후보 중 두 모델 × 세 조건 평균 CER이 가장 낮았다. 평균 CER은 원형 31.35%, 고정 Gain 13.60%, RMS 12.99%였다. 고정 Gain은 원음 2,638,704개 샘플 중 100,309개(약 3.80%) clipping과 Zipformer 원음 CER +3.04%p로 탈락했다. RMS도 원음에서 Zipformer +0.53%p, SenseVoice +0.40%p 악화가 있으므로 무조건적인 개선은 아니다. 이 임계값은 결과 전에 정했고 모델별로 정책을 따로 선택하지 않았다.

RMS 후보는 현재/과거 100ms 블록만 사용하며 목표 -26dBFS, 최대 +24dB, peak 0.98 제한이다. 목표보다 작은 블록을 증폭하고 큰 블록은 원래 RMS를 유지하면서 peak만 제한한다. 발화마다 상태를 초기화하는 **파일 실험**이므로 연속 스트림의 gain 상태·청감 품질은 별도 검증해야 한다. RMS는 새 clipping이 없었으나 합성 잡음만 입력한 Host 산술 검사에서 -55dBFS가 약 -31.59dBFS로 올라갔다. 실제 환경 잡음/무음 오탐에 안전하다는 근거가 아니다. SNR을 개선하는 잡음 제거 기능도 아니다.

RP5에서 동일 PCM을 재생성한 450개 전처리 호출은 모두 Host 파생 PCM과 일치했다. 전처리 계산 RTF는 원형 경로 0.02441, 고정 Gain 0.02452, RMS 0.02448, CPU 약 100%다. 파일 읽기·100ms 입력 수집·ASR을 제외한 Python 연산이며 원형 경로도 검사와 PCM 변환을 수행한 비용이다. 이 시간을 batch RTF에 더해 실제 Streaming 지연이라고 보고하지 않는다. 새 PCM은 원본 WAV와 별도 경로에 보존했다.

기존에 결과를 본 FLEURS 100개는 이번에 새 ASR 평가를 실행하지 않았다. 정책을 확정한 뒤 문장 ID가 겹치지 않는 미사용 자료·다화자·실제 저음량/잡음 녹음으로 최종 평가해야 한다.

## 3. 냉각 및 제한 관측

시작 조건은 53°C 이하와 현재 제한 비트 0의 연속 3표본, 실행 중 중단선은 75°C·현재 제한·새 이력·필수 계측 누락이다. 1초 간격으로 온도·CPU0 sysfs 클럭·팬 RPM·현재/이력 비트를 기록했다. 고정 governor/클럭·CPU affinity·주변 온도·다른 서비스 부하는 통제하지 않았으므로 완전히 동일한 열 조건이라고 주장하지 않는다.

| 초기 연속 부하 | 실제 시간 | 완료 호출 | 최고 온도 | 평균 추론 CPU | RSS | 마지막/첫 전체 KSS 반복 시간 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Zipformer 1T | 180.46초 | 400 | 67.20°C | 100.15% | 265.84 MiB | 0.9997배 |
| SenseVoice 1T | 180.18초 | 556 | 68.85°C | 100.13% | 567.22 MiB | 0.9981배 |

각각 완전한 KSS 50개 반복이 8회/11회 있었고, 관측한 범위에서 초반 대비 후반 처리 저하가 드러나지 않았다. 이 부하 도구는 50개 WAV를 미리 메모리에 읽으므로 RSS를 한 파일씩 읽는 공통 평가기의 모델 메모리와 동일시하지 않는다. 두 프로세스 모두 동시 관측 TID 최대 5개, CPU를 주로 사용한 TID는 하나였다. 센서 표본에서 현재 제한 비트는 모두 0, 과거 이력은 `0xe0000` 그대로였다. 이력 자체를 이번 throttling 발생으로 기록하지 않았다.

음량 6개 실행의 시작 온도는 51.80~52.90°C, 실행 최고는 67.75~69.95°C였고 모두 통제 조건을 통과했다. CPU0 sysfs 값은 로딩/경계를 포함해 1.5~2.4GHz 범위였으며, 이것만으로 주파수 제한을 판단하지 않았다. 팬 회전 센서는 읽혔으나 팬 종류·히트싱크 접촉·케이스 통풍·실내 온도는 물리적으로 확인하지 않았다. 1Hz 사이의 짧은 제한은 기존 이력 비트가 이미 켜져 있으면 놓칠 수 있다.

추가 **SenseVoice 1T 480.18초**는 1,488호출·완전한 50개 반복 29회로 통과했다. 평균 추론 CPU 100.12%, RSS 568.58 MiB, 마지막/첫 반복 시간 0.9982배로 후반 처리 저하가 관측되지 않았다. 다만 최고 **73.80°C**, 마지막 1분 평균 72.57°C까지 올라 3분 검사보다 열 여유가 작았다. 팬 센서는 3,097~10,200 RPM이었고 현재 제한은 0이었다. 8분 기록을 무기한 안정성이나 고정 열평형의 보장으로 해석하지 않는다.

이어 기존 **Zipformer 2T**는 52.90°C에서 시작해 **14.09초 후 76.00°C**가 관측되어 종료했다. 종료 직후 표본은 77.10°C였다. 480초 계획 중 완료 호출은 30개이며 `control_rejected`, `temperature_limit`, exit -15로 보존했다. 중단 전 완료 호출의 CPU는 약 329.15%, CPU를 주로 사용한 TID는 4개였다. 이는 실패 실행의 진단이며 성공한 RTF 비교에 넣지 않는다. 강제 종료 전에 추론 RSS 집계가 저장되지 않아 해당 값은 null이다.

**현재 throttling 비트는 이 실패 실행에서도 0이었다.** 이번 실패는 사전 설정한 보수적 냉각 조건 초과이며, 새 하드웨어 throttling 발생으로 기록하지 않았다. 이후 추가 부하/통제 비교를 중단했다. 기존 1T 비교가 허용 범위 안에서 완료됐다는 사실은 유지하되, 높은 부하와 동시 실행의 냉각 합격을 주장하지 않는다. 팬 전원·설치 방향/풍량·히트싱크 접촉·케이스 통풍·주변 온도 확인과 동일 절차 재검증이 필요하다. 팬 곡선이나 OS 설정을 임의로 바꾸지 않았다.

## 4. VAD·최대 구간 후보

새 VAD 가중치 추가는 ‘모델 추가 제외’ 범위를 확인하는 질문에 대한 답을 기다리고 있어 다운로드하지 않았다. 설치된 sherpa-onnx 2.0.1의 VAD API는 확인했고, 도구는 로컬 Silero 파일만 받도록 구현했다. **실제 ARM64 VAD 로딩, 짧은 발화 누락, 무음/잡음 검출, 종료 판정 지연은 미측정(null)**이다. Host mock 검사 결과를 실제 성능으로 사용하지 않는다. 근거: [sherpa Silero VAD 안내](https://k2-fsa.github.io/sherpa/onnx/vad/silero-vad.html), [Silero 공식 저장소/MIT](https://github.com/snakers4/silero-vad).

| 최대 구간 후보 | KSS 원본 WAV 중 더 긴 파일 | 단순 고정 분할의 내부 경계 수 | 검증할 절충 |
| --- | ---: | ---: | --- |
| 3초 | 34/50 | 34 | 짧은 처리 단위와 잦은 문장/단어 절단 |
| 5초 | 4/50 | 4 | 우선 실험할 중간 후보 |
| 8초 | 0/50 | 0 | 개발 낭독의 경계 감소와 긴 Refine 처리 단위 |

이 표는 WAV 길이 산술이며 실제 VAD의 강제 분할 횟수가 아니다. **5초를 첫 실측 후보로 권장**하되 3/8초도 같은 자료로 평가한다. 초기 후보 설정은 16kHz/512프레임, 1T, threshold 0.5, 최소 음성 100ms, 종료 무음 300ms다. 짧은 발화는 종료 무음으로 닫고 계속되는 음성만 최대 길이에서 나누는 설계다. 현재 수치가 짧은 한국어 응답에 적합한지는 미검증이다.

구간 소유 범위 `[start,end)`와 200ms 왼쪽 문맥을 분리한다. 원시 VAD 경계와 겹침 제거량을 모두 남기며 문맥 중복을 텍스트로 단순 연결하지 않는다. 실제 단어 잘림·중복은 정답 정렬 후 확인한다. KSS에 음소 종료 정렬이 없으므로 도구가 기록할 수 있는 값은 원본 WAV 끝 기준 대리 endpoint다. 빠른 파일 입력의 오디오 시간축과 실제 1배속 wall 지연을 별도 필드로 두고, flush에서만 확정되면 정상 endpoint 지연으로 채우지 않는다.

## 5. 권장 구조와 M3-1 구현 순서

현재 근거는 **Streaming을 지속하면서 VAD로 닫힌 짧은 구간만 Offline Refine하는 구조를 후속 실험할 가치**를 지지한다. 동시 실행의 속도·냉각·Hybrid 최종 CER 성공은 아직 입증하지 않았다. 하나의 수집기와 원본/전처리 링버퍼, Zipformer 프로세스, VAD 구간화, 제한된 Refine 대기 큐, SenseVoice 프로세스를 사용한다. 두 모델에는 같은 전처리 프레임을 공급한다. UI/결과 병합 서비스는 이번에 구현하지 않았다.

1. **냉각·VAD 전제조건 확인:** 물리적 냉각 확인 뒤 허용 조건을 다시 통과해야 높은 부하의 통제 비교를 진행한다. 허용된 VAD 파일의 출처·라이선스·해시를 고정하고 `m30_vad_probe.py`를 원음/저음량/잡음/무음/짧은 발화/긴 합성 입력에 실행한다. 3/5/8초 후보의 검출·완전 누락·경계·대리 endpoint를 비교한다. 일부 짧은 발화의 실제 음성 경계를 사람이 검수해 실제 누락/종료 지연을 확인한다.
2. **공통 전처리의 연속 상태 검증:** `audio_policy.py`에 블록 상태 API를 최소한으로 추가하고, 기존 파생 PCM과 단일 파일 일치·무음→음성 전환·peak·상태 초기화 정책을 시험한다. 동일 프레임을 두 모델에 공급하며 Refine 구간마다 다시 정규화하지 않는다. 전처리 포함 단독 Zipformer 1배속 기준선을 새로 측정한다.
3. **계측 전용 동시 실행기:** 새 `src/edge_asr/hybrid_probe.py`, `scripts/benchmark_hybrid.py`, `configs/hybrid_probe.toml`, `tests/test_hybrid_probe.py`를 추가할 계획이다. 독립 모델 프로세스는 `spawn`으로 한 번 로드한다. 기존 `streaming.py`의 수집·bounded queue·단조 시계 계측을 유지하고 구간 ID·enqueue/start/finish 이벤트만 추가한다.
4. **세 구성의 실제 비교:** Zip1T+Sense1T → Zip1T+Sense2T → Zip2T+Sense1T를 시험하고, 반복 순서는 교차한다. 각각 짧은 검사 후 조건 통과 시 10분 이상·3회로 확대한다. 입력 드롭 0, 계측 완결, 큐 유계, OOM/hang/현재 제한 없음이 우선 완료 조건이다. 큐 초과 시 오디오 드롭과 Refine skip을 별개 기록하고 누락된 구간을 성공처럼 처리하지 않는다.
5. **지연 분해와 판단:** 첫 부분 가설은 오디오 시작 기준 p50/p95, Refine 대기는 start-enqueue, 처리 시간은 finish-start, 실제 음성 종료 후 확정은 정렬된 종료 시각부터 finish까지 측정한다. 정렬 없으면 WAV 끝 대리값만 보고한다. PID별/전체 CPU·RSS·시스템 가용 메모리·TID·온도·클럭·드롭·최대 백로그를 함께 기록한다. 현재 단독 batch RTF로 이 값들을 추정하지 않는다.

텍스트 병합과 강제 분할 후 정확도는 별도 검증 대상이다. 낮은 Offline CER을 그대로 Hybrid CER 개선으로 간주하지 않는다. 사용자와 정할 사항은 VAD 가중치 추가 범위, 실제 짧은 발화 정답 정렬 자료, 허용 첫 자막/확정 지연과 Refine skip 비율이다.
