# M2-3 RP5 통제 비교·외부 평가 기록 (2026-10-28)

Host 에이전트가 SSH로 RP5에서 실제 실행했다. **36개 실행, 측정 호출 1,438/1,438 성공, 워밍업 108/108 성공**이다. 1,438개는 독립 발화 수가 아니라 반복과 별도 진단을 포함한 호출 수다. KSS 주 비교 18회·TID 진단 6회·외부 평가 2회·무음 2회·짧은 발화 2회·합성 장문 6회이며 동시 모델 실행은 하지 않았다.

**SenseVoice는 이번 외부 자료에서 정확도 이점이 있지만, 무음 오인식·장문 비용·발열·동시 실행 지연을 해결하기 전에는 Hybrid 채택을 확정하지 않는다.** 현재 냉각 조건을 포함한 batch 결과이며 고정 클럭에서의 모델 고유 속도 순위가 아니다.

## 조건과 재현성

- RP5 ARM64 / Debian 13 / Python 3.11.18 / NumPy 2.4.6 / sherpa-onnx 및 core 2.0.1. sherpa 네이티브 ORT **1.28.2**, 별도 Python onnxruntime 패키지 **1.31.1**을 구분했다.
- 기존 가중치·KSS WAV·정답·`ko_cer_v1`과 기본 TOML을 유지했다. 실험별 파생 TOML에서 스레드만 변경했다. Zipformer는 기존 encoder/joiner INT8 파일과 비-int8 이름의 decoder 파일, tail padding 0.66초를 사용한다. SenseVoice는 배포 INT8, `ko`, ITN false, 기존 특수 태그 분리 정책이다. 양자화 그래프 dtype/알고리즘을 새로 검증하지 않았다.
- 모델 1회 로딩, 발화마다 새 인식 상태, 첫 발화 워밍업 3회, 파일 순차 처리다. 모델 로딩·WAV 읽기·워밍업은 추론 RTF에서 제외한다. 워밍업 시간 자체는 미계측이며 횟수·성공·발화 ID는 기록했다.
- 실행당 외부 timeout 600초, TERM 후 5초 KILL, 가상 주소 공간 4GiB, core dump 0을 실제 평가 PID에서 검증했다. memory cgroup controller가 없어 RSS 4GiB 상한은 아니다. 제한 완화·패키지 설치·모델 변경을 하지 않았다.
- CPU는 코어 1개가 100%다. RSS는 모델 상주 상태의 관측 최고값으로 정확한 순간 피크를 보증하지 않는다. 로딩과 추론 RSS를 빼서 모델 메모리를 계산하지 않는다.
- 행렬 실행 소스 `36312ce`, 후속 실행 `53e2615`; 단계 사이 `src/edge_asr` 파일 해시·모델 파일·언어/출력 정책 일치를 확인했다. [실험 절차](../../docs/research/m2_comparison.md), [외부 자료 검토](../../docs/research/m2_external_data.md), [기계 판독 요약](m2-3-comparison-20261028.json).

RTF의 역수는 처리 배속이다. 예를 들어 선택된 Zipformer 2스레드는 약 9.29배, SenseVoice 4스레드는 약 22.11배의 batch 처리량이다. 실제 입력·Refine 확정 지연이 이 배속으로 줄어든다는 뜻은 아니다.

Zipformer 4스레드는 `kss-train-01008` 한 발화에서 가설이 달랐고 오류가 88→91개로 늘었다. 같은 구성 안 3회는 모두 동일했다. 1/2스레드는 가설도 같았다. 입력/가중치/평가 소스/스레드 이외 설정을 대조했으며, 네이티브 연산에서 차이가 생긴 원인은 미확인이다.

사전 자동 선택은 모든 스레드의 가설 일치를 요구했으므로 실제로 거부됐다. 이를 성공으로 바꾸지 않았다. 외부 추론 전에 개발 자료를 검토하여 최소 오류 구성 중 중앙 RTF 최저의 5% 이내에서는 적은 스레드를 선택하는 기준으로 **Zipformer 2 / SenseVoice 4**를 고정했다. `selection-auto.log`, `review_selection.py`, `selection.json`에 정책 변경과 근거를 남겼다. 외부 결과에 맞춘 재선택은 하지 않았다.

구성별 로딩 시간 중앙값은 Zipformer 2.431~2.488초, SenseVoice 1.836~1.854초였다. 로딩 중 관측 RSS 최고는 각각 284.7 / 534.7 MiB다. 모델 해시를 먼저 읽으므로 cold-storage 로딩 측정은 아니다. 기본 `configs/`의 Zipformer 2·SenseVoice 1스레드는 그대로이며 비교 설정은 원시 실행 폴더의 `config.toml`이다.

## CPU 스레드와 온도

별도 진단 6회에서 첫 측정 파일 이후 3초간 TID를 100ms마다 관찰했다. 파일 사이 I/O도 포함하며 이 실행의 속도는 KSS 주 비교에서 제외했다. 아래 활동 TID는 자기 관찰 구간 평균 CPU ≥1%인 TID 수다. 전체 TID 수와 실제 CPU 활동 수는 다르다.

| 모델 | 설정 스레드 | 관측 전체 TID 최대 | CPU 활동 TID |
| --- | ---: | ---: | ---: |
| Zipformer | 1 | 5 | 1 |
| Zipformer | 2 | 8 | 4 |
| Zipformer | 4 | 14 | 8 |
| SenseVoice | 1 | 5 | 1 |
| SenseVoice | 2 | 6 | 2 |
| SenseVoice | 4 | 8 | 4 |

Zipformer 2스레드 진단에서 약 100.0/99.3/73.3/55.0%를 사용하는 4개 TID가 관측됐다. 약 324%는 단위 오류로 보이지 않으며 설정값은 전체 프로세스 CPU 상한이 아니다. ORT 세션별 풀과 spinning은 가능한 설명이지만 역할·원인 확정에는 네이티브 프로파일링이 더 필요하다([공식 ORT 문서](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)).

냉각 대기 마지막 표본은 모두 55°C 이하였지만, 직전 별도 표본은 36회 중 5회에서 기준을 넘었다: KSS 2회 55.1°C, 외부 Zipformer 55.65°C, 무음 SenseVoice 56.2°C, 121초 SenseVoice 55.1°C다. 이 편차를 숨기지 않으며 엄격한 등온 시작으로 간주하지 않는다.

실행 중 최고 온도는 85.9°C다. 행렬 05번 Zipformer 4에서 soft 온도 제한 이력, 08번 Zipformer 4에서 주파수 제한·throttling 이력이 새로 나타났다. `0xe0000`은 누적 이력이며 이후 모든 순간에 제한 중이었다는 뜻은 아니다([Raspberry Pi 비트 정의](https://www.raspberrypi.com/documentation/computers/os.html#get_throttled)). 1초 클럭 표본 1.5~2.4GHz에는 초기화·대기도 섞여 있어 저클럭 표본을 모두 열 제한으로 해석할 수 없다.

하드웨어 읽기 관찰 한 시점에는 pwmfan 9,674rpm / 제어 상태 4/4였다. 팬 설치·히트싱크 접촉·실내 온도는 직접 확인하지 않았다. 냉각 설정을 변경하지 않았고 **지속 부하 냉각을 보완한 재측정 전에는 고정 클럭의 속도 차이를 확정하지 않는다.**

## Hybrid 판단과 다음 단계

**Streaming으로 부분 자막을 표시하고, 제한된 음성 구간을 SenseVoice로 재인식하는 구조는 다음 검증 후보**다. 이번 결과만으로 단일 Streaming보다 실제 사용자 경험이 낫다고 판정하지 않는다.

1. 냉각 능력과 입력 음량 정책을 먼저 점검한다. gain을 시험한다면 기존 WAV를 보존한 별도 파생 입력으로 두 모델에 같은 정책을 적용하고 이번 점수를 덮어쓰지 않는다.
2. 동시 실행은 CPU 여유를 보기 위해 Zipformer 1/2와 SenseVoice 1/2부터 비교할 수 있다. 이번 단독 batch 최속 SenseVoice 4가 동시 실행에서도 최선이라는 근거는 없다.
3. 마이크 전에 1배속 replay로 첫 부분 자막 p50/p95, VAD endpoint 시간, 구간 수집·큐 대기·Refine 확정 시간, 수정 빈도/악화 발화, 드롭·백로그·동시 RSS·장시간 온도를 측정한다. 허용 지연과 최대 구간 길이를 먼저 정한다.
4. 무음은 VAD/구간 정책으로 검증하고 “응/그” 같은 단어를 임의 삭제하지 않는다. 실제 음성에서 SenseVoice가 더 틀린 4개도 포함해 교체 정책을 평가한다.
5. 화자 ID를 확보한 더 다양한 음성·장치·잡음·자발화 및 별도 최종 평가 집합을 준비한다. FLEURS 학습 중복 미확인과 이번 사후 분석의 한계를 유지한다.

실제 Streaming 첫 부분 시점, 정답 정렬 인식 지연, Offline Refine 확정 지연, endpoint, Hybrid 드롭/백로그, UI 표시 지연은 이번 결과에서 null이다. 기존 M1 paced_stream 수치는 그 실행의 결과로 유지한다. Hybrid 런타임·Qwen 추가는 이 단계에 포함하지 않았다.
