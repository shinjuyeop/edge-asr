# Q4 prefill의 3T 커널 호출 진단 — 2026-11-13

**3T에서도 Q4 prefill의 비용 증가는 입력 변환과 행렬곱 양쪽에 남았습니다.** 현재 열 제한 없이 수행한 추가 진단에서 같은 긴 PCM의 LLM prefill은 Q8 약412ms·Q4 약546ms였습니다. 같은 MAC 수를 처리한 GEMM의 작업자 CPU 합계는 Q4가21~36% 컸고, F32 활성값 변환은3.5~3.7배였습니다. 추적한 함수의 CPU 증가분 중 행렬곱 GEMM/GEMV가약80~84%를 차지했습니다. 이는 해당 진단의 작업자 CPU 증가분이며 전체 wall 지연의 원인 비율이 아닙니다.

최적화를 적용한 결과가 아니라 **병목 범위를 좁힌 진단**입니다. 생성2T/음성·prefill3T·기존 repack ON·모델/bridge/엔진을 유지했습니다.4T는 기존 실험으로 보존하고 공유 Q8 기본과 실시간 갱신 조건을 바꾸지 않았습니다. [검토용 전체 JSON](kernel-q4-20261113.json), [사전 조건](../../../docs/research/qwen_realtime.md#q4-3t-커널-추적--2026-11-13-사전-조건).

## 입력·실행·계측

- 소스: `a59c90d`, 고정 upstream `7d7f0287530bc8981690f361d8c1627dbae1c99a`. 기존 `prefix-20261112-01/bridge`와 CPU 엔진에 별도 `kernel-q4-20261113-01/libedge_kernel_trace.so`만 추가했습니다. 패키지 설치·운영 엔진 재빌드 없음.
- 모델: 기존 Q8_0/Q8_0과 text Q4_K_M/audio Q4_0. 기존 연속 입력 호출에서 추출한1.028초/4.024초 PCM을 그대로 복사했습니다. WAV SHA는 각각 `c863e9c7585d86532a417317d4f5c2629fa5d0072552d5cf9519936db91832f7`, `b08ecd5591f1bc473866e54ae2bdaec0ec6c727e14de574606a7b3798105f597`입니다.
- `kernel-q4-20261113-01`: 운영 Q8→추적 Q8→추적 Q4→운영 Q4, 총64호출. 첫 Q4 진단의 열 제한을 확인한 뒤 보존했습니다.
- `kernel-q4-20261113-02`: 추가 조건을 `plan.json`에 선언하고 추적 Q4→추적 Q8로32호출. 호출마다 **측정 타이머 밖에서 동일2초 휴지**를 두었습니다. 이 휴지는 실시간 요청 간격·자막 설정과 무관하며 성능 가속으로 집계하지 않습니다.
- 각 조건은 같은16행·8라운드의 공통 `qwen/benchmark.py` reproduction입니다.1~4라운드는 준비,5~8은 끔→켬→켬→끔이며 측정 모드/PCM별2호출 평균입니다. node 동기화 프로파일은 켜지 않았습니다.
- 기존 장비 잠금·600초/4GiB 운영 guard·온도 admission 생략/관측·기본 열 보호를 유지했습니다. 원시는 `results/optimization/opt3/`의 위 실행 ID에, 실행기·분석·검증은 대응하는 `results/maintenance/`에 보존합니다. 잘린 PCM 정답·CER·RTF 기반 실시간 성능은 새로 만들지 않았습니다.

추적기는 공개 ELF 함수 호출을 감싸 실제 선택된 repack 커널을 기록하고 원래 함수로 전달합니다. `CLOCK_MONOTONIC`·`CLOCK_THREAD_CPUTIME_ID`로 **작업자별** 경과/CPU 시간을 모읍니다. 중첩된 입력 변환을 중복 합산하지 않으며 그 합계는 병렬 사용자 대기시간과 다릅니다. 입력 변환은 **중간 F32 활성값→Q8_0/Q8_K**이며 원음이나 모델 가중치를 새로 양자화하는 작업이 아닙니다. [구현·범위](../../../native/README.md#gguf-cpu-커널-호출-추적).

## 실제 선택된 커널

| 가중치 | prefill GEMM | 활성값 형식 |
| --- | --- | --- |
| Q8_0 | `ggml_gemm_q8_0_4x4_q8_0` | Q8_0 |
| Q4_K | `ggml_gemm_q4_K_8x4_q8_K` | Q8_K |
| Q6_K — Q4_K_M에 포함 | `ggml_gemm_q6_K_8x4_q8_K` | Q8_K |

대응하는 GEMV도 관측했습니다. 이 표본의 prefill에는4행 GEMM으로 처리하고 남는 행을 GEMV로 처리하는 경로가 함께 있습니다. **아래 GEMV는 prefill의 나머지 행이며 token decode 비용과 구분합니다.** 8x8/I8MM 경로 호출은 관측하지 않았습니다. 현재 컴파일된8x4 경로에는 ARM NEON·DOTPROD 코드가 있으므로 ARM 최적화 부재나 전체 generic GEMM으로의 후퇴로 해석하지 않습니다.

양쪽 모델의 단계별 MAC 수와 변환한 활성값 원소 수는 같았습니다. 음성 prefill의 합계는 short 약112.05억 MAC/732.16만 활성값, long 약280.13억 MAC/1,830.4만 활성값입니다. Q4의 행렬 차원이 커진 현상은 아닙니다.

## 추가 진단 — 현재 열 제한 없는 조건

아래 prefill wall은 **추적 끔**, 작업자 CPU는 **추적 켬**의 평균입니다. 서로 다른 측정 모드를 합산하지 않습니다.

| 지표 | short Q8 | short Q4 | long Q8 | long Q4 |
| --- | ---: | ---: | ---: | ---: |
| LLM 음성 prefill wall | 162.05ms | 203.04ms | 411.69ms | 546.33ms |
| GEMM 작업자 CPU 합계 | 379.40ms | 457.60ms | 885.06ms | 1,204.88ms |
| 남은 행 GEMV 작업자 CPU 합계 | 38.55ms | 58.17ms | 20.79ms | 29.18ms |
| 활성값 변환 작업자 CPU 합계 | 8.86ms | 32.54ms | 24.28ms | 85.29ms |

short/long에서 GEMM의 CPU 증가율은20.61/36.13%, 활성값 변환 비율은3.67/3.51배였습니다. **입력 변환만 빨리 해도 GEMM의 비용 차이는 남습니다.** 반대로 GEMM만 보면서 입력 변환을 제외해도 전체 경로를 설명할 수 없습니다.

고정 소스의 `ggml-cpu/repack.cpp`를 보면 Q8_K의4행 활성값 변환은 최대값 탐색·정수화·재배열·부분합을 처리하는 공통 구현입니다. `arch/arm/repack.cpp`의 Q8_0 변환에는 NEON 전용 구현이 있습니다. Q4_K GEMM에는4비트 분리·블록 scale/min 처리와 정수 dot이 함께 있고 Q6_K도 별도 복원/scale을 처리합니다. 실제 호출 심볼·고정 소스·원래 바이너리의 disassembly를 함께 확인했으며 관련 소스 SHA를 JSON에 보존했습니다.

이 차이는 후속 조사 지점입니다. **GEMM 내부의 bit unpack·scale·로드·dot·레지스터/캐시 비용은 아직 분리하지 않았으므로 어느 하나를 지배 원인으로 확정하지 않습니다.** 메모리 대역폭이나 명령별 cycle을 측정한 결과도 아닙니다.

## 계측 비용과 열 조건

같은 추적 라이브러리의 켬/끔 native 전체 호출 차이는 첫 진단 Q8 short/long 약+1.35/+2.10%, Q4 +1.57/−0.09%였습니다. 추가 진단은 Q8 +1.09/+1.61%, Q4 +3.26/+1.90%였습니다. 이는 각2회 평균의 관측 차이이며 잡음·순서·열/클럭 변동이 섞여 있습니다. 음수 차이를 계측이 가속했다고 해석하지 않으며 일정 오버헤드를 빼서 보정하지 않습니다.
