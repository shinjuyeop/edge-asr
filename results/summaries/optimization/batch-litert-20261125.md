같은 WAV 20개·170.712초를 각 파일 전체 한 번씩 전사했다. VAD와 부분 요청은 없었다. 100개에서 FLEURS 8개·Zeroth 12개를 길이 ≤5초·5~8초·8초 초과로 나눈 뒤, 기존 T/P8 오류 합의 분위수를 골랐다. ‘매일’ 문제 원음은 사전에 포함했다. 원래 100개 목록 순서를 유지했다. 대표 진단 표본이므로 전체 100개의 새 성능 추정치로 사용하지 않는다. [11월 9일 전체 100개 Batch 7.67%](fixed100-baseline-20261109.md)

양쪽 모두 Q8, 생성 2·음성/Prefill 4스레드, 고정 텍스트 prefix KV, 컨텍스트 512, 생성 상한 128, 한국어 지정이다. A/B 차이는 T·P8과 같은 단일 Conv1·2·3/GELU HEF의 사용이다. 호출 합과 RTF에서 WAV 읽기·모델 로드·첫 호출과 워밍업 3회는 제외했다. 모델 로드 A/B 2.54/2.12초, 첫 호출 5.67/4.79초. 디스크 캐시를 비우지 않았다. 100ms RSS 관측과 추론 PID CPU 시간을 사용했다. CPU 온도·실클럭은 guard의 보드 표본이다. B는 첫 호출·워밍업 포함 24개 모델 호출에서 CNN 동작을 확인했다. 긴 원음은 한 모델 호출 안에서 음성 Encoder를 나누어 총 40회 HEF를 실행했다.

A 대비 B의 호출 합 변화율은 -16.45%, Encoder 평균 시간 변화율은 -49.80%였다. 평균 Encoder 1.774→0.891초, Prefill 1.051→1.019초, Decode 2.802→2.787초로 호출 차이는 대부분 Encoder에서 나왔다. 열 제한 플래그는 A 85/167표본, B 72/143표본에 있었고 두 조건의 실클럭은 관측 범위에서 약 1.50GHz였다. B의 문자 오류 변화는 +10자였으며 원음별 1개가 개선되고 2개가 악화됐다. 토큰열이 일치한 파일은 15/20개다. Encoder 양자화가 바뀌면서 출력 토큰과 Decode 호출 수가 달라질 수 있다. 같은 정규화 가설에서 오류가 남은 파일은 9개였다. 단일 호출에서도 생기는 오류로, 증분 전사의 경계 처리만 바꿔서는 제거하기 어렵다.

오류가 늘어난 두 파일 가운데 `zeroth-147_003_0390`의 7자는 숫자 표기에서 생겼다. A의 ‘이천십삼년’, ‘오백억’이 B에서는 같은 값을 뜻하는 ‘2013년’, ‘500억’으로 표시됐다. 공통 `ko_cer_v1`은 이를 문자 차이로 계산한다. `fleurs-9215841188177323168`에서는 B의 ‘적외선 공간법’ 등 실제 단어도 바뀌었다. ‘매일’ 문제 음원은 A와 B의 전체 WAV 호출에서 모두 정답과 일치했다.

## LiteRT-LM 실행 판정

**보류.** 11월 25일 확인한 최신 공개 태그 v0.20.0(`95df4c2`)의 ARM64 Python wheel을 RP5의 격리 Python 3.13 환경에 설치했다. 공식 번들의 SHA-256은 Host와 RP5에서 검증했다. 같은 한국어 3초 PCM을 붙인 일반 CLI 호출은 x86-64 Host와 ARM64 RP5에서 모두 `NOT_FOUND: Output tensor not found: features`로 대화 세션을 만들지 못했다. 공개 번들의 Encoder 시그니처 출력 이름은 `output_0`이다. 일반 대화 오디오 경로와 ASR용 Omni 경로 사이의 호환성 차이다. 일반 CLI가 오류 메시지 뒤 코드 0을 반환해 전사 출력도 함께 확인했다. [공식 릴리스](https://github.com/google-ai-edge/LiteRT-LM/releases/tag/v0.20.0) · [ARM64 wheel](https://pypi.org/project/litert-lm-api/0.20.0/#files)

이 릴리스의 GitHub 바이너리 첨부 목록에는 Linux ARM64 `omni_runner`가 없다. v0.20.0 소스에서 모델 카드가 안내한 `bazel build -c opt //omni:omni_runner`를 ARM64에서 직접 수행했다. Bazel 7.6.1과 별도 경로에 푼 Clang 19.1.7을 사용했고, 대상 분석에서 588 패키지·18,512 구성 대상이 확인됐다. 의존성 다운로드 후 실제 ARM64 컴파일이 시작됐지만, 준비부터 약 24분이 지나고 빌드 래퍼의 1,000초 상한에서 3,347/5,949 작업까지 기록한 뒤 종료 코드 124로 중단했다. 재사용할 빌드 캐시는 보존했다. 한국어 전사·C의 1·3·5초 성능·CER는 모두 미측정이다. 따라서 속도·정확도 경쟁력을 먼저 확인하는 조건에 따라 C의 1배속 Stage 3도 보류했다. 이 결과는 ARM64에서 공식 ASR 실행 경로를 준비하는 비용을 보여 준다. [Omni 빌드·음성 실행 안내](https://github.com/google-ai-edge/LiteRT-LM/blob/v0.20.0/omni/README.md#1-quick-start-build-and-run-omni_runner)

Omni 파일 CLI는 엔진 로드와 `ProcessNext/Flush` 전체 시간만 출력한다. Omni의 출력 API는 합쳐진 전사 조각 단위다. 토큰별 TTFT·TPOT나 Encoder/Prefill/Decode의 비교 시간은 이 API에서 직접 얻을 수 없다. 다음 비교가 가능해지면 파일 처리 시간과 첫 미확정 본문 반환 시점을 별도로 기록해야 한다.

## LiteRT-LM의 계산 경계와 스트리밍 구조

공식 공개 번들은 `qwen3_asr_0.6b_5s_i8.litertlm` 959,627,232바이트다. 번들에서 직접 확인한 Encoder 입력은 FP32 `[1, 128, 500]` log-Mel, 출력은 FP32 `[1, 73, 1024]`다. LLM은 `prefill_128`과 `decode` 시그니처, 최대 512위치의 KV 버퍼를 제공한다. INT8은 이 번들의 가중치·변환 형태를 가리킨다. 공개 코드는 길이가 짧은 유효 음성도 500 프레임 특징 텐서로 인코딩하며 실제 길이는 Decode 토큰 상한에 사용한다. 완전히 조용한 창에는 별도 단락 경로가 있고 조건에 따라 중심 정렬 STFT로 재시도한다. 20개 중 5초 이하는 1개여서 C를 실행하더라도 19개는 5초 창 분할을 거친 전사로 집계해야 한다. [모델 카드](https://huggingface.co/litert-community/Qwen3-ASR-0.6B/blob/5028edc410addd0f9cf0b35a58a38aeb8bea4604/README.md) · [특징 추출](https://github.com/google-ai-edge/LiteRT-LM/blob/v0.20.0/omni/speech2text/log_mel_spectrogram_processor.cc#L655) · [인식기](https://github.com/google-ai-edge/LiteRT-LM/blob/v0.20.0/omni/speech2text/litert_speech_recognizer.cc#L69)

| 기능 | v0.20.0 Qwen3-ASR 실제 코드 |
| --- | --- |
| 음성 창과 첫 출력 | `omni_runner`는 5초 창·겹침 0.4를 넘겨 2초를 재사용하고 3초씩 전진한다. 이 설정에서 연속 입력의 첫 미확정 후보는 약 3초부터 요청할 수 있다. 세션에 비율을 생략하면 내부 기본값은 0.75다. 일반 파일 명령은 WAV 전체를 1초 조각으로 먼저 큐에 넣고 처리한다. 파일 실행의 처리 시간과 1배속 지연은 측정 경계가 다르다. |
| 경계 병합 | 기본 `TimestampTextMerger`는 유효한 단어 시각이 있으면 시간 제약과 편집 정렬을 사용한다. Qwen `LmDecoder`의 반환 토큰에는 시각이 없다. 이 모델은 겹침 근처의 단어·문자 일치 구간을 찾는 `MergeByWordCount`를 사용한다. 맞는 연결을 찾지 못하면 앞의 미확정 문자열을 확정하고 다음 결과를 보류한다. |

| 문맥과 KV | 이전 음성 일부를 다음 창의 입력에서 다시 사용한다. 각 창이 새 Encoder를 거치고 `LmDecoder`가 `Reset()` 후 음성 임베딩 Prefill을 실행한다. 생성 중에는 KV를 사용한다. 앞창의 생성 텍스트나 Encoder/KV를 다음 창에 넘기는 코드가 이 Qwen 경로에 없다. |
| 입력·스케줄 | `ProcessNext`와 스테이지별 스레드풀을 사용하는 `ProcessAsync`가 있다. `PushInputSource`의 기본 큐는 무제한이다. 현재 edge-asr처럼 새 확정 대기 때문에 오래된 부분 요청을 취소하거나 큐 크기를 제한하려면 입력·스케줄러 계약을 연결해야 한다. |

1. **기존 llama.cpp + Hailo에서 P8의 첫 부분 스케줄링을 먼저 개선한다.** P8의 선택된 첫 본문 p95 사례는 원음 시작 후 7.73초에 제출했고 큐는 0.003초, 실행 시작→첫 본문은 1.69초였다. 100개에서 최신 본문을 내지 못한 부분 요청 비용은 T 5.16초, P8 60.61초였다. 부분 취소의 계산시간은 23.19→131.05초였으며 일부 취소는 이미 유용한 본문을 냈다. 첫 부분 입력 길이를 제한하고, 첫 본문을 낼 요청을 긴 반복 부분보다 우선하며, 다음 확정이 가까울 때 새 본문을 낼 여유를 보고 후속을 생략하는 대조를 한다. 열 보호는 유지한다.
2. P8의 확정 PCM·토큰 및 경계 CER를 대조해 보존하고 첫 본문·최신 음성 갱신 공백을 T에 접근시키는지 잰다. 일부 PCM 진단에서 유효한 15~20% 이상 차이가 확인되면 동일 100개와 독립 자연발화로 확대한다. 다음 순서는 Q8 CPU Decode와 음성 Prefill이다.
3. 공식 Linux ARM64 Omni 실행 파일 또는 재사용 가능한 빌드가 확보될 때 C의 한국어 단일 창을 먼저 재개한다. 해당 조건에서 속도·정확도·자원 중 비교 가치가 보여야 1배속 소규모 실험에 들어간다. LiteRT-LM 전체 전환과 Hailo 연동은 별도 구현 비용이 든다. 고정 shape와 무시각 겹침 병합의 효과를 RP5에서 먼저 확인할 근거가 필요하다.

## 재현과 상태

- [요약 JSON](batch-litert-20261125.json)의 `selected` 순서와 WAV SHA를 사용한다. 원본 `data/evaluation/edge100-20261109-01/manifest.jsonl`을 ID로 골라 원래 행을 보존한다. UTF-8 JSONL의 입력 SHA는 JSON에 있다. 1·3·5초 PCM은 `results/optimization/opt3/hailo8l-q8-20261120-01/inputs/front.jsonl`과 동일하다.
- RP5에서 기존 실행 잠금 `results/listener/inference.lock`을 잡고 ARM 상한을 1.5GHz로 설정한다. 조건별 시작 전 2초 간격 3회 67°C 이하를 확인한다. 기존 운영 열 보호와 거버너를 사용한다. Batch A→B, 반복 PCM B→A 순서다. B에만 `LD_PRELOAD`와 `EDGE_ASR_HAILO_CNN_STACK_HEF`를 [검증한 프로필](../../../configs/listener_hailo_boundary.toml) 경로로 지정한다.
- `thermal-run --temperature-policy operational --skip-temperature-admission` 아래에서 `tools benchmark-qwen3 --config configs/gguf_realtime_2_4.toml --manifest <목록> --output <원시 폴더> --repetitions 1`을 실행한다. Batch는 `--protocol baseline`, 12개 PCM 행은 `--protocol reproduction`이다.
- 첫 B 준비는 기존 펌웨어 디렉터리에 대한 임시 설치 도구의 보호 검사에서 중단됐다. 이후 보드에 있던 펌웨어와 보관본이 바이트 단위로 일치함을 확인해 그 파일을 사용했다. 실행 뒤 드라이버를 내리고 ARM 상한과 기존 펌웨어 해시를 복원 상태에서 확인했다.
- 원시는 두 장비의 `results/optimization/opt3/batch-litert-20261125-01/`에, 실험 명령·냉각·빌드·원본 해시 목록은 개발 PC `results/maintenance/batch-litert-20261125-01/`에 보관한다. 회수한 원시 파일 44개의 SHA-256이 양쪽에서 모두 일치했다. 모델·HEF·WAV와 원시 로그는 Git에서 제외한다. Host Python 회귀 514개, Node 8개, Ruff와 보존 자산·공유 설정 검사를 통과했다.
