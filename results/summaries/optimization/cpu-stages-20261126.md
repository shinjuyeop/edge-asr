**선정 및 입력 조건.** 기존 1·3·5초 WAV와 고정 P8 확정 158구간 중 입력 프레임·출력 토큰 수의 15·50·90백분위에 가장 가까운 6개를 썼다. ## 어떤 계산이 달라졌는가

**KleidiAI Q8.** 기존 OFF/ON 엔진은 같은 upstream과 CPU native·OpenMP·repack 옵션으로 빌드했다. ON이 로드한 Q8 CPU 전용 버퍼는 603.90MiB였다. T/P8와 같은 CNN HEF 제출 로그를 호출별로 확인했다. 고정 소스는 Q8_0의 32개 단위 scale을 적용한 뒤 행의 최대 절댓값으로 scale을 다시 계산해 INT8로 반올림하고 pack한다. 같은 GGUF를 열어도 이 버퍼의 수치가 달라진다. 5초에서 모델을 로드한 뒤의 이득과 별도로, ON의 프로세스당 로드 시간은 9.8~10.1초였고 같은 빌드 계열 OFF는 2.2~2.4초였다. [고정 런타임의 Q8 pack](https://github.com/ggml-org/llama.cpp/blob/7d7f0287530bc8981690f361d8c1627dbae1c99a/ggml/src/ggml-cpu/kleidiai/kleidiai.cpp) · [이전 독립 Decoder 측정](decoder-q4-20261117.md)

**결합 Prefill.** 이번에 구현한 선택 bridge는 같은 요청 안에서 이미 계산한 음성 임베딩과 바로 뒤의 프롬프트 텍스트를 한 causal batch로 처리한다. 각 음성 행의 위치, 후속 토큰 ID와 위치, 마지막 행의 logits 요청을 유지한다. 앞의 고정 prefix KV는 기존 경로를 쓴다. 이전이나 미래의 PCM을 재사용하지 않는다. 마지막 음성 청크와 suffix가 한 physical batch에 들어갈 때만 실행하며, 음성과 suffix가 합쳐진 시간은 `audio_suffix_eval_s` 한 곳에 기록한다. Host의 실제 x86 Q8 입력 3개에서 토큰열을 확인한 뒤 RP5의 같은 소스·같은 엔진으로 결합 끔/켬을 별도 빌드했다. [bridge](../../../native/gguf/bridge.cpp) · [빌드 옵션](../../../native/gguf/build.py)

**기존 P8 확정 점유.** 저장된 고정 100개의 성공 확정 158회, 3,470 decode 호출에서 native 합은 497.762초였다. Decode 275.179초(55.3%), Audio Prefill 91.255초(18.3%), Encoder 88.734초, 텍스트 prefix/suffix 9.770/24.911초, sampling 2.992초, KV 초기화·재사용 처리 0.734초였다. KV 내부 읽기와 쓰기는 Attention/그래프 시간에도 포함된다. sampling·KV 초기화만 모두 없앤다는 가정의 절감 상한도 이 기록에서는 0.75%다. [P8 경계](boundary-20261124.md) · [부분 요청과 워커 점유](partial-scheduling-20261125.md)

가중치를 읽는 Decoder의 Q8 텐서는 출력층 165,306,368바이트, Attention 계열 187,314,176바이트, FFN 계열 280,870,912바이트다. 이 세 합은 약 633.49MB다. 입력 embedding 테이블 전체는 토큰마다 읽지 않으므로 제외했다. 5초 기준 토큰당 75.0ms에서 논리 가중치 크기를 시간으로 나누면 약 8.44GB/s이며 목표 60/50ms에는 10.56/12.67GB/s가 필요하다. 실제 DRAM 트래픽은 캐시·prefetch·활성값·KV·스레드 동작을 포함하며 이 계산으로 확정할 수 없다. RP5의 L2는 코어당 512KiB, 공유 L3는 2MiB다.

정수 누적 분리, 두 거리의 prefetch, OpenMP 대기, 토큰 2개 묶음은 기존 교차 실측에서 전체 ASR 이득이 작았다. 전체 Q4와 Q6 출력층 보강은 확정 실패와 CER 악화를 남겼다. 이 실험에서는 같은 Q8 가중치의 실행 경로와 Prefill 결합에 계산 예산을 사용했다. ## 같은 Q8 파일에서의 전사 동등성

- 결합 Prefill은 RP5에서 결합 전·후 9개 PCM의 원문·토큰이 매번 일치했다. 18회 호출 평균 합은 끔 44.72초, 켬 43.97초(1.68% 감소), CPU 124.71→121.73초였다. Prefill 10.57→9.84초(6.9% 감소), 5초 전체 2.608→2.569초였다. 출력 표본 내 동등성은 확인했으며 결합 순서에 따른 모든 입력의 수치 동등성은 입증하지 않았다. 8초 입력은 앞 음성 청크를 따로 처리하고 마지막 음성 청크와 suffix만 결합했다. 전체 호출의 선별 기준 5%에는 미달해 이 후보의 1배속 평가는 생략했다.
- KleidiAI의 1·3·5초 PCM과 P8 확정 6개 중 5개는 원문·토큰이 같았다. 나머지에서 `ib리그 명문 대학의 발표인이 믿어야 할까요?`가 `ib리그 명문대학의 발표인이 믿어야 할까요`로 바뀌었다. 짧은 PCM에 정답 문장을 인위적으로 붙이지 않았다.
- 별도 확대 대조는 기존 Batch 20개 가운데 P8의 소유 범위가 원음에 단독 귀속되는 18개를 사용했다. 원음 경계를 걸치는 두 개는 제외했다. 26개 확정 PCM에 대한 새 운영 출력은 저장 P8의 원문·토큰과 26개 모두 같았다. KleidiAI는 같은 26개를 80.74→73.89초(8.5% 감소)에 끝냈고 6개 토큰열이 달라졌다. 같은 원음 안에서 순서대로 연결해 채점한 `ko_cer_v1`은 67/731(9.17%)→70/731(9.58%)였다. 치환/누락/삽입은 29/31/7→32/31/7였다. 모든 구간에서 EOG까지 전사했다.
- 실제로 `이천십삼년 한 해 동안`이 `2013년 한 해 동안`으로, `상속세의 헛점을`이 `상속세의 허점을`으로 바뀌었다. 띄어쓰기·문장부호만 바뀐 사례도 있었다. 이 채점은 발화 의미와 표기 관습을 따로 판정하지 않는다. 18개는 개발·회귀 자료다.

독립 검증용 자유대화는 두 KsponSpeech 평가 분할에서 2~6·6~10·10~20초를 하나씩 골랐다. 모델 출력 확인 전에 길이를 충족하도록 검색 범위를 넓혀 528개 후보에서 시드와 해시로 6개(44.294초)를 확정했다. 평가·개발 목록의 기존 해시 915개를 배제했고, 기존 워커 599개에 기록된 원음 SHA-256 158종과의 중복도 0개였다. 화자 ID가 없어 화자 독립성은 확인할 수 없었다. 채점은 공개 정서법 전사와 기존 `ko_cer_v1`으로 고정했다. [사용한 데이터 리비전](https://huggingface.co/datasets/jubang0219/KsponSpeech/tree/3a7bb5fef6937bbc29baffd25bbf1443e4f40564)

## 실제 CPU 커널과 장치 한계

고정 5초와 P8 8초 PCM에서 기존 graph callback과 PMU preload를 별도 진단으로 실행했다. OFF의 실제 심볼은 `ggml_gemm_q8_0_4x4_q8_0`, `ggml_gemv_q8_0_4x4_q8_0`, `quantize_mat<4,Q8_0>`, `quantize_row_q8_0`였다. 출력층의 가중치 shape은 [1024, 151936]이다. ON은 실제 ASR 세 호출 및 초기화에 대해 KleidiAI의 `16x4_neon_dotprod` GEMM 24,704회와 `1x4_neon_dotprod` GEMV 88,448회 진입을 별도 wrapper로 확인했다. 이 실행은 속도 표에서 제외했다. [고정 DOTPROD dispatch](https://github.com/ggml-org/llama.cpp/blob/7d7f0287530bc8981690f361d8c1627dbae1c99a/ggml/src/ggml-cpu/kleidiai/kernels.cpp) · [기존 PMU 계측](pmu-q8-20261117.md)

Decode 104회(5초와 8초 각 두 번)의 node 합이 분모다. 출력층은 약 17.4ms/토큰의 계측 시간이었다. 일부 KV 접근은 Flash Attention과 메모리 연산에 포함돼 KV 단독 비용, barrier 단독 대기, 실제 DRAM 읽기 바이트는 분리하지 못했다. per-node 동기화를 켜면 해당 두 PCM native 합 평균은 뒤쪽 비계측 대조보다 5.0% 길었다. PMU는 같은 PCM 순서에서 준비를 제외한 4회씩 비교했다. 끔 14.586초, timing 14.800초(+1.47%), cache 15.158초(+3.92%), stall 15.100초(+3.52%)였다.

880,052회 유효 PMU 표본에서 그룹 실행/활성 시간이 같았다. 출력층/나머지 GEMV의 L2 refill/access는 29.46/30.48%, IPC는 0.62/0.65, backend stall/cycle은 77.78/76.71%였다. 두 작업자의 MAC 분배는 각각 약 50:50이었다. 독립 512MiB 순차 읽기·합산(2스레드, 1.5GHz)에서는 첫 회를 제외하고 9.66~9.69GB/s였다. 이 단순 루프는 CPU에서 실제로 달성한 비교점이며 시스템 메모리의 최대 대역폭 측정은 아니다. 50~60ms 목표의 논리 가중치 처리율은 이 루프보다도 높다. 같은 단일 토큰·가중치 배치에서 가벼운 prefetch나 sampling 변경만으로 목표를 달성할 근거는 약하다.

## P8 스트리밍 결과 해석

개발 7개·서울 1개·독립 대화 6개는 같은 날 두 엔진을 모두 1배속으로 재측정했고, 각 프로세스는 같은 4초 입력으로 워밍업했다. 고정 100개·서울 8개·낭독 4개·30분 연속은 11월 24일 저장 P8 운영 대조와 이번 KleidiAI 실행을 비교했다. 이 네 쌍은 각각 같은 입력 목록, WAV, VAD 신호, 워밍업 PCM과 확정 PCM을 대조했다. 날짜·입력 시작 온도·실클럭이 달라 지연 차이 전부를 CPU 커널의 효과로 귀속할 수 없다. T는 이번에 재실행하지 않았다. T의 저장 고정 100개 CER는 11.95%, 첫 본문·최신 공백·공통 끝→확정 p95는 각각 4.13·4.00·3.06초다. [T·P8 원래 대조](boundary-20261124.md)

고정 100개에서 이전 확정이 첫 부분 요청을 막은 시간 합은 269.65→238.12초, 첫 부분 제출 가능 시점에서 실제 첫 요청 제출 또는 확정까지의 p95는 5.81→4.39초였다. 성공 부분 요청은 98→140회, 취소된 부분 요청은 86→81회였다. 확정 호출에서 절약한 38.63초와 부분 호출에 더 쓴 38.68초가 거의 같았다. 확정의 단어 내부 종결 후보는 10→9건, 인접 반복은 4→3쌍, 삽입 반복은 4→3건이었다. 정규화된 부분 자막 수정은 40→61회, 철회한 접미부는 295→362자로 늘었다. 갱신 기회가 늘면서 화면의 수정량도 늘었다.

확정 PCM을 기준으로 원문까지 확인하면 짧은 구간에서 차이가 드러난다. 고정 100개의 0.25초 `어.`, 0.31·0.48초 `이.`가 후보에서 모두 `.`이 됐다. 서울의 0.34초 `네.`와 0.29초 `아.`도 `.`이 됐다. 정규화 후 빈 확정은 고정 100개에서 3→6개, 서울 8개에서 0→2개였다. 두 구성 모두 해당 자료의 모든 확정 호출을 EOG로 끝냈다. 이 조각에 독립 정답이 없으므로 운영 출력이 실제 발화와 맞는지는 별개다.

**운영 P8을 정확도·토큰 회귀 기준으로 유지하고 KleidiAI는 반응성 대조용으로 권장한다.** 5초 Audio Prefill 35.7% 절감과 대부분의 1배속 자료에서 짧아진 갱신 공백은 재현할 가치가 있다. 서울·낭독에서 오류가 늘고 짧은 구간의 본문이 사라지는 경우가 생겼다. 같은 Q8에서 토큰 동등성을 우선하는 서비스에 일괄 적용할 근거는 부족하다. 기존 T의 첫 본문 4.13초 수준, 5초 호출 2.2초·RTF 0.44, Decode 토큰당 50~60ms와 20~30% 절감 목표에는 미달했다. 30분 실행의 온도와 클럭은 현재 냉각 환경의 지속 한계를 보여 준다. 전력계와 DRAM 바이트 카운터는 이번에 사용하지 않았다.

다음 구현 우선순위는 **Q8_0의 32개 단위 scale을 보존하는 다중 행 FFN·Attention Prefill**이다. 동일 PCM에서 현재 KleidiAI의 Prefill 이득 중 얼마나 보존하면서 짧은 전사의 출력 차이를 줄일 수 있는지 먼저 확인할 수 있다. Decode에서는 FFN과 Attention 선형층의 합이 약 64%이고 출력층은 약 22%다. 새 가중치 배치가 실제 토큰당 시간을 반복해서 줄이고 완료율·오류를 보존할 때 확대한다. 짧은 본문·정규화 후 빈 전사·부분 자막의 철회를 다음 회귀 항목에 포함한다.

m=results/maintenance/cpu-stages-reproduction

for k in off on; do

```bash
cd ~/projects/edge-asr
m=results/maintenance/cpu-stages-20261126-01
flock -w 60 results/listener/inference.lock \
  bash results/maintenance/batch-litert-20261125-01/use-device.sh \
  bash "$m/run.sh" "on-retest-$(date +%Y%m%d-%H%M%S)"
```

장치 스크립트는 실험 전과 같이 드라이버가 내려간 보드에서 기존 펌웨어 해시를 확인하고 HailoRT 4.23 라이브러리를 준비한다. `run.sh`는 선택한 엔진의 `engine/bin`을 `LD_LIBRARY_PATH` 앞에 놓고, `thermal-run` 아래 기존 `benchmark-qwen3 --protocol reproduction`을 사용한다. 실시간 비교는 동일한 P8 프로필로 `replay-qwen3`와 `subtitle-metrics`를 사용했다.
