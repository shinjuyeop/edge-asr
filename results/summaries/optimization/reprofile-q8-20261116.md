# Q8 재프로파일링: 긴 표시 공백과 실제 연산 병목

2026-11-16. **체감 지연은 짧은 초기 결과 뒤 후속 요청이 막히는 경로를 먼저 보완하고, 엔진 최적화는 Q8 decode와 audio encoder를 우선 검토하는 것이 타당합니다.** 최신 연속 입력 850호출을 재집계하고, 해당 실행의 PCM 3개로 RP5에서 추가 48호출을 계측했습니다. 모든 추가 호출의 전사/token ID가 원래와 같았습니다. 이번은 병목 분석이며 최적화 효과를 새로 측정한 결과는 아닙니다. [검토용 JSON](reprofile-q8-20261116.json), [사전 조건](../../../docs/research/qwen_realtime.md#q8-지연-경로연산-재프로파일링--2026-11-16-사전-조건).

## 전체 호출 비용: decode가 가장 크다

현재 유지한 **예산3.0초의 427호출** 기준입니다. 합계657.033초는 891.145초 입력 중 부분/확정 호출의 누적 실행 시간이며 사용자 지연과 다릅니다. 단계가 겹치는 `audio_and_prefill_s`를 다시 더하지 않았습니다.

| 단계 | 누적 시간 | 전체 호출 비용 비중 |
| --- | ---: | ---: |
| token decode — 다음 토큰 생성 연산 | 310.531초 | **47.26%** |
| audio encoder | 192.713초 | **29.33%** |
| LLM 음성 prefill | 102.457초 | **15.59%** |
| 음성 뒤 공통 text suffix 평가 | 44.338초 | 6.75% |
| sampling | 3.751초 | 0.57% |
| 토큰 callback | 2.640초 | 0.40% |
| 전처리 | 0.193초 | 0.03% |
| KV 초기화·제거 | 0.00961초 | 0.00146% |
| 앞 고정 text prefix 평가 | 0초 | 0% —427호출 모두 캐시 적중 |

나머지는 위 타이머 밖의 호출 비용입니다. 예산3.2초의423호출도 decode 약46.72%·encoder29.74%·음성 prefill15.82%로 같은 큰 순서입니다. 전체 decode 평균은 토큰 평가1회당 약62.31ms였습니다. 이 값만으로 메모리 대역폭·CPU 연산·동기화 중 어느 것이 제한인지 확정하지 않습니다.

## 표시가 늦는 두 경로

**원음별 첫 표시**의 평균2.374초는 같은100개 이벤트의 요청 전 경과1.516초 + 큐0.482초 + 호출 시작부터 표시0.376초로 분해됩니다. 요청 전에는 원음 앞 무음·VAD 시작 위치·부분 음성 수집이 포함되므로 전부 없앨 수 있는 낭비로 해석하지 않습니다. 음향 단어 시작/끝 주석도 없습니다. 첫0.6초는 요청할 PCM 기준이고 원음 재생0.6초 뒤 표시를 보장하지 않습니다.

최초 부분125회의 누적 큐 대기는93.702초였습니다. 그중 앞선 확정 호출의 **첫 토큰 이전과26.825초, 첫 토큰 이후와64.943초**가 겹쳤습니다. 후자는 전체 누적 대기의69.31%입니다. 첫 토큰 이후에는 decode·sampling·callback 등이 포함되며 순수 decode 타이머와 같다고 부르지 않습니다. 현재 직렬 작업자는 앞 확정 호출이 끝나야 다음 부분을 시작하므로, 확정 decode 가속은 다음 발화의 첫 표시에도 영향을 줄 후보입니다.

반면 **첫4자까지5초가 넘은12개**는 다음과 같았습니다.

| 같은12개 이벤트의 경로 | 평균 |
| --- | ---: |
| 원음 시작→그4자를 낸 요청 제출 | **5.234초** |
| 그 요청의 모델 큐 대기 | 0.00062초 |
| 호출 시작→4자 표시 | 1.568초 |
| 합계 | **6.803초** |

이12개 중10개는 확정 호출에서,2개는 후속 부분에서 첫4자가 나왔습니다. 앞선 최초 부분의 큐 문제와 마지막4자 표시 작업의 큐를 혼동하면 원인을 잘못 짚게 됩니다. 전체 분위수를 서로 더하지 않고 각 이벤트의 합과 공통 청취 지표를 검산했습니다. 첫4자는 정답4자를 의미하지 않습니다.

대표 `zeroth-104_003_1968`은 최초0.612초 PCM이2.170초 기다린 뒤 `.`만 반환했고, 비용/끝 여유 판단 후 최종에서 첫4자가7.242초에 나왔습니다. `fleurs-9406104450793293120`은 최초 큐가0.3ms여도 `오` 뒤 비용 예산에 막혀4자가8.178초에 나왔습니다. 앞 사례에는 큐와 후속 보호가 모두 필요하고 뒤 사례는 큐 순서만 바꿔 해결하기 어렵습니다. 이 두 원인의 분리가 이번 분석의 핵심입니다.

입력 처리 큐 p95는1.835ms·100ms 청크 처리 p95는14.941ms였고, Python 토큰 수신→발행은 p95 약0.011ms였습니다. 웹의300ms 조회는 별도 체감 개선 후보지만 RP5 이벤트 자체의7초 지연을 설명하지 않습니다. SSH·브라우저·물리 스피커 지연은 이번에 측정하지 않았습니다.

## 추가 실제 계측: encoder와 Q8 행렬 연산

아래는 기존 운영 bridge의 준비 후4회 평균입니다. 고정 PCM 내부 시간으로, 새 연속 성능과 구분합니다. 연속 실행과 시작 온도·호출 순서·토큰 callback 유무가 달라 값의 감소를 최적화 이득으로 보지 않습니다.

| PCM | 전체 호출 | encoder | 음성 prefill | text suffix | decode |
| --- | ---: | ---: | ---: | ---: | ---: |
| 최초0.612초 | 0.399초 | 0.160초 | 0.092초 | 0.089초 | 0.056초 |
| 후속2.276초 | 1.652초 | 0.469초 | 0.234초 | 0.091초 | 0.847초 |
| 확정4.504초 | 3.243초 | 0.802초 | 0.409초 | 0.096초 | 1.913초 |

계측을 켠 각 단계의 **node 시간 합계 내 비율**은 다음과 같습니다. 이를 위 운영 시간에 직접 곱해 절감량을 추정하지 않습니다.

| 연산 경로 | 최초 | 후속 | 확정 |
| --- | ---: | ---: | ---: |
| encoder FP16 합성곱·투영·IM2COL | **48.78%** | **51.42%** | **49.48%** |
| 그중 두 번째 합성곱 행렬곱 `node_15` | 24.6% | 25.0% | 24.1% |
| 음성 prefill Q8 행렬곱 | 89.0% | 84.6% | 75.4% |
| decode Q8 행렬곱 | **93.6%** | **91.4%** | **89.4%** |
| decode의 `output.weight` —위 행렬곱에 포함 | 22.8% | 22.4% | 22.0% |

고정 upstream `tools/mtmd/models/qwen3a.cpp`의3회 conv2d→투영과 node를 대조했습니다. Q8에서도 유지된 FP16 앞단이 encoder의 절반가량입니다. prefill은 여러 층의 행렬곱에 분산되며, decode에는 어휘 출력 행렬 하나의 비중도 큽니다. **첫 token 준비를 줄일 때는 encoder가 가장 큰 단일 단계, 전체 처리와 다음 요청 대기를 줄일 때는 decode가 가장 큰 단계**입니다. `output.weight`를 건너뛰면 같은 토큰을 보장할 수 없으므로 커널·벡터화·데이터 배치 같은 계산 경로를 검토해야 합니다.

짧은 최초의 text suffix 비용약90ms도 보이지만, 이 text는 앞 음성의 attention 결과에 의존합니다. 문자열이 같다는 이유로 이전 KV를 그대로 재사용할 수 없습니다. 현재9토큰의 음성 **앞** prefix와 다른 조건입니다.

## 어떤 순서로 개선할까

| 우선순위 | 후보 | 기대하는 개선 경로 | 난이도·제약 |
| --- | --- | --- | --- |
| **1 — 작은 실험** | 최초 결과가1~3자/구두점일 때 후속1회 보호 | 확정까지 기다리는 긴 공백에 직접 개입 | 기존 일반 예산 확대와 구분. 유휴 시 최신 음성으로 한 번만, 횟수/큐 제한을 유지해 첫4자·최종 반환을 함께 검증 |
| **2 — 엔진의 가장 큰 비용** | Q8 decode의 GEMV·출력 행렬 경로 | 확정 처리와 다음 최초 요청 대기 감소 | 커널 내부 비용·작업 분할을 더 좁혀야 함. 같은 전사/토큰을 유지하는 가속은 아직 미측정 |
| **3 — 첫 token 준비** | encoder FP16 합성곱/투영 경로 | 첫 호출과 모든 반복 호출 준비 시간 감소 | 구현 난이도 높음. 별도 빌드와 수치·전사 동등성 검증 필요 |
| **4** | Q8 음성 prefill·suffix 연산 | 첫 token 준비의 나머지 비용 감소 | encoder보다 작은 전체 비중. 입력 의존성을 유지하며 배치·커널 검토 |

첫 후보의 구체적인 다음 실험은 **최초 결과가4자 미만인 구간에만 제한적으로 후속 요청을 보호**하는 것입니다. 임시/확정 상태를 구분하고 최종5초 원음·210구간 전사/token·428오류 유지를 검사합니다. 첫4자/갱신 공백이 줄어도 다른 발화 첫 표시·실패/드롭·최종 반환·열 부담을 함께 기록해야 합니다. 아직 구현하거나 효과를 측정한 정책은 아닙니다. 입력 경계를 바꾸는 부분 목록 선별 대신 원래100개 시간축을 유지합니다.

임시 생성 길이 제한은 보조 후보입니다. 실제 로그에서 부분 호출173개가4자에 도달한 뒤 종료까지 쓴 시간은 합계50.367초,8자에 도달한75개는19.462초였습니다. 후자는 전체657.033초의2.96%에 해당하는 **이미 관측한 잔여 실행 구간**입니다. 중단 구현·새 스케줄에서 그대로 절감되는 양이 아니고, 짧은 표시가 오히려 더 나빠질 수 있습니다.4자 제한은 임시 내용이 너무 짧아질 수 있고, 확정 생성을 자르면 정확도 유지 조건과 충돌합니다. 현재 어댑터는 EOG 없는 종료를 실패로 처리하므로 임시 전용 정상 중단 계약·캐시 초기화·최종 회귀 검증부터 필요합니다. 일괄8자 제한만으로 큰 지연 해결을 기대하지 않습니다.

KV 초기화·전처리·Python 토큰 발행은 현재 비중이 작아 우선순위가 낮습니다. 기존 음성 prefix KV를 무조건 재사용하거나 이미 악화가 관측된 확정3초로 돌아가는 것을 이번 결과가 지지하지 않습니다. 현재 실험만으로 냉각 개선의 가속률·메모리 대역폭 병목·새 엔진의 우열을 주장하지 않습니다.

## 계측 영향·검증·보존

node 계측은 graph 분할·동기화를 추가합니다. 같은 계측 bridge 끔 대비 켬의 전체 비용은 최초24.42%·후속9.67%·확정8.64% 증가했습니다. node 순위는 진단 근거로 사용하되 일정 오버헤드를 빼서 운영 성능으로 환산하지 않습니다. 단계 node 합계의 wall coverage는 약94.5~99.5%이며 모든 trace가 유효하고 넘침은0입니다.

| 추가 실행 | 시작 /최고 /종료 온도 | 현재 제한 플래그 |
| --- | --- | --- |
| Q8 운영 | 57.85 /81.50 /72.70°C | 0 |
| Q8 계측 | 73.80 /83.15 /74.35°C | 0,8 |

48호출은 모두 성공했고 원래 PCM별 전사/token ID와 같았습니다. 기존 engine 라이브러리·가중치·환경과 보호814파일이 유지됐고 새 원시33파일 해시·Host/RP5의 지연/연산/잔여시간/검증 JSON 독립 재집계가 일치했습니다.600초/4GiB guard·장비 잠금·부팅 ID도 유지했습니다. Host 관련35개 중34통과·선택 native 헤더1개 생략이며 RP5 실제 모델48호출과 구분합니다. 첫 Host 명령의 테스트 모듈명 오류는 보존하고 올바른 `test_qwen3_gguf`로 재실행했습니다. 모델 코드가 바뀌지 않아 전체 회귀·새100개추론은 반복하지 않았습니다.
