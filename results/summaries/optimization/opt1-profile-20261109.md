# OPT-1 ONNX 호출 경계 실측 — 2026-11-09

고정 KSS 6개에서 **LLM prefill+token decode의 ORT 실행이 내부 전사 시간의 71.32%**를 차지했습니다. 56ms 실패는 첫 logits가 약 0.46초에 준비된 뒤 64회의 token decode에서 약 4.6~4.7초를 쓰는 것으로 확인했습니다. 추론·가중치 최적화 전의 병목 분석이며 성능 개선 실험은 아닙니다. [프로토콜·계측 정의](../../../docs/research/opt1_profiling.md), [기계 판독 요약](opt1-profile-20261109.json).

## 구성과 입력

소스 `fa3975b34063da74093199b232a1a170e035480b`, 기존 Qwen3-ASR-0.6B INT8·sherpa-onnx 2.0.1/native ORT 1.28.2·2T·max_total_len 512·max_new_tokens 128을 사용했습니다. 기존 wheel은 그대로 읽고, 별도 계측 공유 라이브러리를 실험 자식 프로세스에만 LD_PRELOAD했습니다. ARM64 빌드의 헤더/코드/바이너리 해시와 원본 ORT 해시를 기록했습니다.

Host/RP5 native mock에서 C API 인자·출력·오류 전달, 전사별 reset, off, overflow, 세션 해제를 검증했습니다. 실제 RP5에서는 Conv·Encoder·Decoder 3개 세션과 Run 순서를 확인하고 모든 native event가 Python decode_stream 안의 순차 시각 범위에 들어가는지 검사했습니다. 실제 ONNX 연산·세션 옵션·출력 처리는 기존 런타임과 어댑터가 수행합니다.

OPT-0의 KSS 6개와 고정 진단 8개를 재사용했습니다. Stock anchor는 6회, ABBA는 6파일×4라운드=24회입니다. ABBA 첫 추론·워밍업 3회는 off이고 scored 라운드는 off/on/on/off입니다. 단계 비중은 이 중 on인 12호출(고유 6개×2회)의 내부 transcribe 시간 합을 분모로 계산합니다.

사용자 요청대로 operational + skip-temperature-admission을 사용했습니다. 온도 대기·온도/열 감속 중단은 생략하고 기본 펌웨어 보호·4GiB·300초·전압/필수 센서 검사와 온도/클럭 관측은 유지했습니다. 원시 실행은 `results/optimization/opt1/opt1-profile-20261109-01/`입니다.

## 계측 영향과 회귀

ABBA on/off는 같은 proxy·API hook 경로에서 시계/이벤트 기록을 켜고 끈 비교입니다. on 처리 시간 합의 상대 차이는 -0.848%였습니다. 파일별 p50 차이는 모두 ±5% 이내입니다. 음수 차이를 속도 개선이나 음수 오버헤드로 해석하지 않습니다. 작은 표본·열/실행 상태 변동을 포함한 관측입니다.

내부 transcribe 바깥의 wrapper 추가 시간은 on 평균 0.144ms, off 평균 0.082ms입니다. 이는 ctypes 호출·event 수집/검증 등 바깥 비용만 측정하며 native 내부 계측 비용이나 상시 hook 비용 전체의 상한이 아닙니다.

별도 stock anchor RTF는 0.6746, ABBA 전체 24호출 RTF는 0.7039입니다. 온도/순서·반복 수가 달라 이 차이를 순수 hook 오버헤드로 분리하지 못합니다. ABBA off에도 proxy와 Run 전달 hook이 있어 상시 경로 비용이 남습니다. 후속 엔진 비교에서는 profiler를 끈 실제 실행기를 사용하고, 단계 분포는 별도 진단으로 취급합니다.

Stock 6/6·ABBA 24/24 성공, 정답 문자 커버리지 100%이며 모든 raw text/tokens가 OPT-0와 같습니다. KSS 고유 6개 CER 2.20%(2/91자)는 품질 회귀 검사이며 전체 KSS 50개 결과의 개선이 아닙니다.
