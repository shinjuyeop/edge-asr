# 빠른 Q4 연속 수정 자막 — 2026-11-17

최신 음성으로 임시 자막을 계속 고치는 `continuous` 정책을 구현했습니다. 횟수·누적 비용 상한 대신 최신 후보 하나·실행 완료 알림·최종 우선·열 상태를 사용합니다. **연속 입력과 수정 가능한 출력**이며 encoder/음성 LLM KV의 증분 실행은 아닙니다. 기존 공유 Q8·Q4 2/3회 프로필은 보존합니다.

## 동작과 반복 작업

- 최초 최소 입력 0.6초, 후속 최소 증가량 0.8초를 유지합니다. 새 입력과 추론 완료 때 판단하며, 마지막 실제 실행의 `end_frame`을 기준으로 합니다. 0.8초는 표시 주기가 아닙니다.
- 입력 수집은 계속하고 추론 하나·최신 부분 후보 하나·기존 유한 final 큐를 사용합니다. 후보는 PCM이 아닌 범위/reader만 갱신하며 실제 실행 직전 공통 락 아래 snapshot을 만듭니다. 완료 후 최신 입력을 다시 확인하고 동일 범위를 새 입력 없이 반복하지 않습니다.
- final이 대기하면 먼저 처리하고 같은 구간의 후보는 폐기합니다. 구간 끝 기본 0.2초만 합치며, 기존의 전체 예상 추론 비용을 near-final 대기에 더하지 않습니다.
- 접두부 재표시 억제를 재사용하고, 같은 길이 수정·삭제·revision 보호와 최근 확정 문맥 유지를 추가했습니다. 빈 partial은 이전 자막을 유지하되 실패·`empty_partial`을 남기고 새 입력에 다음 기회를 줍니다. final 성공 기준은 그대로입니다.
- 현재 제한 또는 82°C 이상/센서 결측이면 새 부분 요청을 보류합니다. 제한 해제·78°C 이하에서 재개하며 sticky 이력은 현재 제한으로 보지 않습니다. 기존 thermal-run·4GiB 주소 공간/실행시간 제한·단일 추론 잠금을 유지합니다. 팬·전압·클럭·OS·패키지를 변경하지 않았습니다.

기존 코드에도 부분 요청 병합·단일 추론·고정 text prefix KV·접두부 재표시 억제가 있었습니다. 이를 새 연산 절감으로 세지 않습니다. 새 정책은 완료 시 재판정과 lazy snapshot을 연결했으며, 후보 갱신 수가 실제 PCM 복사/추론 수로 늘어나지 않도록 했습니다. 전체 계산량은 기존 Q4 3회보다 늘 수 있습니다.

마지막 구간의 최종 반환/큐 대기 p95는 첫 구간보다 조금 늘었지만 구간별 단조 악화는 없었습니다. RSS 중앙값은1231.53→1243.03MiB로 약11.5MiB 늘었습니다. 입력/추론 큐의 폭증은 없었으나 결과/계측 이력을 계속 보관하는 현재 평가 세션을 무제한 운영 메모리 상한으로 해석하지 않습니다.

## 단계 진단과 선택 특징 캐시

새 연속 실행의 첫 구간에서 실제 사용한 PCM5개를 고정해 별도 연산 계측 bridge로30회 재현했습니다. 기존 bridge/엔진을 덮어쓰지 않았고 off0→off1→on0→on1→off2→off3 순서입니다. 모든 전사/token이 원래 호출과 같았습니다. 계측 ON의 평균 native 시간은 OFF보다5.04% 길었으며, ON 시간을 무계측 성능으로 사용하지 않습니다. 최고80.4°C·현재 제한0을 관측했습니다.

계측 ON10호출의 encoder graph 합계4.450초 중 합성곱3개의 행렬곱1.775초·합성곱 뒤 투영0.299초·IM2COL 약0.194초입니다. 명시적으로 이름 붙은 Transformer FFN up/down 행렬곱만1.051초이며 attention·정규화·나머지 연산도 남습니다. 그래프 밖 FFT/Mel 비용을 native `preprocess_s`로 오인하지 않습니다. 현재 native encoder 시간에는 실제 특징 추출이 포함되고 `preprocess_s`는 주로 입력 준비/shape 처리입니다.

작은 선택 실험은 **정규화 전 log-Mel 접두 프레임**으로 한정했습니다. 필터·창 함수·설정·반사 패딩을 포함한 실제400샘플 창이 같을 때만 재사용합니다. 끝 경계는 다시 계산하며 입력 전체 최대값 정규화와 모든 후단을 원래대로 실행합니다. 합성곱 출력·Transformer 전체·음성 LLM KV는 재사용하지 않습니다.

`verify`는 원래 전체 계산과 비트 단위로 비교하고 불일치 시 원래 출력으로 복귀합니다. `on`은 검증 뒤 비용 비교용입니다. 캐시가 추가하는 지속 저장은501 Mel프레임·690112바이트 이하, 추가 임시 공간1MiB 이하이며 segment/설정/모델/오류/취소/close 수명을 관리합니다. 기존 엔진의 고정 exported 함수에 새 preload만 연결하고 엔진/가중치 SHA를 검사합니다. 기본 프로필에는 연결하지 않습니다.

RP5 `c89e28e`의 실제 검사는 고정 PCM5개에 큰 음량의 tail/이동한 시작 범위를 더한7입력을 사용했습니다. 원래 계산7회와 verify14회에서 상태·전사·token이 같고, verify14회 모두 raw Mel 비트가 같았습니다. 별도30회 비용 비교(off20/on10)도 원래 전사/token을 유지했습니다.

| 5개 PCM 한 묶음 | OFF 앞2회 | ON 2회 | OFF 뒤2회 |
| --- | ---: | ---: | ---: |
| raw Mel 합계 | 17.87 / 17.97ms | 8.86 / 8.81ms | 18.34 / 18.27ms |
| 전체 native 합계 | 5.352 / 5.319초 | 5.401 / 5.638초 | 5.631 / 5.785초 |
| 계산한 Mel 프레임 | 1123 / 1123 | 346 / 346 | 1123 / 1123 |

ON 묶음마다777/1123프레임(69.19%)을 재사용했고 최대 추가 지속 메모리는690112바이트였습니다. **반복 특징 계산은 실제로 줄었지만**, 절약한 raw Mel은5호출당 약9ms로 전체 약5.5초의0.2% 미만입니다. 전체 native 시간은 열/실행 순서 변동보다 작은 이득을 입증하지 못했습니다. verify는 원래 전체 계산도 수행하므로 성능 수치에서 제외합니다. 검증 실행은 최고83.15°C/현재 제한8, 속도 실행은85.90°C/현재 제한6·8을 관측했으며 온도 통제 성능 실험으로 해석하지 않습니다.

같은6개의 연속 입력 OFF→ON→OFF에서도 최종15구간 PCM·전사/token·CER21.07%·빈 부분 실패1·드롭0을 유지했습니다.

계측 순서와 열 상태가 다르고 실제 부분 호출 수도 달라, 수십 ms 차이를 캐시의 개선으로 확정하지 않습니다. 호출 전체/연속 지연의 일관된 이득이 없어 **비활성 실험으로 보존**합니다. 이 캐시가 현재 발열/갱신 공백을 해결한다고 보지 않습니다. 스케줄러의 기본 프로필은 기존 prefix KV만 사용합니다.

## 실행·청취

측정 웹에서 **빠른 Q4 · 연속 수정 · 최종 우선**을 선택합니다. 취소 없는 비교용은 **빠른 Q4 · 연속 수정 자막**입니다. 저장 기록은 원음별 확인으로 한 음원 뒤 확정 자막을 읽고 **다음 음원**으로 넘길 수 있습니다. 원래 시간축의 연속 재생도 유지합니다. 기록 재생은 모델 재실행이 아닙니다.

```bash
  --profile configs/listener_continuous.toml \
  --profile configs/listener_continuous_priority.toml \
  --run results/optimization/opt3/continuous-q4-20261117-02/pilot-continuous \
  --run results/optimization/opt3/continuous-q4-20261117-02/full100-continuous
```

[RP5 단일 추론 명령](../../../docs/guides/qwen3_optimization.md#빠른-q4-연속-수정-후보), [청취·마이크 사용법](../../../docs/guides/listener.md#연속-수정-자막-후보)을 따릅니다. WAV 라이브와 마이크는 같은 스케줄러 경로를 사용하며, 실제 장비/브라우저 검증 범위를 아래와 구분합니다.
