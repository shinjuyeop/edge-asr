# RP5 Q8 + Hailo-8L 자막 연속성 실측

고정 100개 한국어 원음, 서울 자연발화 8개와 장시간 반복 입력을 Raspberry Pi 5에서 1배속으로 처리했다. [설정·실행별 지표·무결성 JSON](subtitle-continuity-20261123.json)

## 1. 추천 구성과 바로 실행할 명령

**추천은 Qwen3-ASR-0.6B Q8 + Hailo-8L Conv1·2·3/GELU, 생성 2·음성/Prefill 4스레드, 4초 ASR 구간과 짧은 쉼의 문맥을 결합한 T다.** 고정 100개에서 첫 본문 중앙값/p95는 2.96/7.13→2.52/4.13초, 5초 초과 최신 갱신 공백은 16→0회, 공통 원음 끝→확정 p95는 3.72→3.06초였다. 고정 CER는 450→460/3,848자(11.69→11.95%)다. 같은 서울 자연발화에서 정답 경계를 가른 단어의 오류와 정상 반복은 개선됐고 전체 오류는 269→270/2,129자였다.

[추천 청취 프로필](../../../configs/listener_hailo_continuity.toml)은 처음 0.45초, 이후 새 음성 0.65초와 첫 본문 생성 예상시간으로 부분 요청을 결정한다. ASR은 최대 4초, native VAD 최대 15초이고 한도 근처의 짧은 쉼을 분할점으로 쓴다. 실제 VAD 종료 후 500ms 이내의 재개에만 최대 200ms의 미소유 음성을 덧붙인다. 텍스트 prefix KV는 재사용하고 Decode와 나머지 인코더는 CPU에서 처리한다. 독립 검산 때 확정 토큰 보존을 가장 우선하는 경우의 5초 H는 아래 대조표와 같은 실행 ID로 다시 들을 수 있다.

터미널을 저장소 루트에서 열고 다음 명령을 실행한다. 이 RP5에 보존한 드라이버 4.23 임시 세션이 Hailo를 열고 청취가 끝나면 원래 상태로 돌린다. 포트가 사용 중이면 `--port`와 링크의 번호를 함께 바꾼다.

```bash
run=results/optimization/opt3/subtitle-continuity-20261123-01
.venv/bin/python scripts/edge_asr.py tools listen-qwen3 \
  --ssh rp5 --port 8776 \
  --ssh-device-session results/maintenance/hailo8l-q8-20261120-01/with-device-02.sh \
  --profile configs/listener_hailo_continuity.toml --profile configs/listener_hailo_cnn.toml \
  --manifest data/evaluation/longform-20261117-01/natural.jsonl \
  --run "$run/fixed-T" --run "$run/fixed-A" --run "$run/natural-T" --run "$run/natural-A"
```

## 4. 자막 멈춤과 문장 끊김의 확인된 원인

- 고정 A에서 4초를 넘긴 원음은 19개였다. 15개는 확정 요청에서 처음 본문이 나왔고 그 구간에는 앞선 부분 요청이 없었다. 13개는 종료가 가까워 부분 요청을 보류한 결정이 기록됐다. 하나의 원음에 처음 표시한 부분 요청까지 시계를 연결할 수 있는 80개의 적격→제출 p50/p95는 0.610/1.630초였고, 그중 다른 추론이 워커를 점유한 시간은 0.605/1.622초였다. 제출→추론 시작은 0.00019/0.00032초, 추론 시작→본문은 0.615/0.865초였다. 각 분포의 분위수는 서로 다른 원음을 가리킬 수 있다.
- 기준선의 가장 늦은 첫 글자 ‘분’은 원음 시작 뒤 8.872초에 나왔다. 제출 전 6.719초, 제출한 뒤 큐 1.536초, 추론 시작부터 0.617초였다. 입력은 계속 들어왔다. 별도 9원음에서는 앞선 두 확정이 1.373초와 0.551초씩 워커를 점유한 동안 새 부분 요청이 기다렸다. 0.45초부터 부분 요청을 허용해도 이 시간은 남는다.
- 같은 PCM에서 접두부를 다시 생성할 때 서버는 중복 토큰의 표시를 억제한다. 이 때문에 모델이 실행 중이어도 새로운 글자가 없을 수 있다. 완성된 부분을 확정으로 교체할 때도 글자가 달라질 수 있다. 고정 A는 252자를 철회했다. 후보 교체는 아직 실행되지 않은 입력 범위의 교체도 포함한다. 실제 계산 낭비는 취소 시간과 의미 갱신 없이 끝난 부분 요청의 시간으로 따로 계산했다.
- 저전압·열 보호, VAD 종료, 최대 길이 절단은 다른 사건이다. 원음 및 소유 PCM 해시, VAD/스케줄러 결정, 전체 입력 프레임, 실제 워커 시작/종료를 대조했다. OS의 열 제한 플래그가 나타난 구간에서도 1.5GHz 상한 부근 실클럭이 관측됐다. 열만으로 개별 공백의 원인을 설명할 수 없다.
- 기존 개인 녹음은 11월 13일 WAV 세 개였다. 20.2초 녹음에는 VAD 구간이 없고, 50.5초 녹음에는 7.612초부터의 부분 “흠.”이 확정 “응.”으로 바뀐 기록과 14.556–15.028초의 구두점 단독 확정이 있다. 19초 녹음은 사용자가 중단한 실행이다. 개인 녹음에 채점 정답이나 당시 브라우저 화면은 없다. 저장 이벤트로 재구성한 결과와 이번에 실제 Chrome에서 다시 관찰한 화면을 구분했다.

### 다음 확정 PCM의 선행 인코딩

기준 A의 100개 원음에서 확정 210회가 사용한 음성 인코더 경과 합은 101.71초였다. 그중 CNN 동기·재배열은 2.73초였다. 접수된 다음 확정 PCM과 이전 요청의 decode 시간이 일부 겹치는 경우는 89회였고, 이전 첫 토큰이 나온 뒤부터 완료 전까지 제출된 확정은 38회였다. 저장된 시각에서 계산한 교집합은 전체 인코더를 이상적으로 병렬 처리할 때 최대 19.90초, CNN 단계만 겹치면 0.61초였다. 이는 CPU·메모리 경합을 빼고 계산한 상한이다.

후보는 이미 큐에 접수된 맨 앞 확정 PCM 한 개의 사본만 보유한다. 직전 요청이 CPU에서 토큰을 생성하는 동안 기존 mtmd_context로 Mel·CNN HEF·나머지 음성 인코더를 수행한다. LLM prefill·decode·KV는 기존 직렬 context가 처리한다. 다음 요청의 mtmd 호출 전 백그라운드 작업을 회수하고 job ID, PCM 길이·전체 바이트 및 임베딩 shape가 맞을 때만 재사용한다. 작업 생성 실패도 최종 FIFO에 기록한 뒤 원래 경로에서 실행한다. 인코더 예외나 불일치는 사유를 기록한 뒤 동기 재인코딩하며, 종료 시 비동기 작업을 먼저 회수한다. ## 11. 돌아와서 확인하는 방법

1. 위 명령으로 청취 화면을 연다. **기록 재생**에서 같은 원음을 A와 추천 실행으로 번갈아 듣는다. 발행 시각을 그대로 따라가려면 **연속 재생**을 고른다. 원음별 확인은 늦은 확정까지 보여준 뒤 다음 원음을 누를 때까지 기다린다.
2. **라이브**에서 추천 프로필과 개별 원음 또는 앞 6개를 선택한다. **RP5 실행 준비 → 시작** 후 실행 조건의 스레드·스케줄러와 워밍업 Hailo 호출을 확인한다. 저장된 결과 선택은 라이브 실행을 시작하지 않는다.
3. 실물 마이크를 연결했을 때만 **마이크**에서 해당 입력 장치와 같은 프로필을 선택해 짧게 말하고 중지한다. 두 번 반복한 구절과 짧은 쉼을 예로 들어, 주 자막과 전체 확정 이력을 함께 확인한다.
4. 이전 속도 기준은 같은 서버에서 **Q8 + Hailo-8L CNN · 5초 기준**을 고른다. CPU Q8 장치 대조는 같은 청취 명령의 프로필에 `--profile configs/listener.toml`을 추가해 선택한다.
