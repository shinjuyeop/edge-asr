# Qwen Q8의 Conv1·2·3을 하나의 Hailo-8L HEF로 실행한 결과

2026년 11월 23일 · RP5 실측 · 실행 ID `hailo-cnn-stack-20261123-01` · 추론 소스 `f59e551`. [수치·모델 및 원시 기록 해시](hailo-cnn-stack-20261123.json)

**Conv1·2·3과 원래 GELU 세 개를 묶어 실제 NPU 가속을 확인했다.** CPU 대비 210개 확정 추론이 607.67→508.69초(16.29% 감소), 첫 자막 중앙값이 7.48→2.92초였다. 여유 시간에 부분 요청이 60→132회로 늘어 전체 요청의 추론 합은 693.89→671.19초(3.27% 감소)였다.

**정확도를 지키는 NPU 경로로는 Conv2 단독을 권한다.** 같은 3,848자에서 CPU 419개, Conv2 단독 395개, 묶음 450개의 오류가 발생했다. 묶음은 Conv2보다 확정 추론이 9.34% 빨랐지만 오류가 55개 늘었다. 세 층을 함께 실행하는 기능은 지연 실험용으로 보존하고 기본은 Q8 CPU로 유지한다. 다음 NPU 실험은 Conv1·2의 양자화 오차를 줄인 뒤 독립 음성과 같은 100개에서 재검증하는 것이 우선이다. CPU에서는 여전히 가장 큰 비용인 토큰 decode를 우선한다. 이번 묶음은 고정 100개에서 정확도 유지 조건을 충족하지 못해 긴 자연발화·낭독 재생으로 확대하지 않았다.

## 한국어 원음 100개 1배속 대조

세 경로 모두 891.145초의 동일 원음·VAD·가중치·설정으로 재생했다. PCM 해시로 대조한 확정 구간은 210개, 정답은 3,848자다. 각 원음 시작부터 그 원음에 단독 귀속되는 첫 서버 자막의 중앙값과 p95, 더 최신 음성을 반영한 표시 사이의 공백 p95, 구간 끝에서 확정 발행까지의 p95를 구분했다. 브라우저 화면 렌더 시간은 측정 범위 밖이다.

묶음의 동일 확정 native 시간은 CPU 대비 16.29%, Conv2 단독 대비 9.34% 짧았다. 부분 요청을 포함한 전체 추론 합은 스케줄러가 선택한 호출 수도 반영한다. 입력은 1배속이므로 누적 계산 시간과 재생의 시작→배출 시간은 별도 지표다. 세 경로의 확정 생성 토큰 합은 CPU 3,552개, Conv2 3,539개, 묶음 3,540개였다.

묶음에서 첫 자막 p95에 해당하는 실제 음원은 `zeroth-121_003_0845`였다. 이 음원은 시작→요청 제출 5.60초, 큐 대기 0.002초, 실행 시작→첫 표시 1.64초가 걸렸다. 이 분해는 해당 음원 한 건의 기록이다. 전체 첫 표시 100개 가운데 부분 요청에서 처음 보인 음원은 80개였다.

## 어떤 연산을 묶었나

Qwen3-ASR-0.6B Q8의 오디오 GGUF에서 세 3×3 합성곱의 가중치와 bias를 추출했다. 각 층은 stride 2이고 원래 `ggml_gelu_erf`를 사용한다. Hailo에 Mel 100프레임 청크를 보내고 세 번째 GELU 뒤의 480×16×13 텐서를 돌려받는다. Conv1과 Conv2의 큰 중간 텐서는 장치 안에서 다음 층으로 이어진다. CNN 출력 투영, Encoder Transformer 18층, 최종 임베딩, LLM prefill·decode와 KV 관리는 기존 CPU 경로에서 실행한다. [ONNX 추출](../../../native/gguf/export_audio_boundaries.py) · [GGML·HailoRT 연결](../../../native/gguf/hailo_conv.cpp)

| 청크 하나 | 입력 → Conv1 → Conv2 → Conv3 |
| --- | --- |
| 높이 × 너비 × 채널 | 128×100×1 → 64×50×480 → 32×25×480 → 16×13×480 |
| 장치 입출력 | UINT8 입력 12,800바이트, 출력 99,840바이트. 5초 진단의 6청크에서 논리적 입출력은 76,800 / 599,040바이트 |
| Conv2 단독과의 차이 | 같은 6청크에서 Conv2 단독의 논리적 입출력은 9,216,000 / 2,304,000바이트. 두 경로 모두 GGML에는 FP32를 반환 |

**지난번에 막힌 GELU를 어떻게 통과했나.** DFC 3.34.0에서 기존 곱셈 순서로 내보낸 대조 그래프는 세 `Erf`에서 모두 파싱이 실패했다. 이번 그래프는 원래 식의 곱셈 순서를 `(x * (1 + erf(x / sqrt(2)))) * 0.5`로 썼다. 계수와 가중치는 동일하다. ONNX Runtime에서 두 FP32 그래프는 1·3·5초 실입력 모두 최대 절대 차이 0이었다. DFC의 중간 그래프에서 세 Conv 모두 `params.activation = gelu`를 확인했다. INT8 장치의 출력 오차는 아래에 따로 측정했다.

Host x86-64의 Python 3.10·DFC 3.34.0에서 Hailo-8L을 대상으로 보정·컴파일했다. 보정에는 KSS 개별 원음 49개에서 캡처한 실제 Mel 청크 98개를 사용했다. 평가 100개와 원음 ID·파일 SHA-256 교집합은 0이다. 최적화 레벨 0, 압축 레벨 0, 배치 1이다. RP5의 `hailortcli parse-hef`에서 단일 네트워크·단일 컨텍스트와 UINT8 NHWC 입력·FCR 출력을 확인했다. 장치 실행 기록에서 CPU 기준의 Conv1·2·3 im2col 세 개가 모두 사라지고, 같은 Mel을 받는 `after_conv_blocks` Hailo 노드 하나와 CPU 투영이 남았다.

## 장치와 대조 조건

- RP5 aarch64, Linux 6.12.62+rpt-rpi-2712. Hailo-8L은 `0001:01:00.0 [1e60:2864]`, PCIe 5.0 GT/s ×1이다. 부팅용 Transcend TS256GMTE110S는 USB 480 Mbit/s로 연결돼 있다. HailoRT·드라이버·펌웨어는 4.23.0이다.
- Qwen3-ASR-0.6B Q8_0 GGUF·mmproj, 고정 llama.cpp `7d7f028`, 기존 Q8 bridge, 생성 2스레드·음성/prefill 3스레드와 고정 text prefix KV를 사용했다. 같은 가중치·실행기에서 선택 preload와 HEF만 바꿨다. [공통 설정](../../../configs/gguf_realtime.toml)
- 기존 장비의 냉각을 사용했다. 성능 실험은 CPU 주파수 정책을 1.50 GHz로 맞추고 2초 간격 3회 연속 71.5°C 이하일 때 시작했다. 펌웨어 열 보호는 동작하며 입력 중 실제 클럭과 제한 비트를 기록했다. PCM 순서는 CPU → Conv2 → 묶음, 100개 1배속 순서는 묶음 → Conv2 → CPU였다. 각 경로의 100개 스트리밍은 한 번씩 측정했다. 세 경로에서 SSH 상태를 확인했고, CPU 재생 중 별도 프로세스가 후속 진단용 Python 모듈을 한 번 import했다(약 1.3초).
- 같은 한국어 원음 100개(FLEURS 40, Zeroth 60)를 같은 순서로 1배속 재생했다. Silero VAD 0.3, 구간 최대 5초, 첫 부분 요청 기준 0.6초, 새 음성 최소 1초, headroom 정책·열에 따른 부분 호출 조절·확정 우선 취소·토큰 표시를 사용했다. 채점은 `ko_cer_v1`이다. 선행 고정 4초 갱신 실험의 수치를 이번 대조에 합치지 않았다.

오차는 같은 RP5 CPU 텐서를 기준으로 한 상대 L2다. 묶음과 CPU의 Mel 입력은 세 길이 모두 비트 단위로 같았다. 실제 CNN 출력의 최대 절대 오차는 1·3·5초에서 각각 0.429, 0.463, 0.463으로 측정됐다. 별도 Host DFC 정수 모의 실행의 5초 CNN 출력은 CPU 대비 28.37%, 실제 장치 출력 대비 10.20% 차이가 났다. 전사·속도 판정에는 실제 RP5 결과를 사용했다.

5초 PCM의 층별 오차를 추적하기 위해 Host에서 동일 양자화 HAR의 세 GELU 출력을 읽고 층별 scale·zero point로 역양자화했다. CPU 기준 상대 L2는 Conv1 뒤 15.95%, Conv2 뒤 28.56%, Conv3 뒤 28.37%였다. FP32 DFC에서는 각각 0.034%, 0.184%, 0.235%였다. 조사한 세 길이에서 CPU의 각 층 출력 중 해당 UINT8 표현 범위를 벗어난 값은 0개였다. 초기 두 층에서 이미 오차가 커져 첫 후속 대상은 Conv1·2의 보정과 정밀도다. 이 층별 값은 Host 모의 결과이고, 단일 HEF가 장치에서 외부로 내보낸 값은 세 번째 GELU 출력이다.

## 재현과 검증

1. Host에서 별도 경로에 같은 Q8 mmproj를 지정해 `native/gguf/export_audio_boundaries.py --audio-gguf <mmproj> --tokens 26 --output <새 경로>`를 실행한다. `cnn_stack.onnx`를 사용한다. GGUF·ONNX는 기존 변환 환경, Hailo 컴파일은 별도 Python 3.10 환경을 사용했다.
2. DFC의 `ClientRunner(hw_arch="hailo8l")`에서 `translate_onnx_model(..., net_name="qwen_cnn_stack")`을 호출한다. 공식 모델 스크립트 `model_optimization_flavor(optimization_level=0, compression_level=0, batch_size=1)`를 적용했다. 각 캡처의 `inp_chunks`를 FP32 `[N,128,100,1]`로 이어 `optimize(samples)`하고 `compile()`의 바이트를 HEF로 저장했다. 이번 HEF의 SHA-256은 `2eaa3e44f082b6b91465cc2a3c1cdea8bc3c18b309ca508d223b7d0312b04235`다.
3. RP5에서 HailoRT 4.23.0으로 선택 라이브러리를 빌드한다. 기존 평가 자식에 `LD_PRELOAD=<hybrid.so 절대 경로>`와 `EDGE_ASR_HAILO_CNN_STACK_HEF=<HEF 절대 경로>`를 주고 동일한 `benchmark-qwen3` 또는 `replay-qwen3`를 호출한다. Conv2 대조는 기존 무편향 `conv2_linear.hef`를 선택하고 CPU 대조는 preload 없이 실행한다. 각 확정 호출에서 선택된 Hailo 콜백의 실제 실행을 검증했다.
