2026-11-11. **다음 개발 구성은 Q8·3T입니다.** 같은100개에서 CER11.12%를 유지하며 최종 구간 처리 합계8.9%·전체 추론 합계8.3%가 줄었고 첫 표시 p95는5.20→4.56초였습니다. 기존 `num_threads`만 바꿨으며 새 어댑터·추론 엔진·KV 정책은 추가하지 않았습니다. ## 조건

RP5 실제 추론 소스는 `306f4a6`입니다. 기존 Q8 text/audio·토큰 bridge·같은 Python 환경·greedy·context512/출력128·KV K/V f16·호출별 KV 초기화를 유지했습니다. 바꾼 값은 새 실행 경로의 TOML `model.num_threads`뿐입니다. 현재 bridge는 생성용 `n_threads`·prefill용 `n_threads_batch`·오디오 `ap.n_threads`에 같은 값을 전달합니다. [공식 llama API](https://raw.githubusercontent.com/ggml-org/llama.cpp/7d7f0287530bc8981690f361d8c1627dbae1c99a/include/llama.h), [실제 bridge](../../../native/gguf/bridge.cpp).

Q8·VAD0.3·rms26-floor80(ASR 원음 보존)·VAD/ASR5초·문맥0·첫 부분1초/이후4초·토큰 표시·접두부 재표시 보류·입력100ms/10청크·최종 FIFO4/부분 대기1·EOF30초·첫 추론1회/워밍업3회·4GiB·온도 대기 없는 운영 조건을 고정했습니다. 입력은 추가 무음0초·1배속·파일 경계 초기화 없이 계속 받았습니다.

최종210개 구간 좌표·PCM·전사·토큰 ID가 모두 일치했습니다. 치환195·삭제157·삽입76개도 같았습니다. 원음 경계 중첩1개로 발화별 corpus CER는null이며 정답3848자 전체를 연결 CER에 포함했습니다. 전체 입력 프레임도 같습니다.

사전100개 개발 조건13개를 모두 통과했습니다. 같은 최종 구간 합계는50.84초(8.92%)·전체 추론 합계는59.70초(8.26%) 줄었습니다. 최종 음성 처리/prefill은약22.7% 줄고 decode는약11.2% 늘었지만 전체 비용은 감소했습니다.3T가 모든 연산을 더 빠르게 만든 것은 아닙니다. KV 초기화 합계는 최종210개에서1.50→1.53초이며 재사용 최적화는 이번에 적용하지 않았습니다.

부분 호출은6회 늘었습니다. 최신 대기 요청의 교체 여부가 달라질 수 있어 같은 최종 호출 비용을 따로 비교했습니다. 전체 문자 철회159→164자는 실제 내용 변경을 포함하며 부분 정답 정확도 개선을 뜻하지 않습니다. 접두부 재표시 철회는 양쪽0입니다. 관측 RSS 증가는0.95MiB로 허용32MiB 이내였습니다.3T의 최고 온도는 더 높았으며 저지연 실사용·최종 장시간 안정성 통과를 뜻하지 않습니다.

첫 표시는 원음 시작→비어 있지 않은 텍스트 이벤트 발행이며 실제 화면 시각이 아닙니다. 파일 끝 기준 반환은 원음 입력 끝→마지막으로 겹치는 최종 호출 반환이며 단어 음향 끝과 다릅니다. engine TTFT는 native 호출 시작→첫 비EOG 토큰이고 음성 처리/prefill 포함·큐/Python 표시 제외입니다. 시간 합계는 부분 재전사를 포함하며 batch RTF나1배속 전체 경과 시간과 구분합니다.

4자 표시는 한글·영숫자 기준이며 자기 최종 전사의4자 보존 시각과는 다른 지표입니다. 첫 표시·완성 문자열·파일 끝 반환 모두 공통 원음100개를 기준으로 비교했습니다.

양 끝2T를 두었지만 열·실행 순서 영향을 완전히 제거한 반복 통계는 아닙니다. 첫2T 파일럿은 현재 제한이0이었고 후속 파일럿에서는0·6·8을 관측했습니다.100개 비교의 온도·실제 클럭·제한도 위 결과와 함께 보존합니다. 한국어 전반·독립 평가·자연 대화·마이크 성능으로 일반화하지 않습니다.
