# OPT-0 첫 단독 기준선·56ms 오류 재현 — 2026-11-09

Qwen3-ASR-0.6B INT8의 단독 실행 경로를 분석하고 RP5에서 작은 반복 기준선과 기존 실패를 재현했습니다. **모델·추론 정책 최적화 전의 출발 관측**입니다. [사전 계획과 조건 변경](../../../docs/research/opt0_pilot.md), [기계 판독 요약](opt0-pilot-20261109.json).

## 실행과 판정 범위

최종 운영 실행의 소스는 `5c8c9f15fc8079ef564db954d4b6fe4a2c8d3def`입니다. 기존 별도 `.venv-qwen3-onnx-20261106-01`, sherpa-onnx 2.0.1/native ORT 1.28.2, 기존 자산 SHA-256, 한국어·2T·max_total_len 512·max_new_tokens 128을 사용했습니다. KSS 개발 50개를 길이/ID 순으로 정렬한 6개(고유 19.7790625초)를 선택했습니다. 첫 추론 1회·추가 워밍업 3회 후 5라운드로 각 파일을 5회 처리하고 라운드 시작을 회전했습니다.

초기 75°C 중단 정책 아래 연속 실행은 scored 8/30회 후 중단됐습니다. 냉각 후 독립 실행은 한 기준선 6/6회와 원 발화 전체 대조를 완료했습니다. 다음 냉각 대기 중 사용자가 온도와 무관하게 진행하도록 요청해 driver·자식을 종료하고 신규 운영 ID로 전환했습니다. 이 과정의 중단·미완료·취소 기록은 보존했습니다.

최종 ID는 `results/optimization/opt0/opt0-operational-20261109-01/`입니다. `operational --skip-temperature-admission`으로 시작 온도 대기와 온도/열 감속에 따른 중단을 생략했습니다. 기본 펌웨어 보호·4GiB·외부 300초·전압/필수 센서 검사는 유지했습니다. **온도/클럭을 고정한 통제 실험이 아니며**, 같은 조건의 후속 비교에서 실제 열 상태를 함께 확인해야 합니다.

## 56ms 오류

원 FLEURS 7.44초 발화와 두 구간 PCM의 해시를 검증했습니다. 56ms는 896프레임이며 기존 실패와 정확히 같은 PCM입니다. 다음은 최종 운영 진단의 순서와 결과입니다.

| 입력 조건 | API 결과 | 호출 시간(초) | native 반복 경고 |
| --- | --- | --- | --- |
| tail-first | 실패 | 5.210 | 65토큰에서 발생 |
| tail-repeat | 실패 | 5.148 | 65토큰에서 발생 |
| preceding-5s | 반환 성공 | 3.652 | 없음 |
| tail-after-prefix | 실패 | 5.187 | 65토큰에서 발생 |
| tail-context200ms | 반환 성공 | 0.700 | 없음 |
| tail-context500ms | 반환 성공 | 0.651 | 없음 |
| tail-context1000ms | 반환 성공 | 0.797 | 없음 |
| full-utterance | 반환 성공 | 4.394 | 없음 |

56ms만 첫 호출·재호출·앞 5초 직후 호출하면 모두 같은 반복 경고로 실패했습니다. 현재 운영 검사에서 약 5.15~5.21초를 썼고, 초기 53°C 입장 검사에서도 동일 PCM이 약 5.0초 후 같은 경고를 냈습니다. 입력 예산은 512 안에 들어가고 native 반복 탐지가 65토큰에서 작동했습니다. native가 반복 꼬리를 잘라 반환한 토큰은 1개이므로 반환 토큰 수만 보고 생성 비용을 해석하면 안 됩니다. 어댑터는 stderr 경고를 검사해 이를 실패로 보존했습니다.

앞 문맥 200/500/1000ms를 붙이면 경고는 사라졌지만, 200/500ms 조건에서는 원 발화 정답에 없는 “시스템” 출력이 관측됐습니다. 문맥 추가를 품질 해결책으로 채택할 근거는 아직 없습니다. 원 발화 전체는 별도 53°C 입장 대조에서 4.312초, 최종 운영 진단에서 4.394초에 경고 없이 반환했습니다.

이는 한 PCM의 재현 사례입니다. 모든 짧은 입력이 실패한다거나 원인이 입력 길이 하나라고 일반화하지 않습니다. 구간 정답 시각 주석이 없으므로 진단 CER는 전부 null입니다. 진단 실행 exit 0은 8개 호출·기록을 끝냈다는 뜻이며 모델 API 결과는 성공 5·실패 3입니다. `worker.status=completed_with_model_failures`와 원시 경고·전사는 그대로 남습니다.

## 실행 구조와 다음 분석

공식 v2.0.1 소스와 현재 어댑터에서 `create_stream → accept_waveform(특징) → decode_stream(Conv·Encoder·prefill·token decode) → 출력 검사`를 확인했습니다. 매 전사의 KV cache는 새로 만들고 한 전사 내부의 토큰 단계에서 갱신합니다. [소스 근거와 흐름도](../../../docs/research/opt0_pilot.md#실행-경로-분석).

encoder/prefill/decode별 시간과 TTFT는 현재 경계에서 분리할 수 없어 null입니다. 다음 OPT-1은 실제 native 구간별 시간·호출/생성 토큰 수를 계측하고, 일반 발화와 56ms 반복 사례를 함께 비교합니다. 짧은 잔여 구간의 수집/문맥/확정 정책도 별도 후보로 검증합니다. 아직 짧은 구간 자동 삭제, 토큰 상한 변경, GGUF 엔진 또는 Qwen 부분 자막을 적용하지 않았습니다.
