# Q8 확정 생성의 토큰 후보 묶음 검증 — 2026-11-19

이전 부분 전사의 토큰을 후보로 두고 현재 Q8이 묶어서 검증하는 선택 native 경로를 구현했다. **RP5 고정 PCM 8개에서 4개 묶음의 decode 합계는 15.55~17.32%, 호출 전체 native 합계는 7.25~8.77% 감소했다.** 그러나 한 구간에 마침표가 추가돼 사전 원시 전사/토큰 동등성 조건에 미달했다. 2개 묶음은 출력이 모두 같았지만 비용 감소 조건에 미달했다. **공유 Q8와 현재 가변 스트리밍 설정은 유지한다.** [전체 계측·명령·해시](token-draft-20261119.json).

이번 결과는 **고정 PCM의 호출 비용 진단**이다. 새 구성의 1배속 스트리밍·전체 CER·첫 자막·최신 입력 반영 공백·확정 지연은 측정하지 않았다. 사전 선별을 통과하지 않아 실시간 어댑터의 자동 후보 전달도 연결하지 않았다. 전체 시스템이 위 비율만큼 빨라졌다는 뜻이 아니다.

## 선택 근거

직전 `q8-cache-headroom-20261119-01`의 창 없는 Q8 기준 기록에서 확정 233호출의 합계는 401.700초, 그중 토큰 decode는 183.846초(45.77%)였다. 각 확정 전에 실제 끝난 마지막 부분 전사의 token ID와 최종 접두부를 비교하면 714/2,987토큰(23.90%)이 일치했다. 성공한 부분만 보면 575토큰이며 나머지는 협력적으로 취소된 부분의 원시 토큰이다. 이미 끝난 결과로 계산한 가능성 분석이며 실제 미래 출력이나 절감 시간을 미리 아는 정책으로 사용하지 않는다.

음성 창 캐시와 달리 전체 음성 encoder·prefill·최종 Q8 정밀도·5초 확정은 그대로다. 이전 부분 문구를 다시 한 토큰씩 생성하는 비용을 줄일 수 있는지를 조사했다. 별도 Q4/draft 모델은 로드하지 않아 이중 모델의 메모리·동시 실행 비용을 추가하지 않았다.

## 구현 범위

- 기존 `native/gguf/bridge.cpp`를 확장하고 상태 정책만 `token_draft.h`로 분리했다. 기존 `benchmark.py`의 요청 준비 hook으로 다음 한 호출에 후보를 공급한다. 모델·엔진·환경·공유 설정은 유지하고 bridge만 별도 경로에 빌드했다.
- 첫 토큰은 원래 Q8의 전체 음성 prefill 뒤 선택한다. 확정된 토큰과 뒤의 후보를 같은 causal batch로 평가하고, 각 위치의 Q8 greedy 결과가 후보와 일치한 경우에만 해당 KV/logits를 소비한다. 후보를 그대로 출력하거나 확정하지 않는다.
- 불일치 뒤 KV를 제거하고 Q8이 선택한 토큰부터 원래 생성으로 복귀한다. EOG·출력 상한·반복·UTF-8 검사와 token callback 순서를 유지한다. setter는 후보를 한 번만 소비하며 잘못된 token ID/길이/설정은 거부하고 대기 후보도 지운다.
- 묶음 계산은 직렬 계산과 부동소수 연산 경로가 달라질 가능성이 있으므로 알고리즘상 검증과 실제 원시 출력 동등성을 구분한다. 이번 출력 차이의 구체적 연산/수치 원인은 아직 분리하지 않았다.

설계 확인은 [고정 llama.cpp 예제](https://github.com/ggml-org/llama.cpp/blob/7d7f0287530bc8981690f361d8c1627dbae1c99a/examples/speculative-simple/speculative-simple.cpp)와 [speculative sampling 논문](https://arxiv.org/abs/2302.01318)을 참고했다. 다른 장비·모델에서의 속도 향상을 RP5 예상값으로 사용하지 않는다. 이번 구현은 기존 greedy sampler와 이미 생성한 부분 후보를 사용하는 제한된 경로다.

## 같은 PCM의 비용

자연발화와 낭독에서 각각 성공 부분의 긴 일치·취소된 부분·후보 없음·짧은/없는 일치의 4사례를 골랐다. 최종 PCM의 float 해시와 과거 전사를 검증한 8개이며, 후보는 해당 최종 호출 시작 전에 실제 생성된 부분 token ID다. 일부 과거 부분 입력은 VAD가 소급 확정한 음성 끝보다 길지만, 당시 이미 도착한 음성만 사용했다. 음성 KV를 재사용하지 않는다. 선정 사례의 원음은 `natural-000/001/002/004`, `reading-000/001/019/020` 구간이다.

각 조건에 warmup 3회 뒤 8호출을 수행했다. 직렬 앞→묶음2→묶음4→직렬 뒤 순서이며 같은 Q8·2/3T·text prefix KV·bridge·PCM 순서다. 아래 합계는 warmup을 제외한다. 후보 준비 hook·WAV I/O는 기존 benchmark 호출 타이머 밖이고, native 합계는 음성 처리·prefill·생성 전체다. 첫 생성 토큰은 native 시작 기준이며 실제 첫 자막/최신 음성 갱신 간격이 아니다.

2개 묶음은 native 합계 2.63~4.23%, decode 합계 6.03~8.00% 감소했다. 추가 평가 토큰 없이 후보 20/20개를 수락했다. 4개 묶음은 후보 30/31개를 수락하고 1개를 버렸다. 4개 묶음의 평가 160토큰은 원래 출력 158개에 추가 마침표 1개와 버린 후보 1개를 포함한다. 출력 길이가 달라진 비용까지 포함한 관측값이다.

원시 동등성·양쪽 직렬 대조 대비 native 3% 이상 및 decode 10% 이상 감소라는 사전 조건에서, 2개 묶음은 비용 기준·4개 묶음은 동등성 기준에 미달했다. 8개는 사례를 의도적으로 선정한 작은 표본이고, 전체 233구간이나 1배속 처리량의 대표 평균으로 환산하지 않는다. 묶음 크기8은 Host 상태 검사 범위이며 RP5 성능은 미측정이다.

## 원시 차이와 분리 재현

`natural-002`의 원래 최종 전사는 `어떤 스님들은 저희 같은 경우는 한 두 분 정도가`이며, 4개 묶음에서 마지막에 마침표 token ID13이 하나 추가됐다. 앞 14토큰은 그대로다. 후보는 앞의 실제 부분 5토큰뿐이고 묶음 검증은 앞부분에서 이미 끝났다. 이 차이를 후보의 마침표를 그대로 복사한 결과로 해석하지 않는다.

같은 PCM을 별도 한 프로세스에서 3회 warmup 뒤 8회 검사했다. 4개 묶음 3회 모두 같은 마침표가 추가됐으며, 그중 한 번은 text prefix KV를 먼저 완전히 초기화했다. 직렬 앞/뒤·2개 묶음·setter를 호출하지 않은 다음 호출·잘못된 setter 뒤 호출은 모두 원래 전사/토큰으로 돌아왔다. 이전 후보의 잔류나 warm prefix KV 재사용만으로 설명되는 현상은 아니었다. 정확한 수치 원인을 확인한 것은 아니다.

문장부호/공백을 제거하는 `ko_cer_v1` 정규화 뒤에는 이번 8개 출력이 모두 기존과 같다. **이것을 전체 CER 유지나 정확도 악화로 판정하지 않는다.** 잘린 최종 PCM에는 독립 구간 정답이 없으며, 더 많은 발화에서 차이가 문장부호에만 국한되는지도 아직 모른다. 별도 사례 반복은 수명/출력 진단이며 성능 평균에 섞지 않았다.

## 판정과 다음 검증

실시간 연결은 보류한다. 큰 비용 절감 후보가 생겼지만 raw 토큰 동등성을 보장하는 경로로 채택할 근거는 부족하다. 기존 1배속 Q8 가변 설정과 그 실측값은 그대로 유지한다.

다음 유력 검증은 **같은 233개 확정 PCM에서 4개 묶음의 출력 차이가 문장부호에만 한정되는지와 Q8 greedy logits/연산 경로의 차이를 분리하는 것**이다. 그 결과를 바탕으로 동등성 보완 또는 허용할 정확도 계약을 명시한 후, 1배속 스트리밍의 갱신 공백·확정 지연·CER를 검증한다. 이번에는 전체 PCM 확대·모델 변환·최종 분할 변경을 추가 실행하지 않았다.
