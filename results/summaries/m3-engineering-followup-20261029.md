# M3 후속: 지속 음성 경로 준비와 냉각 기록 확인

2026-10-29. Host main 기준 커밋 `7485367` 이후의 추가 구현이다. **Host 구현·모의 검사 완료, 새 RP5 검증과 소스 동기화는 연결 실패로 미완료**다. 기존 M1/M2/M3 실측·원본 데이터·모델·RP5 환경을 변경하지 않았다.

## 완료한 작업

- 기존 k2 Silero v4 가중치의 확률·h/c 상태만 유지하는 선택적 Python ORT 경로를 추가했다. 실제 PCM은 기존 유한 링버퍼가 보관한다. 기본 native 경로와 30초 안전 예산은 유지한다. 기존 네이티브 객체에서 예산 해제는 거부한다.
- `probe-annotated-vad --backend bounded`에서 로딩/호출 자원·공통 PCM·예비 주석 채점을 재사용하고 백엔드와 런타임을 구분한다. 기존 native 집계기에 새 백엔드를 합치지 않는다. 새 모델 다운로드·패키지 설치·Hybrid 실행은 하지 않았다.
- `inspect-cooling`에서 기존 기록 해시·과거/현재 제한·소프트웨어 중단·모든 노출 팬 센서·클럭을 읽기만 한다. 값이 없을 때 0으로 채우지 않는다.
- 직접 판단하기 어려운 청취 메모 5개는 모두 `판단 어려움`으로 유지했다. 기존 배포 예비 주석, endpoint null, 정답 승격 여부를 변경하지 않았다.

## Host 검증

Python 3.11.14에서 전체 **184개 테스트 통과**. Ruff 정적 검사·포맷, 문서 경로·CLI 지연 import, 배포 스크립트 구문, M1 원본 SHA 검사를 통과했다. wheel 빌드와 wheel 내부 25개 명령의 지연 import도 확인했다. 실제 신경망 가중치를 사용한 검사는 아니다. [검증 요약 JSON](m3-engineering-followup-20261029.json).

지속 확률 mock 4,096창(오디오 시간축 131.072초)에서 내부 파형 축적 없이 상태와 좌표만 유지했다. 35초+137프레임 합성 PCM에서 3/5/8초 소유 구간 상한·최대 200ms 문맥·유한 버퍼·소유 PCM 바이트 일치·강제 구간 사이 reset 부재를 확인했다. 이 길이는 합성 입력의 길이이며 실행 벽시계 시간·실제 음성 정확도가 아니다.

기존 VAD 160개 원시 결과를 재채점해 저장 요약의 모든 계산 필드가 동일했다. 기존 Zipformer paced_stream 50개도 요약 및 개별 점수가 동일했다. 이전 보고서가 별도로 덧붙인 설명 필드는 비교 대상에서 제외했으며 파일 자체는 수정하지 않았다.

## 기존 냉각 기록의 재분석

원시 `execution.json`·`thermal.jsonl`을 수정하지 않고 [새 JSON](m3-cooling-audit-20261029.json)에 해시와 재분석을 보존했다.

| 기존 실행 | 감시 표본 | 감시 최고 온도 | 팬 관측 | 현재 제한/새 이력 | 기존 판정 |
| --- | --- | --- | --- | --- | --- |
| Zipformer 2T | 15 | 76.0°C | 시작 3,152 → 중단 표본 8,688RPM | 관측 표본 0 / 새 비트 0 | 75°C 소프트웨어 기준에서 중단 |
| SenseVoice 1T | 480 | 73.8°C | 시작 3,098RPM, 최대 10,200RPM | 관측 표본 0 / 새 비트 0 | 당시 단독 실행 완료 |

Zipformer는 부하 전 표본으로부터 약 14.09초 후 중단 기준 위의 표본을 관측했고, 정지 직후 별도 표본은 77.1°C였다. 기존 `0xe0000`은 시작 전부터 있던 제한 이력이다. 팬이 당시 회전했고 RPM이 증가했다는 근거가 있으므로 단순한 팬 미동작을 원인으로 확정할 수 없다. 방열판 접촉·통풍·실내 온도는 미확인이다. 이 기록은 현재 냉각 합격 또는 동시 ASR 부하 합격이 아니다.

## 다음 실행과 미검증 항목

RP5 `192.168.1.32:22`는 이번에 timeout/`No route to host`로 접속하지 못했다. 새 모델 실행·벤치마크·센서 조회·pull 성공 기록은 없다. Host main commit/push 이후 RP5의 main 동기화는 별도로 필요하다.

연결 복구 후에는 [검증 절차](../../docs/research/m3_bounded_vad.md)에 따라 기존 환경/자산 보존 확인 → 읽기 전용 냉각 조회 → 기존 80개 개발 입력의 bounded VAD 실제 실행 → native 대비 경계/PCM/실패 대조 → 실제 30초 초과 활성과 RSS 확인 순서로 진행한다. 18개 보류 표본은 실행하지 않는다. Python ORT와 native ORT 동등성, 실제 단어/음소 보존, 마이크·드롭/백로그·Hybrid 동시 성능은 미검증이다. 사람 판단이 불확실한 라벨은 계속 보류한다.
