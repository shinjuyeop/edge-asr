# M3-3 같은 VAD 구간의 실제 Streaming/Refine 병합

2026-11-03, 실측 소스 `05c3e7b`. [사전 계획](../../docs/research/m33_segment_merge.md)에 따라 RP5에서 기존 KSS50 → 합성120초1개 → 디지털무음6개를 각1회, 총300.115875초의 WAV를 **실제1배속으로 공급**했다. Zip1T+Sense2T+VAD1T, `vad0`, 구간별 Zip 상태 초기화/300ms 보류/100ms 처리의 별도 모드다. 같은 실제 출력에 세 선택 상태기계를 동시에 적용했으며, 원시 재생만으로 지연을 만든 실험이 아니다. UI·스피커 재생·마이크는 실행하지 않았다. [정확한 수치·환경·증거 JSON](m33-segment-merge-20261103.json).

**구간별 결과 수신·병합은 동작했지만 이 모드를 기본값으로 채택하지 않는다.** 파일 종료를 기다리는 구조적 대기는 제거했으나 새 Zip 경로의 CER와 첫 부분 지연이 기존 연속 경로보다 나빠졌다. 기존 연속 Zip·모델·TOML·원본/과거 결과를 유지하고, 다음에는 연속 인식 상태를 보존하는 경계 대응을 검증한다.

## 정확도와 회귀

| 입력 | 과거 연속 Zip CER | 이번 구간 Zip 유지 | 완전 Refine 채택 | 정규화 일치 때만 채택 |
| --- | --- | --- | --- | --- |
| KSS50 / 756자 | 11.64% (88자) | **19.71% (149자)** | 5.56% (42자) | 19.71% (149자) |

| 디지털무음6개 | CER null / 비어 있지 않은 출력0 | null / 0 | null / 0 | null / 0 |

과거 연속 Zip은 원본 WAV 전체를 입력받지만 이번 Zip은 VAD 소유 구간만 입력받고 상태·tail을 구간마다 새로 적용한다. VAD 생략·경계·상태 초기화·청크 위치·보류 등이 함께 다른 조건이며 차이를 한 원인으로 확정하지 않는다. 같은 가중치/원음/정규화의 개발 자료 비교로, 동시 통제 또는 독립 최종 평가는 아니다.

KSS 구간 Zip의 삭제 오류는 과거11→이번43자, 합성은12→23자였다. KSS 원본별로 과거 연속 Zip보다3개 개선/19개 동률/**28개 악화**, 합성1개는 악화했다. 단순히 구간 reset을 생산 경로로 옮길 근거가 없다.

완전 Refine은 이번 구간 Zip보다 KSS37개 개선/11개 동률/2개 악화지만, 더 나은 **과거 연속 Zip 기준으로는25개 개선/17개 동률/8개 악화**다. 나빠진 임시 전사를 기준으로만 개선을 강조하지 않는다. `agreement_only`는 정규화상 같은 구간만 바꿔 CER 개선이0이다. 선택 구간은 KSS Refine11/Zip46, 합성 Refine6/Zip37이었다.

새 VAD 구간의 소유/PCM은 과거 온라인 VAD0과100개 모두 같았고 Refine 전사는100개 모두 일치했다. 따라서 Refine 최종 정확도는 그대로였다. 정답은 선택 후 원본 파일 단위 `ko_cer_v1` 채점에만 썼다. 구간별 정답 시간 경계가 없으므로 구간별 CER는 만들지 않았다. 임의 텍스트 필터·중복 제거·발화별 유리한 모델 선택은 적용하지 않았다.

## 첫 부분과 실제 구간 확정 지연

| 첫 Zip 부분 출력 | 과거 연속 Zip | 이번 구간 Zip |

수신 후 이벤트 적용과 구간 확정은 다르다. Refine이 먼저 와도 Zip 구간 마감이 끝날 때까지 기다리며 마지막 행의 최대값은 KSS64.894ms·합성59.375ms였다. 로컬 Pipe 수신에는 child 원시 기록·직렬화·OS 스케줄링·수신 역직렬화가 포함된다. 각 정책의 순차 상태 적용/계측 비용도 포함했다.

합성은 **43개 중42개가 원본 파일 종료 전에 확정**됐다. KSS도57개 중7개는 파일 종료 전 확정됐다. 이전 파일 단위 재생의 합성 첫 Refine 준비→파일 선택117.604초 대기와 달리 이번에는 구간별 적용을 관측했다. 집계 단위/처리 경로가 달라 배율 개선으로 환산하지 않는다. 음향 정렬·UI/네트워크 표시·마이크 지연은 여전히 미측정이다.

## 자원·큐·열 조건

| 입력 | Zip 호출 RTF | main+Refine 평균 CPU | 동시 관측 RSS 합 최대 | 최고 관측 온도 | 입력/Refine 드롭 |

Zip 호출 RTF는 생성/청크/구간별 tail·최종 native 호출 wall의 합을 전체 WAV 길이로 나눈 공학 지표다. 독립 batch RTF나 첫 자막 지연으로 바꾸지 않는다. 무음의 원시 호출 합은0이지만 ASR0회이므로 모델 RTF 성능을0으로 보고하지 않는다. main 루프 활성 wall 비율은 KSS0.1894/합성0.1795이며 VAD·분배·기록 등이 포함된다.

CPU는1코어=100%, 실제1배속 대기까지 포함한 main+Refine PID 합이다. main에는 VAD·병합3정책·reader·분배/계측이 포함되고 producer는 제외했다. RSS 합은 같은 시각 표본이며 공유 페이지 중복이 가능하다. 무음에도 모델은 로딩된 상태이고 VAD·큐 polling·계측은 실행됐다. 단독 모델 batch CPU와 직접 비교하지 않는다. 실제 TID 표본은 JSON/원시에 보존했고 TID의 native 런타임 역할은 확정하지 않았다.

입력 백로그 관측 최대는 KSS/합성0.2초·무음0.1초, Refine 대기 큐는 최대1작업·무음0이며 종료 시 모두0이었다. 손실/실패/미반환은0이다. 기존 `operational` guard와 실제 main/Refine PID 각각4GiB 제한을 확인했다. 현재 제한·새 이력·필수 계측 결측은 표본상0, 과거 이력0xE는 유지됐다. 팬/OS/클럭 설정은 바꾸지 않았다. 이는 고정 클럭·열평형 통제 비교가 아니다.

## 구현과 검증

- 새 `segment_merge.py`는 기존 유한 큐 위에 실제 결과 수신 reader와 구간 상태를 추가했다. 구간 끝을 모를 때는 `end=null`/`end_bound`를 구분하고 이미 Zip에 공급한 범위를 소급 잘라내지 않는다. 실제 입력 float32 PCM100구간과 청크2,514개를 원본에 대해 검증했다. 동일성은 **실제 원음 payload** 기준이며 Zip 전용0.66초 tail은 별도 모델 설정/호출 비용으로 기록했다.
- `probe-concurrent --segment-merge`의 명시적 별도 경로와 `summarize-segment-merge`를 추가했다. 기존 기본 경로/어댑터/TOML은 유지했다. 원시 Zip/Refine 결과와 병합 입력, 적용 이벤트·최종 스냅샷을 교차 확인하고 Host 재생3회가 RP5 요약과 일치했다.
- Host **255개/33.154초**, RP5 **255개/56.953초** 테스트 통과. 신규9개는 자연 종료/강제 분할·미정 끝·정확한 PCM·지연/역순·무음·실제 IPC·실패 회수·재집계를 모의 모델로 검사했다. 이 테스트를 native 추론 성공과 혼동하지 않는다. 실제 RP5 추론은 위3회로 별도 확인했다.
- 기존 실제9개 기록의 재집계와 M3-2의27개 정책/108개 정책 산출물 불변을 확인했다. 새 원시 **69개 / 11,833,087바이트**의 전송 SHA256이 일치했고, 기존 **5,210개 비 Markdown 파일**은 변경/누락0이었다. Python3.11.18·numpy2.4.6·sherpa2.0.1·Python ORT1.31.1, native ORT1.28.2 및 기록한 시스템 설정을 유지했다. 잔여 실험 프로세스0/동일 부팅도 확인했다.

원시는 양쪽 `results/preflight/m33-segment-merge-20261103-01`, 계획·테스트/실행/보존 로그·검증 집계기는 `results/maintenance/m33-segment-merge-20261103-01`에 보존하고 Git에서 제외한다. 공개 JSON에는69개 전송 해시·입력/모델/소스·재집계·환경/로딩·온도/TID/자원·정확한 지연·과거 대비 개선/악화가 있다. 각 자료1회/같은 개발·스트레스 자료이며100구간을 독립100개 자연 발화로 부르지 않는다.

## 다음 순서

이번 모드는 안전한 구간 대응과 실제 수신/적용 검증용으로 남기고 자동 채택하지 않는다. 다음에는 **기존 연속 Zip 상태를 유지한 채 native tokens/timestamps와 VAD 경계를 대응**시킬 수 있는지 먼저 진단한다. 원문 재구성·시각 원점/범위·부분 결과 안정성·경계 교차 토큰을 실제 API/출력으로 확인해야 한다. 단어 시간을 임의로 만들거나 문자 수를 시간 비율로 나누지 않는다.

이 조건이 맞으면 연속 provisional을 유지하고 확정 가능한 구간만 교정하는 별도 후보를 설계한다. 경계 매핑이 불확실하면 교정을 보류하는 사유를 남긴다. 부분 정확도/첫 표시의 회귀를 먼저 차단한 뒤 실제 병합 지연·개별 악화·입력/Refine 손실을 함께 비교한다. 자연 장문·마이크·UI·사람 검수 경계·장시간 서비스·최종 독립 평가가 남아 있으므로 M3 전체나 Hybrid 배포 완료로 표시하지 않는다.
