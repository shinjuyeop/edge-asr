# M3-1 Streaming + Refine 동시 측정

작업 기준일 2026-11-03. **단독 대조군 4회와 동시 구성 6회, 계획한 10/10회가 실제 RP5에서 성공했다. 입력 드롭·Refine 드롭·실패·미반환은 모두 0이다.** 이번 조건에서 1T+2T의 Refine 반환이 가장 빨랐다. 다만 고정 5초 Refine은 120초 합성 입력에서 Streaming보다 정확도가 나빠, 자동 결과 교체 정책은 채택하지 않는다. [상세 수치·환경·증거 해시 JSON](m31-concurrent-20261103.json), [사전 고정 계획과 명령](../../docs/archive/model-comparison/m31_concurrent.md).

## 조건과 재현 범위

벤치마크 소스는 `acf5136`이다. Host main push 후 RP5를 동기화하고 새 ID `m31-concurrent-20261103-01`로 실행했다. 모델/기존 TOML/전처리/정규화를 유지하고 유효 스레드 설정만 바꿨다. Zipformer encoder/joiner INT8·기존 decoder·tail 0.66초, SenseVoice INT8·`ko`·ITN false·기존 특수 태그 분리, 공통 `ko_cer_v1`이다. 결과 병합·금칙어·중복 제거·전체 WAV fallback은 없다.

RP5 ARM64·Debian 13·Python 3.11.18·NumPy 2.4.6·sherpa/core 2.0.1이다. sherpa 네이티브 ORT **1.28.2**와 별도 설치된 Python ORT **1.31.1**을 구분했다. 이번 VAD 없는 실행에서는 후자의 VAD 추론을 호출하지 않았다. 각 실행에서 모델을 한 번 로딩하고, 자료 첫 발화의 앞 최대 5초로 모델별 3회 워밍업했다. Zipformer 워밍업 30회·SenseVoice 18회이며 로딩/워밍업은 아래 계측에서 제외했다.

- KSS 개발 50개: 원음 **164.919초·756자**, 원본 순서로 이어붙여 1배속 공급했다. 파일 경계에서 Zipformer 상태를 새로 만들고 최종 flush했다. Refine은 파일마다 최대 5초/문맥 0으로 총 **54구간**이다. 순서는 단독1T → 1+1 → 1+2 → 단독2T → 2+1이다.
- 기존 합성 장문 1개: **120.5869초·519자**, 같은 정책으로 **25구간**이다. 위 순서를 뒤집어 실행했다. 자연 대화나 독립 평가 자료가 아니다.
- 조건별 **1회**이며 두 자료의 점수·지연을 합치지 않았다. 공급한 오디오는 총 1,427.5294초, Streaming 원본 평가 **255/255**, Refine 작업 **237/237** 성공이다. 독립 발화 492개로 해석하지 않는다.

독립 입력 프로세스는 100ms/대기 5청크/drop_newest, Refine은 별도 프로세스·대기 2구간/drop_newest다. 고정 구간이 도착하면 같은 청크의 Zipformer decode 전에 Refine에 제출했다. 단독 대조군도 같은 원음 버퍼·구간 해시 계산을 수행했다. 이는 순수 ASR 연산만의 벤치마크가 아니라 두 모델을 동시에 구동하는 계측 도구다.

## 정확도와 구간 정책

| 자료 | Streaming 최종 CER | 고정 5초 Refine CER | 치환/삭제/삽입: Streaming → Refine |
| --- | --- | --- | --- |
| KSS 개발 50개 | 11.64% (88/756) | **5.16% (39/756)** | 71/11/6 → 25/9/5 |
| 120초 합성 1개 | **11.18% (58/519)** | 18.30% (95/519) | 44/12/2 → 20/74/1 |

자료별로 Streaming은 5개 구성의 원문 가설이 같았고, Refine은 3개 동시 구성의 원문 가설이 같았다. 단독 대조군 대비 Streaming 전사 변경은 0개였다. 따라서 이번 Refine의 장문 악화를 스레드 경합이나 입력 드롭 때문이라고 설명할 증거는 없다.

장문 Refine은 Streaming보다 **37자 오류가 많고**, 특히 삭제가 늘었다. 임의의 5초 경계에서 음성/문맥을 자르는 정책이 원인 후보이나, 강제 정렬·다른 분할 정책과의 같은 조건 비교 없이 원인을 확정하지 않는다. 같은 합성 입력의 과거 [전체/VAD0/VAD200](m3-vad-context-20261103.md) 오류는 44/32/37자였다. 이번 고정5초는 95자다. 실행 순서·워밍업·분할·동시 여부가 달라 과거 지연/RTF를 이번 것과 같은 조건으로 합치지 않지만, 구간 정책의 정확도 검증이 필요하다는 근거는 남긴다.

두 출력의 CER를 따로 채점했으며 **최종 Hybrid 병합 CER는 null**이다. KSS에서 Refine이 더 좋다는 이유로 장문에서도 무조건 덮어쓰는 정책은 채택하지 않는다. 이미 점수를 본 KSS/합성 입력/FLEURS100을 최종 독립 평가로 부르지 않는다. 기존 무음 오출력 기록도 그대로 유지한다.

각 성분의 p95를 더해 전체 p95로 만들지 않았다. KSS 파일 끝은 100ms 청크 격자와 일치하지 않아 dispatch에 최대 약 100ms가 포함된다. 장문 1+2의 dispatch p95 39ms도 관측값 그대로 남겼으며 원인은 확정하지 않았다. KSS 원본 중 4개는 5초를 넘어 짧은 마지막 구간이 앞 구간과 연달아 들어올 수 있다. 최종 장문 구간은 0.5869초뿐이므로 파일 끝 지연이 앞선 5초 구간의 p95보다 작을 수 있다.

모든 실행의 입력 이벤트 최대 백로그는 **0.1초**, 동시 구성의 Refine 대기 최대는 **1구간**, 종료 시 대기는 0이다. 공급 100ms 큐·Refine 큐 모두 드롭 0이며 완전한 프레임/구간 순서를 검증했다. 6개 동시 구성에서 232/237개 Refine 호출에 Zip 호출의 wall 겹침이 있었다. 이는 실제 두 호출의 시간 구간 겹침이며 같은 순간의 CPU 코어 병렬 실행 시간을 직접 측정한 값은 아니다.

첫 부분 지연은 **파일 시작→어댑터의 첫 비어 있지 않은 부분 반환**이다. 정답 음향 시작 정렬/마이크/UI 지연이 아니다. Refine 반환은 **구간 끝→자식 어댑터 결과 반환 시각**이며 실제 UI 반영이나 병합 확정 시각이 아니다. 최대 5초의 구간 수집 대기·실제 VAD 종료 판정은 위 Refine 반환 수치에 포함되지 않는다. Zip 최종은 기존 tail/파일 끝 강제 flush를 포함하며 음향 endpoint 검증이 아니다.

이번 `zip_call_rtf`는 호출 wall 합/원본 길이이며 KSS 동시 1+1/1+2/2+1 **0.1447/0.1479/0.1210**, 장문 **0.1294/0.1298/0.1062**다. 입력 대기와 겹친 Refine 시간을 더해 단일 batch RTF를 만들지 않는다. 과거 batch RTF와 1배속 입력의 전체 경과 시간/오디오 길이도 구분한다. 구체적인 호출·coordinator 시간은 JSON/원시에 따로 남겼다.

CPU 표는 재생 시작부터 두 경로의 처리 종료까지 인접한 동일 PID 표본의 CPU 합/관측 시간이다. 모델 PID 내 입력 분배·로그·계측 비용과 대기를 포함하고 독립 입력 PID는 제외한다. 그래서 과거 무대기 Zipformer2T batch의 약 324%와 이번 1배속 평균을 성능 개선율로 비교할 수 없다. 모델 PID RSS 합에는 공유 페이지 중복이 가능하며 실제 시스템 RAM/PSS 총량은 아니다. 입력 자식의 lifetime peak RSS도 JSON에 별도 기록했다.

모델 PID 표본의 실제 평균 간격은 0.1004~0.1006초, 관측 최대 간격은 0.1554초다. TID 표본은 약 1초 간격이며 CPU 활동 기준은 해당 TID 관측 구간 평균 ≥1%다. Zip1T는 활동 1개, Zip2T는 4개, Sense1/2T는 각각 1/2개였다. 전체 TID 수와 실제 활동 수를 구분했고 세션별 풀/spinning의 역할은 확정하지 않았다.

로딩 wall은 Zip **2.431~2.513초**, Sense **1.836~1.876초**, 로딩 중 관측 RSS 최대는 각각 **289.7/422.3MiB**였다. 모델 해시를 먼저 읽었고 OS 캐시를 비우지 않아 cold-storage 로딩으로 부르지 않는다. 워밍업 시간·로딩 CPU/RSS·실제 유효 설정과 가중치 해시는 별도 보존했다.

## 열·보존·검증

기존 `operational` guard와 펌웨어 열 보호를 유지했다. 입장 온도는 **51.8~52.9°C**, 감시 최고는 **66.1°C**였다. 표본상 현재 제한·새 제한 이력·필수 열 계측 결측은 없었고 기존 `0xE` 누적 이력을 구분했다. 600초 timeout·4GiB 주소 공간·코어 덤프 제한과 main/Refine 자식의 실제 제한·프로세스 그룹을 확인했다. 종료 후 coordinator/guard/worker/Refine/input/같은 그룹의 살아 있는 자식은 0이다.

온도만으로 중단하지 않는 운영 검사이며 모든 실행의 `control_valid`는 false다. 고정 클럭/등온 비교나 장시간 냉각 보증이 아니다. 과거 [2T 8분 연속 batch의 85.9°C·스로틀링](m3-operational-20261102.md) 결과도 그대로 유지한다. 이번 1배속·최장 약 2분45초 입력의 낮은 열은 그 결과를 무효화하지 않는다.

- 벤치마크 소스 `acf5136`: **Host 221개(17.461초), RP5 221개(34.623초)** 전체 테스트 통과 후 실행했다. 실제 모델 없는 Host mock/spawn·유한 큐/드롭·실패 회수 검증과 RP5 ARM64 추론을 구분한다.
- 종료 후 `9000b76`에서 빈 정답 출력의 집계 정책을 공통 scorer와 맞추고 **Host 222개(17.439초), RP5 222개(34.561초)** 회귀를 통과했다. 이번 입력의 정답은 모두 비어 있지 않아 기존 10회 요약이 새 코드의 재집계와 정확히 일치했다. 이 수정으로 실제 벤치마크를 다시 실행하지 않았다.
- 원시 **176개(26,915,159바이트)**의 RP5↔Host SHA256, 10개 요약 재집계, 원본 WAV/manifest/가중치/설정·실제 Refine float32 payload·태그 분리·프레임/구간 FIFO·외부 제한을 교차 확인했다. 잘못된 지연이나 손실을 0으로 채우지 않았다.
- 기존 `.venv/models/data/results/experiments` 비 Markdown **4,286개 변경·누락 0**이다. 기록한 Python·패키지·시스템 설정과 부팅 ID가 같았고 RP5 작업 트리가 깨끗했다. 회귀 테스트 후 별도 `preservation-final.json`에서도 같은 보존 결과를 확인했다. 새 모델·데이터·패키지를 설치하거나 원본 결과를 수정하지 않았다.
- 원시: 양쪽 `results/preflight/m31-concurrent-20261103-01/`; 계획/실행 순서/보존/테스트/감사/재집계: `results/maintenance/m31-concurrent-20261103-01/`. Git에는 코드·문서·작은 요약만 포함한다. 날짜는 클라이언트 작업일이며 원시 UTC/monotonic 값은 기기 기록 그대로다.

## 종합 판단과 다음 과제

**다음 공학 실험의 기본 후보는 Zip1T+Sense2T**, CPU가 더 낮은 1T+1T는 대조군으로 유지한다. 이번 두 자료에서 1+2의 Refine 반환 p95가 가장 작고 입력/Refine 손실은 없었다. 2+1의 약 7ms 빠른 KSS 첫 부분 p50에 비해 CPU 비용은 컸으며 단회 관측으로 그 작은 지연 차이의 유의성을 확정하지 않는다. 기존 기본 TOML이나 배포 정책을 자동으로 바꾸지 않는다.

다음 우선순위는 스레드를 더 늘리는 일보다 **Refine 구간 경계와 결과 교체의 정확도 검증**이다.

1. 같은 개발/스트레스 입력에서 고정5초와 기존 bounded VAD/EOF/강제 상한의 Refine 출력을 먼저 비교한다. 시작 여유와 강제 분할 문맥을 분리하고 원문·빈 출력·무음 오출력·악화 사례를 모두 남긴다. 이번 결과를 보고 유리한 발화만 골라 채택하지 않는다.
2. 선택 후보로 1배속 동시 실행을 다시 검증해 VAD endpoint·구간 수집·dispatch·큐 대기·모델 반환을 각각 측정한다. 기준선 1+1과 유한 큐/드롭 기록을 유지한다. 지연 허용치·교체 시점은 사용자 요구와 함께 정해야 한다.
3. 그 뒤 제한된 결과 병합을 구현하고 실제 병합 CER·수정/악화율·자막 안정성·누락을 측정한다. 현재 두 개의 별도 CER를 병합 성능으로 대신하지 않는다.
4. 다양한 자연 장문·잡음·짧은 발화·무음과 최종 보류 자료, 이후 마이크/화면/장시간 운영으로 확장한다. 독립 평가·사람 검수·반복 분산·실사용 endpoint·실서비스 RAM/전력은 여전히 미검증이다.

이번 완료 범위는 **고정 구간 동시 계측과 비교**다. 최종 Hybrid 런타임·자막 병합·마이크·M3 전체 완료를 뜻하지 않는다.
