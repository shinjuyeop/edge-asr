# M3-0 후속: 연속 입력과 강제 구간 상한 검증

2026-10-29. **전처리 → VAD → 길이 제한 구간의 기계적 계약을 구현하고 RP5에서 검증했다.** 수정 후 1,048행과 구간 PCM 1,749개를 검증했으며, 독립 입력기를 사용한 1배속 52회 재생에서 입력 드롭은 0이었다. **VAD 정책과 Hybrid 서비스는 아직 승인하지 않는다.** 기존 누락·잡음 오탐, native 활성 구간 30초 제한, 미해결 고부하 냉각 조건이 남아 있다.

## 실제 구현과 첫 실패

초기 `ae94d27` 구현은 활성 VAD에 `flush()`를 호출해 버퍼를 비우는 방법이었다. RP5의 두 번째 입력 `kss-train-01000-quiet24`, 3초 상한에서 native 로그 `Invalid n: -2752`와 잘못된 구간 반환이 발생했다. 첫 실행은 실패로 중단했고, 완료된 1행과 실패 로그를 `results/preflight/m3-segments-20261029-01/`에 보존했다. 냉각 실패로 분류하지 않는다. Host mock 통과가 실제 API 동작을 보장하지 않음을 확인한 사례다.

수정한 `0971c07`에서는 활성 VAD를 flush/reset하지 않고, **외부 공통 PCM 버퍼에서 소유 구간만 나눈다.** 입력 종료 때만 native flush, 새 세션에서만 reset한다. 네이티브 종료가 없는 구간은 내부 버퍼 31초·활성 예산 30초로 제한하고, 초과 윈도 공급 전에 명시적으로 실패 중단한다. 무기한 지속 음성을 처리할 수 있다는 뜻은 아니다. 수정 후 모든 실측은 새 ID `m3-segments-20261029-02`에 저장했다.

- 16kHz/100ms 블록에서 gain/RMS 상태를 유지하고, 512프레임 VAD 입력으로 재조립한다. 잔여 프레임과 EOF 패딩을 구분한다.
- 소유 범위는 `[start,end)`, 상한은 3/5/8초다. 왼쪽 문맥 최대 200ms를 추가한 실제 전달 PCM 상한은 각각 **3.2/5.2/8.2초**다. 구간마다 ID·시각·소유/문맥 범위·PCM 해시를 남긴다.
- 외부 PCM 버퍼 용량은 67,200/99,200/147,200프레임, 재조립 버퍼는 최대 2,111프레임이다. 실제 요청 범위가 사라졌거나 상한을 위반하면 실패한다. 재생 WAV는 전체를 메모리에 준비하므로 이 용량을 전체 프로세스 메모리로 해석하지 않는다.
- 기존 독립 WAV producer와 100ms/4칸 큐를 재사용했다. 드롭이 있으면 압축된 시간축을 정상 구간 결과로 채택하지 않는다. 실제 ASR·텍스트 병합·마이크는 연결하지 않았다.

## 입력·환경·비교 범위

기존 Python 3.11.18, NumPy 2.4.6, sherpa/core 2.0.1, Silero ONNX 파일을 그대로 사용했다. 네이티브 ORT는 1.28.2이며 Python onnxruntime 패키지 1.31.1과 구분한다. VAD 1T, threshold 0.5, 최소 음성 0.1초, 종료 무음 0.3초, **native soft limit 5초는 모든 외부 상한 후보에서 고정**했다. 새 모델/패키지 설치나 OS 냉각 설정 변경은 없었다.

기존 KSS 50개 × 원음/감쇠/감쇠+잡음 150개, 무음 6개·연결 장문 3개·Gaussian 잡음 6개·연속 입력 1개, 총 166개를 재사용했다. 원형/RMS 공통 정책을 비교하되 **앞 0.5초·뒤 1초 무음까지 전처리 상태에 포함**했다. 이전 사전 생성 RMS WAV는 본문만 처리했으므로 조건이 다르며, 과거 결과의 개선 수치로 비교하지 않는다. 원본/이전 파생 WAV는 수정하지 않았다.

- 빠른 입력: 166개 × 3상한 × 2정책 = 996행.
- 기본 1배속: 짧은 KSS 10개+무음 6개+잡음 6개+연속 입력+약 30초 연결 입력, 24개 × 2정책 = 48행. 상한 5초.
- 기본 1배속 목록에서 강제 분할이 0회였으므로, 빠른 입력에서 두 정책 모두 5초를 넘긴 동일 발화 `kss-train-01025-clean`(5.853초)을 골라 3/5초 × 2정책 = 4행을 추가했다. `boundary-plan.json`에 목적을 고정한 **코드 경계 검사**이며 정확도/성능 표본의 대표성을 주장하지 않는다.

총 1,048행은 같은 개발 입력의 설정별 실행이다. 독립 발화 1,048개, 최종 독립 평가, 새로운 ASR CER 측정이 아니다. 모델별/후보별 워밍업 제외는 따로 하지 않았으며 로딩 시간은 별도 기록했다.

## 구간 상한·PCM 결과

| 소유 상한 | 원음: 강제 분할 수 / 실제 최대 소유 길이 | RMS: 강제 분할 수 / 실제 최대 소유 길이 |
| --- | ---: | ---: |
| 3초 | 132 / 3.000초 | 121 / 3.000초 |
| 5초 | 9 / 5.000초 | 3 / 5.000초 |
| 8초 | 0 / 6.112초 | 0 / 5.600초 |

빠른 입력의 정책·상한별 166개 집계다. **8초 경계의 실제 강제 분할은 이 자료에서 발생하지 않았다.** 8초 초과 지속 음성의 소유 프레임 보존·조기 반환은 Host/RP5 mock 단위 테스트로 검증했다. 실제 VAD가 30초 예산에 도달하는 상황도 이번 자료에서는 관측하지 않았다. 해당 중단 분기는 mock 테스트와 코드로 확인했으며 실제 장시간 무중단 음성 검증과 구분한다.

모든 구간 payload 1,749개가 Host에서 계산한 동일 전처리 PCM 범위와 해시 일치했다. 외부 버퍼·native 활성 예산·소유 길이·반환 ID·문맥 상한 위반은 없었다. **VAD가 무음으로 판단해 생략한 부분까지 모두 보존했다는 뜻은 아니다.**

자연 VAD 종료가 확정될 때 후미 대기 구간을 제외하면 이미 강제 확정한 소유 구간보다 끝이 앞설 수 있다. 이 여분은 취소하지 않고 `committed_tail_overhang_frames`에 보존했다. 빠른 입력 3초 후보에서 원음 28,160프레임, RMS 57,344프레임, 5초 후보에서 원음 640프레임이었다(각 집계 전체의 합). 이는 음소 종료 정렬이나 단어 잘림 측정이 아니다. 강제 분할에는 자연 endpoint 지연을 기록하지 않는다.

별도 1배속 경계 검사 결과는 다음과 같다. **각 칸은 동일 발화의 1회 측정**이며 p50/p95나 일반적인 지연 보장이 아니다.

| 전처리 | 상한 | 소유 / 문맥 포함 길이 | 소유 끝 시각 이후 반환 시간 |
| --- | ---: | ---: | ---: |
| 원음 | 3초 | 3.0 / 3.2초 | 103.16ms |
| 원음 | 5초 | 5.0 / 5.2초 | 103.47ms |
| RMS | 3초 | 3.0 / 3.2초 | 102.83ms |
| RMS | 5초 | 5.0 / 5.2초 | 104.54ms |

100ms 수집·512프레임 재조립·큐·계산을 포함한 반환 시각이다. 소유 오디오 길이는 제한되지만 벽시계 지연을 3/5초 이내로 보장하는 서비스는 아니다. ASR 첫 자막 또는 Refine 확정 지연도 아니다.

## VAD 정책은 여전히 미승인

| 개발 항목 | 원음 | RMS |
| --- | ---: | ---: |
| 빠른 입력의 음성 파일 전체 누락(각 후보) | 0/154 | 0/154 |
| 연속 입력 안 발화 구간 전체 누락 | **5/9** | **0/9** |
| 합성 잡음 오탐 | **2/6** | **4/6** |
| 순수 무음 오탐 | 0/6 | 0/6 |

연속 구간 누락과 오탐 사례는 기본 1배속에서도 유지됐다. 같은 짧은 원본 3개를 음량 조건별로 반복한 개발 입력이며, 단어 정확도나 실제 다화자 환경 누락률이 아니다. 같은 잡음의 반복을 독립 표본으로 합치지 않는다. threshold 조정·금칙어 필터·실패 사례 삭제는 하지 않았다. 전체 파일 누락 0만으로 Refine 호출 정책을 승인할 수 없다.

## 1배속 큐·자원·시간

전체 52회 재생에서 **3,084개 청크를 수집했고 드롭 0**, 관측 최대 큐 오디오량은 0.1초였다. 이는 큐에 담긴 오디오의 길이이며 실제 대기시간 100ms를 뜻하지 않는다. 기존 4칸 큐의 상한은 0.4초다. producer/소비 이벤트로 백로그를 다시 계산해 일치를 확인했다.

| 기본 24개/정책 | 원음 | RMS |
| --- | ---: | ---: |
| 큐 대기 p95 | 1.13ms | 1.12ms |
| 입력 대기 제외 파이프라인 계산 RTF | 0.03563 | 0.03735 |
| 전체 호출 시간 기준 부모 평균 CPU | 5.24% | 5.50% |
| 부모 관측 최대 RSS | 74.72 MiB | 74.83 MiB |
| producer 생애 최대 RSS의 최댓값 | 78.78 MiB | 75.38 MiB |
| 짧은 원음 KSS 10개 WAV 끝 대리 지연 p50/p95 | 0.335 / 0.389초 | 0.334 / 0.389초 |

RTF 분모는 앞뒤 무음을 포함한 공급 PCM 시간, 분자는 기존 replay 계측의 전처리·VAD·구간 호출 시간이다. ASR batch RTF와 다르다. CPU는 부모 프로세스의 파일 호출 구간이며 producer CPU는 별도 원시에 있다. 서로 다른 시점의 두 프로세스 RSS 최댓값을 더해 동시 최대 메모리로 주장하지 않는다. 파일 I/O·모델 로딩·프로세스 준비와 실제 입력 시작 시각도 구분했다.

WAV 끝 대리 지연은 실제 음성 끝 정렬이 없는 10개 짧은 원음에 한정했다. 전체 파일 집계에는 연속 파일 뒤쪽 누락 때문에 큰 음수 대리값도 있으며 원시/JSON에서 보존했다. **실제 음소 종료, 단어 보존, ASR 첫 부분 출력, Refine 대기·확정 시간은 미측정(null)**이다.

빠른 입력의 파이프라인 RTF는 0.02812~0.02850, 부모 CPU 약 100%, 관측 최대 RSS는 85.58~107.27 MiB였다. 재생 속도와 동적 클럭 조건이 달라 1배속 수치와의 차이를 최적화 효과로 계산하지 않는다.

## 냉각·보존·검증

- 수정 후 빠른 입력의 최고 온도는 원음 62.8°C, RMS 63.9°C, 기본 1배속은 58.4/57.3°C, 추가 경계 검사는 양쪽 55.65°C였다. 여섯 실행 모두 기존 53°C 이하 시작 조건·75°C 중단선·현재 제한 감시·외부 600초/주소 공간 4GiB 제한을 통과했다.
- 현재 제한 비트는 관측 표본에서 0, 기존 이력 `0xe0000`은 유지됐다. 1Hz 관측이 순간적 제한을 모두 배제하지는 않는다. 고정 클럭·실내 온도·열평형 통제도 아니다. 팬·히트싱크 변경 없음이라는 사용자 보고를 유지하며 **기존 Zipformer 2T 76°C 중단은 해결된 것으로 보지 않는다.**
- Host 전체 **144개 테스트 통과(최종 7.648초)**, RP5 **144개 통과(13.003초, 실측 코드 `0971c07`)**. native 활성 flush 사용 금지, 예산 초과 중단, 후미 끝의 되돌림, 지속 음성 프레임 계약, 실제 과부하 드롭 실패를 추가 검사했다. 기존 ASR 테스트는 통과했지만 기존 ASR 추론을 다시 실행한 것은 아니다.
- 최초 보호 파일 **4,058개**, 첫 실패 기록과 새 목록을 포함한 두 번째 보호 파일 **4,073개**를 대조해 모두 동일했다. 모델·원본·이전 실험·가상환경 파일과 설치 패키지 목록/버전의 변경·삭제가 없었다.
- 새 원시 **210개 파일**을 Host로 복사해 해시 일치 확인. 해시 목록 SHA-256은 `608c834d20b0bd50068aba2a82aefe649b4a16c8c43707077e2b537024228d37`이다. 첫 실패 원시는 두 번째 보호 스냅샷에도 포함된다.

## 변경 파일과 다음 단계

새 `src/edge_asr/segmentation.py`, `scripts/prepare_segmentation_cases.py`, `scripts/m30_segment_probe.py`, `scripts/summarize_segment_probe.py`, `tests/test_segmentation.py`, `tests/test_segment_summary.py`를 추가했다. `src/edge_asr/vad_probe.py`는 선택적인 `endpoint_eligible` 표시를 지원하며 기존 입력의 처리 계약은 유지한다. 한국어 절차와 README·이번 요약을 추가했다. 기존 모델 어댑터·설정·정규화 정책은 변경하지 않았다.

1. **자연 초단문·잡음·음소 경계를 보완한다.** 200ms 안팎 짧은 응답, 실제 환경 잡음과 연속 문맥의 개발 자료를 확보하고 사람 검수 경계를 붙인다. 현재 5/9 누락과 4/6 오탐 사례를 고정 회귀 목록으로 유지한다. 튜닝 전에 후보·판정 기준을 고정하며 최종 미사용 자료는 분리한다.
2. **native 30초 한계를 해소할 방식을 검토한다.** 기존 Python API는 활성 내부 PCM을 부분적으로 제거할 수 없어 실패 중단으로 보호한다. 무중단 서비스에는 더 낮은 수준의 VAD 확률/상태 API나 별도 백엔드 검토가 필요하다. 조용히 reset하거나 입력을 재생해 결과를 이어붙이지 않는다. 새 방식은 기존 검출 결과·구간 경계와 별도 비교한다.
3. **물리적 냉각 확인 후 고부하 조건을 재검증한다.** 팬 동작·히트싱크 접촉·케이스 통풍·주변 온도를 확인하거나 재현 가능한 부하 제한을 정한다. 통과 전 ASR 동시 부하를 재개하지 않는다.
4. 이후 M3-1에서는 공통 PCM을 Zipformer와 Refine에 공급하고, ASR별 독립 프로세스·Refine 제한 큐·enqueue/start/finish 시각·skip/드롭·CPU/RSS·온도를 계측한다. 1T+1T, 1T+2T, 2T+1T의 실제 동시 성능을 단독 결과로 예측하지 않는다. 서비스 병합/UI는 별도 단계다.
